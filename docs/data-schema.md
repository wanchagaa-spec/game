## 1. ภาพรวมกลไก

```
ฆ่าบอส ──► แย่งไข่ (กดค้าง 3 วิ) ──► ฟักที่สวน ──► ตัวแม่ (ตัวละคร + น้ำหนัก)
                                                        │
                                        ┌───────────────┴───────────────┐
                                   วางในคอก                        เก็บในกระเป๋า
                                   (ผลิตลูก + ผลิตเงิน)              (ไม่ผลิตอะไรเลย)
                                        │
                        ┌───────────────┴──────────────┐
                   กองลูก (รวมเป็นกอง)              เงิน
                        │                              │
                   ส่งไปพังกำแพง                 ซื้ออาวุธ/อัปคอก/อัปอัตราผลิต
                        │                              │
                   เปิดด่านถัดไป ◄────────────────────┘
                        │
                   บอสด่านใหม่ → ไข่ดีขึ้น → วนซ้ำ
```

**1 เซิร์ฟเวอร์ = 6 คน ใช้แมพร่วมกัน แต่กำแพงเป็นของแต่ละคน** (คอก 6 แปลง = 6 คนพอดี · ผัง `docs/map-layout.md`) พื้นที่บอสใช้ร่วมกัน เข้าได้เฉพาะคนที่พังกำแพงถึงด่านนั้น

หลักการที่ยึดทั้งเอกสาร:

| หลักการ | เหตุผล |
|---|---|
| **เซฟเฉพาะสิ่งที่ derive กลับไม่ได้** | ตัวคูณคลาส · สูตร damage · ราคา · HP ด่าน อยู่ใน Config ทั้งหมด เซฟแค่ id/น้ำหนัก/เลเวล แล้ว lookup ตอน runtime — บาลานซ์ใหม่ทีหลังไม่ต้อง migrate |
| **เวลาเป็น timestamp สัมบูรณ์** | `os.time()` (Unix UTC) ไม่ใช่ "เหลืออีกกี่วินาที" ทั้งไข่และการผลิตลูกจึงเดินต่อข้ามการออกเกมได้ |
| **id เป็นสัญญาถาวร** | `charId` / `eggId` / `statusId` ที่เขียนลง DataStore แล้ว เปลี่ยนไม่ได้ตลอดชีวิตโปรเจกต์ |
| **น้ำหนักแม่เป็นจำนวนเต็มเสมอ** | เพราะมันคือส่วนหนึ่งของ stack key ทศนิยมเข้ามาเมื่อไหร่กองแตกทันที ([§4](#4-stack-key--หัวใจของระบบกองลูก)) |
| **ทุกอย่างที่ตัดสินผลทำที่ server** | โดยเฉพาะการแย่งไข่ ([§12](#12-จุดที่เสี่ยงโดนโกง-exploit)) |

## 2. ขอบเขตข้อมูล 3 ชั้น

| | **ต่อผู้เล่น** (เซฟลง DataStore) | **ต่อเซิร์ฟเวอร์** (memory หายเมื่อ server ปิด) | **ชั่วคราวระหว่างรบ** (หายเมื่อจบตา) |
|---|---|---|---|
| **เก็บอะไร** | แม่ในคอก · แม่ในกระเป๋า · กองลูก · เลเวลคอก · เลเวลอัตราผลิต · เลเวลอาวุธ · เงิน · `wallProgress` · ไข่ที่ฟังอยู่ · ไข่ในกระเป๋า · แม่ในสนามรบ (`battleRoster`) · ธงรางวัลผ่านด่าน · สถิติ | บอสด่านไหนเกิดอยู่ + HP ปัจจุบัน · ไข่ที่วางอยู่ในรังตอนนี้ · ใครกดค้างหยิบไข่อยู่ + กดมากี่วินาที · ใครอยู่ในพื้นที่บอส · โมเดลทหารฝ่ายรับที่ render อยู่ | HP ทหารฝ่ายรับที่เหลือ · HP กำแพงที่เหลือ · กองทัพที่ส่งไปและที่เหลือรอด |
| **อยู่ที่ไหน** | DataStore `PlayerData_v1` key `player_<UserId>` · **log ธุรกรรม Robux อยู่ DataStore แยก** `PurchaseLog_v1` | ตาราง Lua ใน ServerScriptService | ตาราง Lua ระหว่างคำนวณ |
| **หายแล้วเป็นไง** | ผู้เล่นเสียของถาวร — ห้ามหาย | เกิดใหม่ได้เอง บอสรีเกิดทุก 5 นาทีอยู่แล้ว | คำนวณใหม่ได้จาก PlayerData |
| **ใครเห็น** | เจ้าของคนเดียว | ทุกคนในเซิร์ฟเวอร์ | เจ้าของคนเดียว |

**จุดที่ต้องระวังที่สุด:** `wallProgress` อยู่ฝั่งซ้าย ไม่ใช่ฝั่งกลาง
ความคืบหน้ากำแพงเป็น**ของแต่ละคน** ถ้าเผลอเก็บไว้ฝั่งเซิร์ฟเวอร์ ผู้เล่นจะเสียความคืบหน้าทุกครั้งที่ server ปิด และคนที่เข้ามาใหม่จะได้ด่านของคนอื่นไปฟรี ๆ

ส่วนไข่ในรังอยู่ฝั่งกลางเพราะเป็นของกลางที่ทุกคนแย่งกัน **จนกว่าจะมีคนหยิบสำเร็จ** ตอนนั้นมันถึงย้ายไปฝั่งซ้าย (เข้าสวนฟักของคนนั้น)

## 3. โครงสร้าง PlayerData

```lua
PlayerData = {
    schemaVersion = 3,                     -- number  v2 = battleRoster (3C-1) · v3 = stageClearBonusGranted (4A) · ดู §10.4

    currency = {
        coins = 500,                       -- number  ได้จากแม่ในคอก ใช้ซื้อทุกอย่าง
        gems  = 0,                         -- number  พรีเมียม ยังไม่มีที่ใช้
    },

    -- ══ แม่ในคอก ══ ผลิตลูก + ผลิตเงิน  จำนวน ≤ Config.getPenCapacity(penLevel)
    mothersInPen = {
        {
            uid            = "1234567-1",  -- string   "<UserId ผู้ฟักคนแรก>-<เลขนับ>" ไม่ซ้ำทั้งเกม
            charId         = "wukong",     -- string   Config.Characters (กำหนดคลาส → ตัวคูณ damage/HP)
            weight         = 1500,         -- number   kg จำนวนเต็ม สุ่มตอนฟัก
            statuses       = { "gold" },   -- {string} สถานะที่ติดอยู่ตอนนี้
            lastProducedAt = 1757740000,   -- number   os.time() ที่ settle การผลิตไปถึงแล้ว
            obtainedAt     = 1757700000,   -- number   os.time() ตอนฟักออกมา
            locked         = false,        -- boolean  กันเผลอส่งไปรบ/ขาย
        },
    },

    -- ══ แม่ในกระเป๋า ══ ไม่ผลิตอะไรเลย  จำนวน ≤ Config.Balance.Bag.CAPACITY (100)
    -- โครงเหมือนกันทุกฟิลด์ ยกเว้นไม่มี lastProducedAt (ไม่ได้ผลิตจึงไม่ต้องนับเวลา)
    mothersInBag = { ... },

    nextUid = 2,                           -- number  เลขนับของผู้เล่นคนนี้ ห้ามรีเซ็ต ห้ามลด
                                           --         uid เต็ม = Config.makeUid(UserId, nextUid)

    -- ══ กองลูก ══ dictionary: stack key → จำนวน (ดู §4)
    children = {
        ["wukong|1500|gold"]        = 482000,
        ["wukong|1500|gold,silver"] = 9600,
        ["fish|300|"]               = 12,
    },

    -- ══ เลเวลต่าง ๆ ══
    penLevel        = 1,                   -- number  1..Config.Balance.Pen.MAX_LEVEL (10)
    productionLevel = 0,                   -- number  0..Config.Balance.Production.UPGRADE_MAX_LEVEL (5)
    damageLevel     = 0,                   -- number  0..Config.Balance.DamageUpgrade.MAX_LEVEL (72)
                                           --         ตัวคูณ damage ของกองทัพที่ซื้อด้วยเงิน
                                           --         ⚠️ เป็นของ "บัญชีผู้เล่น" ไม่ใช่ของแม่รายตัว
                                           --         เพดาน = wallProgress × 8 (ดู §8.6)
    weaponLevel     = 1,                   -- number  1..Config.Balance.Weapon.MAX_LEVEL (10)
    speedLevel      = 0,                   -- number  0..Config.Balance.SpeedUpgrade.MAX_LEVEL (5)
                                           --         ความเร็ววิ่งที่ซื้อด้วยเงิน
                                           --         ⚠️ เป็นของ "บัญชีผู้เล่น" ไม่ใช่ของตัวละคร
                                           --         ตายแล้วเกิดใหม่ต้องได้ความเร็วเดิมกลับมา
                                           --         ไม่มีเพดานผูกกับด่าน ซื้อได้เรื่อย ๆ ถ้ามีเงิน (ดู §8.8)
    wallProgress    = 1,                   -- number  ด่านสูงสุดที่พังกำแพงได้แล้ว 1..9
                                           --         เป็นตัวคูณเงินด้วย (×10 ต่อด่าน)

    -- ══ ไข่ที่กำลังฟักในสวน ══ array ยาวคงที่ = Config.Balance.Hatchery.MAX_SLOTS (50)
    -- ⚠️ ต้องเป็น array ไม่ใช่ dict ที่ key เป็นตัวเลข (เหตุผลใน §9.3)
    --
    -- ⚠️ ไข่ทุกฟอง "มีน้ำหนักของตัวเอง" ตั้งแต่ตอนบอสวางไข่ในรัง
    -- ไม่ใช่สุ่มตอนฟัก — เพราะขนาดโมเดลไข่ในรังบอกน้ำหนักให้ผู้เล่นเห็น
    hatching = {
        {
            eggId     = "egg_stage3",      -- string  ไข่ของด่าน 3 (บอสด่าน N วางไข่ด่าน N)
            weight    = 1500,              -- number  kg จำนวนเต็ม ล็อกตั้งแต่ตอนวางไข่
            charId    = "wukong",          -- string? ตัวละครที่จะฟักออกมา — สุ่มไว้แล้วตั้งแต่
                                           --         ตอนวางไข่ (ไม่ใช่ตอนฟักเสร็จ) เพราะเวลาฟัก
                                           --         ต้องใช้คลาสมาคำนวณ (§5.1) ⚠️ ห้ามส่งให้
                                           --         client เห็นก่อนฟักเสร็จ — ความเซอร์ไพรส์ตอน
                                           --         ฟักยังต้องอยู่ครบ · optional เพื่อรองรับ
                                           --         ช่องที่ค้างฟักจากก่อนเพิ่มฟิลด์นี้ (ดู §5.1)
            startedAt = 1757740000,
            hatchAt   = 1757740120,
        },
        false,                             -- ช่องว่างใช้ false ห้ามใช้ nil
        -- ... รวม 50 ช่อง
    },

    -- ══ ไข่ที่ยังไม่เอาเข้าสวน ══ เพดาน Config.Balance.Hatchery.BAG_CAPACITY (1,000)
    -- ⚠️ เป็นคนละเพดานกับ hatching ข้างบน (50) — คุมคนละเรื่อง ห้ามเอามารวมกัน
    --
    -- ⚠️ **ไม่ใช่อาเรย์ยาวคงที่แล้ว** (เปลี่ยนตอน Phase 2A) เก็บเฉพาะฟองที่มีจริง
    -- โครงเดิมเติม false จนครบความจุ → ถ้าเป็นแบบนั้นที่เพดานนี้จะต้องเขียน false เป็นพันตัวลง
    -- DataStore ทุกครั้งที่เซฟ ต่อให้ผู้เล่นถือไข่จริงแค่ 10 ฟอง (โครงใหม่เก็บแค่ ~1.4 KB)
    --
    -- ⚠️ **แต่ละฟองมี `id` ประจำตัว** ไม่ใช่อ้างด้วยตำแหน่งในอาเรย์
    -- เพราะอาเรย์แน่น ลบฟองหนึ่งแล้วฟองที่อยู่หลังเลื่อนตำแหน่งทั้งแถว (ดู §3.3)
    heldEggs = {
        nextEggId = 128,                   -- number  ตัวนับ **ห้ามลด ห้าม reuse**
        items = {                          -- array แน่น ไม่มีรู ไม่มี false
            { id = 125, eggId = "egg_stage1", weight = 320 },
            { id = 127, eggId = "egg_stage3", weight = 48000 },
        },
    },

    -- ══ session lock ══ กันผู้เล่นคนเดียวเปิดสองเซิร์ฟเวอร์พร้อมกัน
    -- ไม่มีตัวนี้ = สองเซิร์ฟเวอร์ถือข้อมูลคนละชุด ใครเซฟทีหลังทับของอีกคนทั้งชุด
    -- `nil` ตอนไม่มีใครถือ · ปลดทุกครั้งที่ผู้เล่นออกจากเกม
    sessionLock = {
        jobId   = "0a1b2c...",             -- string  game.JobId ของเซิร์ฟเวอร์ที่ถืออยู่
        placeId = 123456789,               -- number  ไว้ดีบั๊กว่ามาจาก place ไหน
        at      = 1757740000,              -- number  os.time() ตอนตั้ง/ต่ออายุ
    },

    lastSaveAt = 1757740000,               -- number  os.time() ของการเซฟครั้งล่าสุด

    -- ══ ความคืบหน้าการตีแต่ละด่าน — สะสมถาวร ══
    -- ⚠️ array ยาวคงที่ = Config.Balance.Stage.COUNT (9) · ช่องว่างใช้ false (ดู §9.3)
    --
    -- ทหารฝ่ายรับ **ตายแล้วไม่เกิดใหม่** และ HP กำแพงที่ตีไปแล้วไม่คืน
    -- ทั้งสองค่าต้องเซฟลง DataStore ไม่รีเซ็ตเมื่อออกเกมหรือเซิร์ฟรีสตาร์ท
    -- ไม่งั้นผู้เล่นที่ตีมาครึ่งด่านแล้วเน็ตหลุดจะเสียงานทั้งหมด
    -- และจะไม่มีวันผ่านด่านที่ใช้เวลานานกว่า session เดียว
    stageProgress = {
        false,                             -- ด่าน 1 ไม่มีกำแพง ไม่ต้องเก็บอะไร
        false,                             -- ด่าน 2 พังไปแล้ว
        {
            defendersRemaining = 4500,     -- number  ทหารฝ่ายรับที่เหลือ (จาก 1,000 ของด่าน 3)
            wallHpRemaining    = 50000,    -- number  HP กำแพงที่เหลือ
        },
        false, false, false, false, false, false,
    },

    -- ══ ธงรางวัลผ่านด่าน (Phase 4A · schema v3) ══ ดู §7.12
    -- ⚠️ อาเรย์ boolean ยาวคงที่ 9 ช่อง index ตรงกับ stageProgress · true = ได้ไข่ฟรีของด่านนั้นไปแล้ว
    -- ⚠️ false ≠ "ยังไม่พัง" — ผู้เล่นที่พังด่านไปก่อนอัปเดต v3 ได้ false ทั้งหมด และ**ไม่ได้ไข่ย้อนหลัง**
    stageClearBonusGranted = { false, true, false, false, false, false, false, false, false },

    -- ══ สถานะปุ่มอัญเชิญ ══
    -- true = ปล่อยทหารต่อเนื่องอัตโนมัติ · false = หยุดปล่อย สะสมไว้ในคลัง
    -- กลไกหลักของเกม: สะสมกองใหญ่แล้วปล่อยรวดเดียวทะลุ
    -- ดีกว่าปล่อยทีละตัวแล้วถูกกินทีละตัว
    summonEnabled = true,                  -- boolean

    -- true เฉพาะตอนที่ auto-pause (§7.6) เป็นคนปิด summonEnabled ให้เอง (ตีไม่เข้า)
    -- ผู้เล่นกดปิดเองไม่ตั้งค่านี้ — ใช้แยกว่าจะโชว์แจ้งเตือนไหม (3B) · เคลียร์กลับ false
    -- เองตอนผู้เล่นกดเปิดปุ่มอัญเชิญใหม่
    combatAutoPaused = false,              -- boolean

    -- ══ ลำดับปล่อยทหารที่ผู้เล่นจัดเอง (Phase 3A) ══
    -- อาเรย์ของ stack key (Config.makeStackKey()) หัวอาเรย์ = ปล่อยก่อน
    -- ⚠️ กองที่หมด (count = 0 / ไม่มีใน children) ยังค้างอยู่ในนี้ ไม่ถูกลบ (เผื่อผลิตเพิ่ม
    -- มาเติมทีหลังจะกลับมาอยู่คิวเดิม) · กองใหม่ที่ยังไม่เคยอยู่ในนี้ถูกต่อท้ายอัตโนมัติ
    releaseOrder = {
        "wukong|1500|gold", "wukong|500|",
```

### 3.2 ทำไม `uid` ต้องเป็น global

```
Config.makeUid(1234567, 42)   →  "1234567-42"
Config.parseUid("1234567-42") →  1234567, 42
```

`UserId` ในนี้คือ **ผู้เล่นที่ฟักแม่ตัวนี้ออกมาครั้งแรก** ไม่ใช่เจ้าของปัจจุบัน — **ห้ามเปลี่ยนตอนเทรด** เพราะจุดประสงค์คือความไม่ซ้ำ ไม่ใช่การบอกว่าใครเป็นเจ้าของ

**เหตุผล:** มีแผนจะทำเทรดแม่ระหว่างผู้เล่น ถ้า uid เป็นเลขที่ไม่ซ้ำแค่ในคนเดียว:

```
ผู้เล่น A มีแม่ uid = 5 (ซุนหงอคง 1,500 kg)   ทีมของ A ชี้ uid 5
ผู้เล่น B มีแม่ uid = 5 (ปลา 100 kg)          ทีมของ B ชี้ uid 5

B เทรดแม่ uid 5 ให้ A  →  A มีแม่ uid 5 สองตัว
                       →  ทีมของ A ชี้ตัวไหน? ไม่มีทางรู้
```

แก้ทีหลังไม่ได้ เพราะ uid ฝังอยู่ใน `teams[].motherUids` ที่เซฟไปแล้ว **ต้องตัดสินก่อนเขียนโค้ดเซฟบรรทัดแรก**

ผลข้างเคียงที่ต้องรู้: `uid` เป็น **string** ไม่ใช่ number แล้ว โค้ดที่เทียบ uid ต้องเทียบแบบ string ส่วน `nextUid` ยังเป็น number (เป็นแค่ตัวนับของผู้เล่นคนนั้น)

`Config.validate()` เช็คว่าตัวคั่นของ uid (`-`) ไม่ชนกับตัวคั่นของ stack key (`|` และ `,`)

### 3.3 `heldEggs` — โครงใหม่ที่ต้องเปลี่ยนก่อนขึ้นเพดานเป็น 10,000

> ✅ **ทำแล้วใน Phase 2A** — `BAG_CAPACITY` ขึ้นเป็น 10,000 พร้อมกับโครงใหม่นี้
> (ภายหลังลดค่าเพดานลงมาที่ 1,000 — ดู `src/shared/Config.lua` ตรง `BAG_CAPACITY` —
> แต่โครง `{ nextEggId, items }` ที่ทำไว้ตอน Phase 2A ยังใช้อยู่เหมือนเดิม ไม่เกี่ยวกัน)
> โค้ดอยู่ที่ `src/shared/PlayerData.lua` (`addHeldEgg` / `findHeldEgg` / `removeHeldEgg`)
> **ห้ามแตะ `items` ตรง ๆ ที่อื่น** เพราะ `nextEggId` ต้องเดินหน้าอย่างเดียว

#### ปัญหา

ตกลงกันแล้วว่ากระเป๋าไข่จะขึ้นเป็น **10,000 ฟอง** (สวนฟักยังคง 50)
แต่ตอนนี้ `heldEggs` เป็น **อาเรย์ยาวคงที่ที่ใส่ `false` ในช่องว่าง**

```lua
heldEggs = { {eggId="egg_stage1", weight=320}, false, false, ... }  -- ยาว BAG_CAPACITY เสมอ
```

ขึ้นเป็น 10,000 เมื่อไหร่ = **ต้องเขียน `false` หมื่นตัวลง DataStore ทุกครั้งที่เซฟ**
ต่อให้ผู้เล่นถือไข่จริงแค่ 3 ฟอง

| เพดาน | ขนาดตอนถือไข่ 3 ฟอง | เทียบลิมิต 4 MB |
|---:|---:|---:|
| 50 (ตอนนี้) | ~450 B | 0.01% |
| 10,000 (โครงเดิม) | **~62 KB** | 1.5% — เสียฟรีทั้งหมด |
| 10,000 (โครงใหม่) | ~200 B | 0.005% |

#### ข้อเสนอ: เก็บเฉพาะช่องที่มีของ + id ประจำฟอง

```lua
heldEggs = {
    nextEggId = 128,                              -- ตัวนับ ห้ามลด ห้าม reuse
    items = {                                     -- array แน่น ไม่มีรู ไม่มี false
        { id = 125, eggId = "egg_stage1", weight = 320 },
        { id = 127, eggId = "egg_stage3", weight = 48000 },
    },
}
```

**ทำไมต้องมี `id` ประจำฟอง ไม่ใช้ index เฉย ๆ:**
ตอนนี้ client ส่ง **index ใน `heldEggs`** มาให้ server (`PlaceEggInHatcheryRequest`)
พอ array เป็นแบบแน่น การลบฟองหนึ่งจะทำให้ฟองที่อยู่หลังมัน **เลื่อน index ทั้งแถว**

```
ก่อนลบ:  [1]=A  [2]=B  [3]=C        client เห็น C ที่ index 3
ลบ B:    [1]=A  [2]=C               client กด "วาง index 3" → ไม่มีแล้ว
                                     หรือแย่กว่า: กด index 2 ตั้งใจจะได้ B แต่ได้ C
```

เป็นบั๊กแบบ race condition ที่เกิดจริงเมื่อไข่ฟักเสร็จพอดีตอนผู้เล่นกำลังกด
**ไม่ใช่เรื่องทฤษฎี** — สวนฟัก 50 ช่องทำให้มีไข่ฟักเสร็จบ่อยมาก

#### ผลกระทบต่อ client

| เดิม | ตอนนี้ (Phase 2A) |
|---|---|
| `PlaceEggInHatcheryRequest:FireServer(heldIndex)` | `FireServer(eggId)` — **id ประจำฟอง ไม่ใช่ตำแหน่ง** |
| server validate: เป็น number · จำนวนเต็ม · อยู่ใน 1..BAG_CAPACITY · ช่องนั้นไม่ใช่ `false` | server validate: เป็น number · จำนวนเต็มบวก · **หาเจอใน `items` ของคนนี้** |
| payload ส่ง `heldEggs` เป็นอาเรย์ยาวคงที่ | payload ส่งเฉพาะฟองที่มีจริง + `id` ของแต่ละฟอง |

⚠️ **ไม่ต้องเขียน migration** เพราะตอนเปลี่ยนยังไม่เคยมีใครมีข้อมูลใน DataStore เลย
(Phase 2A คือโค้ด DataStore ชุดแรกของโปรเจกต์) `schemaVersion` จึงเริ่มที่ **1** ตามเดิม
โครง `MIGRATIONS` ใน `PlayerData.lua` ว่างอยู่ แต่กลไกวนเวอร์ชันพร้อมใช้แล้ว

⚠️ **server ไม่ส่งไข่ทั้งหมดทุก sync** — ส่งแค่ `HELD_EGGS_PER_SYNC` (50) ฟองแรก + จำนวนรวม
sync วิ่งทุกวินาที ส่งหมื่นฟองทุกวินาทีคือถล่มแบนด์วิดท์ของตัวเอง

#### ⚠️ UI ต้อง virtualize

ลิสต์ไข่ 10,000 ฟองจะสร้าง GUI element หมื่นตัวถ้าทำตรง ๆ ซึ่งค้างแน่นอน

ต้องทำแบบ **virtualize**: สร้าง element เท่าที่มองเห็นบนจอ (ราว 20–30 ตัว)
แล้วเลื่อนเนื้อหาเข้าออกตาม `CanvasPosition` ของ `ScrollingFrame`
พร้อม **จัดกลุ่มตามชนิดไข่ + ช่วงน้ำหนัก** เป็นค่าเริ่มต้น
เพราะไม่มีใครไล่อ่านไข่หมื่นฟองทีละฟองอยู่แล้ว

## 4. Stack key — หัวใจของระบบกองลูก

### 4.1 รูปแบบ

```
"<charId>|<น้ำหนักแม่>|<สถานะเรียงแล้ว คั่นด้วยจุลภาค>"
```

| กรณี | key |
|---|---|
| ซุนหงอคง 1,500 kg ไม่มีสถานะ | `"wukong\|1500\|"` |
| ซุนหงอคง 1,500 kg มี gold | `"wukong\|1500\|gold"` |
| องค์ยูไล 100,000,000 kg มี gold+silver | `"yulai\|100000000\|gold,silver"` |

สร้าง/แยกด้วย `Config.makeStackKey()` / `Config.parseStackKey()` **เท่านั้น** ห้ามต่อ string เอง

### 4.2 กฎ 3 ข้อที่ห้ามพลาด

**1. ใช้น้ำหนัก "แม่" ไม่ใช่น้ำหนัก "ลูก"**

ลูกหนัก 1% ของแม่ ซึ่งเป็นทศนิยมได้ (แม่ 999 kg → ลูก 9.99 kg) ถ้าเอา 9.99 ไปทำ key จะเจอปัญหา float: โค้ดคนละที่อาจได้ `9.99` กับ `9.990000000000001` → กลายเป็นคนละกองโดยไม่มีใครรู้ตัว

น้ำหนักแม่เป็นจำนวนเต็มเสมอ (`Config.rollMotherWeight` คืน `NextInteger`) จึงเป็น identity ที่ปลอดภัย น้ำหนักลูกคำนวณกลับได้ตลอดด้วย `Config.getChildWeight()`

**2. เรียงสถานะก่อนเสมอ**

`{gold, silver}` กับ `{silver, gold}` คือชุดเดียวกัน ต้องได้ key เดียวกัน `makeStackKey` เรียกใช้ `table.sort` ทุกครั้ง — เรียงตามลำดับ byte ของ ASCII ซึ่งคงที่ ไม่ขึ้นกับ locale นี่คือเหตุผลที่ `Config.validate()` บังคับว่า `statusId` และ `charId` ต้องเป็น `^[a-z][a-z0-9_]*$`

**3. ตัดสถานะซ้ำก่อนเรียง**

`{gold, gold}` ต้องได้ key เดียวกับ `{gold}` ไม่งั้นบั๊กที่เผลอใส่สถานะซ้ำจะสร้างกองผี

> ทั้ง 3 ข้อมีชุดเทสต์ครอบอยู่แล้ว รวมถึงเคส `{silver,gold}` ต้องได้ key เดียวกับ `{gold,silver}`

### 4.3 ทำไมกองลูกไม่เก็บ `charId` / `statuses` แยกอีกชุด

เพราะ **key คือ identity ทั้งหมดของกองอยู่แล้ว** ถ้าเก็บซ้ำเป็น

```lua
children = { ["wukong|1500|gold"] = { charId="wukong", weight=15, statuses={"gold"}, count=482000 } }  -- ❌
```

จะได้ปัญหา 3 อย่างฟรี ๆ:

1. **ข้อมูลขัดกันเองได้** — วันหนึ่งจะมีบั๊กที่ key บอก `wukong` แต่ฟิลด์ข้างในบอก `tang` แล้วไม่มีใครรู้ว่าอันไหนถูก
2. **เปลืองที่ ~5 เท่า** — `["wukong|1500|gold"]=482000` ใช้ ~30 bytes ส่วนแบบ table ใช้ ~130 bytes (ที่ 2,000 กองคือ 60 KB vs 260 KB)
3. **ต้องเขียน validate เพิ่ม** เพื่อกันข้อ 1 ซึ่งเป็นงานที่ไม่ต้องมีตั้งแต่แรก

ค่าของ dictionary จึงเป็น **number ล้วน ๆ** คือจำนวนตัวในกอง

## 5. การผลิตลูก

### 5.1 อัตรา

**อัตราผลิตแปรตามน้ำหนักแม่** (ของใหม่ — เดิมแม่ทุกตัวผลิตเท่ากัน)

```
ผลิต/นาที = 1 × (น้ำหนักแม่ ÷ 100)^0.25 × ตัวคูณ upgrade × ตัวคูณสถานะ
```

| น้ำหนักแม่ | ผลิต/นาที | เติมคลัง 500 เต็มใน |
|---:|---:|---:|
| 100 kg | 1.0 | 8.3 ชม. |
| 10,000 kg | 3.2 | 2.6 ชม. |
| 1,000,000 kg | 10.0 | 50 นาที |
| 100,000,000 kg | 31.6 | 16 นาที |

#### ⚠️ ทำไมเลขชี้กำลังเป็น 0.25 ไม่ใช่ 0.5

น้ำหนักมีผลอยู่แล้ว **2 ทาง**: เงิน (√) และ damage ต่อตัว (√)
ถ้าอัตราผลิตใช้ √ ด้วย **damage รวมต่อวันจะแปรผันตรงกับน้ำหนัก** (√ × √ = 1) → ช่องว่างระหว่างแม่ 100 kg กับ 100M kg จะกลายเป็น **1,000,000 เท่า**

ใช้ 0.25 ได้ราว **31,623 เท่า** — กว้างพอให้ตัวหนักคุ้มค่า แต่ไม่ถึงกับขาดกัน
เลขชี้กำลังอยู่ใน `Config.Balance.Production.WEIGHT_EXPONENT` ปรับได้ `validate()` บังคับว่าต้องอยู่ระหว่าง 0 กับ 1

| | อัตรา | ที่มา |
|---|---|---|
| ออนไลน์ | ตามสูตรข้างบน (แม่**ในคอก**เท่านั้น) | `Config.getProductionPerMinute()` |
| ออฟไลน์ | 10% ของอัตราออนไลน์ | `Config.Balance.Production.OFFLINE_RATE_RATIO` |
| เพดานออฟไลน์ | 8 ชั่วโมง | `Config.Balance.Production.OFFLINE_CAP_SECONDS` |
| ตัวคูณจาก upgrade | `3 ^ productionLevel` สูงสุด ×59,049 | `Config.getProductionMultiplier()` |
| **เพดานคลัง** | **500 ตัว/กอง · เต็มแล้วแม่หยุดผลิต** | `Config.Balance.Production.STACK_CAP` |

**ออฟไลน์เต็มเพดานได้ 48 ตัวต่อแม่ 1 ตัว** (แม่ 100 kg ก่อนคูณ upgrade · แม่หนักกว่าได้มากกว่าตามสูตร)
ผู้เล่นที่มีแม่ในคอก 10 ตัวออกไป 3 วัน กลับมาได้ 480 ตัว ไม่ใช่ 4,320 ตัว

**แม่ในกระเป๋าไม่ผลิตอะไรเลย** — ไม่ต้องมี `lastProducedAt` และไม่ต้องวนถึงตอน settle

### 5.2 วิธี settle

ใช้สูตรเดียวกันทั้งออนไลน์และออฟไลน์ ต่างกันแค่ค่า rate

```
ต่อแม่ในคอก 1 ตัว:
    ratePerSecond = Config.getProductionPerMinute(
                        mother.weight, mother.statuses, productionLevel, ออนไลน์
                    ) / 60
    -- ⚠️ ใช้ helper ตัวนี้เท่านั้น ห้ามคูณเอง — ในนั้นรวม
    --    น้ำหนักแม่ ^WEIGHT_EXPONENT · upgrade · บัฟสถานะ · ตัวคูณออฟไลน์ ครบแล้ว

    windowStart = max(mother.lastProducedAt, now - OFFLINE_CAP_SECONDS)   ← เพดานอยู่ตรงนี้
    elapsed     = max(0, now - windowStart)
    produced    = floor(elapsed × ratePerSecond)
    produced    = min(produced, MAX_PER_SETTLE)                            ← กันนาฬิกากระโดด

    ถ้า produced > 0:
        key = Config.makeStackKey(mother.charId, mother.weight, mother.statuses)
        produced = min(produced, STACK_CAP - (children[key] or 0))   ← เพดานคลัง
        children[key] = (children[key] or 0) + produced
        ถ้าชนเพดาน → แจ้งเตือนผู้เล่นว่าแม่ตัวนี้หยุดผลิตแล้ว
        mother.lastProducedAt = windowStart + produced / ratePerSecond      ← ไม่ใช่ now
```

**บรรทัดสุดท้ายคือจุดที่พลาดกันบ่อยที่สุด** ถ้าเซ็ต `lastProducedAt = now` เศษเวลาที่ยังไม่ครบ 1 ตัวจะถูกทิ้งทุกรอบ ตอนออนไลน์ที่ tick ทุก 5 วินาที (ผลิตได้รอบละ 0.083 ตัวถ้ายังไม่อัป) ผู้เล่นจะไม่ได้ลูกเลยสักตัว การเลื่อนไปเท่าที่ "ใช้จริง" ทำให้เศษสะสมข้ามรอบได้โดยไม่ต้องมีฟิลด์ accumulator แยก

### 5.3 ลำดับตอนผู้เล่นล็อกอินกลับ (ห้ามสลับ)

```
1. โหลด PlayerData + migrate + validate
2. เคลียร์ไข่ที่ฟักครบระหว่างออฟไลน์   ← สร้างแม่ใหม่ ตั้ง lastProducedAt = hatchAt
                                        ถ้าคอกเต็ม ให้ลงกระเป๋า ถ้ากระเป๋าเต็มด้วยให้ค้างไว้ในสวน
3. settle การผลิตออฟไลน์ของแม่ในคอกทุกตัว  ← แม่ที่เพิ่งเกิดในข้อ 2 ก็ผลิตด้วย
4. ตั้ง lastSeenAt = now แล้วเริ่ม tick ออนไลน์
```

**ถ้าสลับข้อ 2 กับ 3** แม่ที่ฟักออกมาตอนชั่วโมงที่ 1 ของการออฟไลน์ 8 ชั่วโมง จะไม่ผลิตอะไรเลยทั้งที่ควรได้ 42 ตัว
สูตร `windowStart = max(lastProducedAt, now - cap)` จัดการเคสนี้ให้เองอยู่แล้ว เพราะแม่ที่เพิ่งเกิดมี `lastProducedAt = hatchAt` ซึ่งใหม่กว่า `now - cap`

### 5.4 ตอน logout / autosave

```
1. settle การผลิตออนไลน์จนถึง now
2. lastSeenAt = now
3. เซฟ
```

ทำข้อ 1 ก่อนเสมอ ไม่งั้นเวลาที่เล่นอยู่ช่วงท้ายจะถูกนับเป็นออฟไลน์ (ช้ากว่า 10 เท่า) = ผู้เล่นเสียเปรียบ

### 5.5 อัปเกรดคอก + ขายแม่ + ข้อ D (Phase 2B-2)

**อัปเกรดคอก** — `UpgradePenRequest` ไม่มีพารามิเตอร์ อัป `penLevel` ขึ้น 1 ขั้นเสมอ ใช้ตาราง `Config.Balance.Pen` ตรง ๆ (`Config.getPenUpgradeCost` / `Config.getPenCapacity`) หักเงิน + เพิ่มเลเวลในบรรทัดติดกันไม่มี yield คั่นกลาง จึง atomic โดยธรรมชาติ (Luau เป็น single-thread) ความจุใหม่มีผลทันทีเพราะทุกจุด (`hatch`, `moveMother`, `buildSyncPayload`) อ่าน `Config.getPenCapacity(data.penLevel)` สด ๆ ทุกครั้ง ไม่มีการ cache ความจุไว้ที่ไหน

**ขายแม่** — `SellMotherRequest(motherUid)` **ขายได้เฉพาะแม่ในกระเป๋าเท่านั้น** (เหมือนกฎ "ส่งรบได้แค่จากกระเป๋า") กันขายพลาดตัวที่กำลังผลิตอยู่ในคอกโดยไม่ตั้งใจ — อยากขายแม่ในคอกต้อง `moveMother` ออกมาก่อน ราคาใช้ `Config.getMotherSellPrice(weight, wallProgress, statuses)` ที่มีอยู่แล้ว (= รายได้ 30 นาทีของแม่ตัวนั้น ดู [ตาราง 5](#82-สูตรเงิน-รากที่สอง--ตัวคูณตามด่าน)) **ไม่ใช่ 60 นาที** — คำนวณฝั่ง server ล้วน ๆ จาก uid เท่านั้น ไม่มีพารามิเตอร์ราคาให้ client ส่งมาเอง

**ข้อ D (คอก+กระเป๋าเต็มพร้อมกันตอนไข่ครบเวลาฟักพอดี)** — แก้โดย**ไม่แตะ schema เลย**:

```
hatch() เช็คที่ว่างก่อนเคลียร์ slot เสมอ
  ├─ มีที่ว่าง (คอกหรือกระเป๋า) → เคลียร์ slot ทันที วางแม่ตามปกติ
  └─ เต็มทั้งคู่ → return เฉย ๆ ไม่แตะ slot เลย (ไม่เคลียร์ ไม่ hideEgg)
                   slot ยังเป็น "occupied" เหมือนไข่ที่กำลังฟัก ต่างแค่ remaining = 0
```

เพราะ `processReadyHatchSlots` เช็ค `now >= slot.hatchAt` ทุกครั้งที่เรียก (ทุก tick + ทุกครั้งที่มี event เปิดที่ว่าง) — slot ที่ค้างจะ "ครบเวลาแล้ว" ตลอดไปจนกว่าจะวางสำเร็จจริง จึงถูกลองใหม่โดยอัตโนมัติทุกครั้งโดยไม่ต้องมีฟิลด์ status พิเศษเพิ่ม

ลำดับคิวตอนมีหลายฟองค้างพร้อมกัน: `processReadyHatchSlots` เรียง slot ตาม **`hatchAt` น้อยสุดก่อน** (ไม่ใช่ตาม `slotIndex`) ก่อนวนลองวางทีละฟอง — ฟองที่ฟักเสร็จก่อนจริงได้คิวก่อนเสมอ ไม่ว่าจะอยู่ช่องไหนในสวนฟัก

ทริกเกอร์ให้ลองวางแม่ที่ค้างทันที (ไม่ต้องรอ tick ถัดไป): ขายแม่สำเร็จ, อัปเกรดคอกสำเร็จ, ย้ายแม่สำเร็จ (ทั้งสองทิศทาง) — ทุกจุดที่อาจเปิดที่ว่างในคอกหรือกระเป๋า เรียก `processReadyHatchSlots` ซ้ำก่อน sync รอบสุดท้ายเสมอ

⚠️ แม่ที่เพิ่งวางสำเร็จหลังค้างไว้นาน ยังใช้ `slot.hatchAt` เดิม (เวลาที่ควรฟักเสร็จจริง ไม่ใช่เวลาที่วางได้จริง) เป็น `obtainedAt`/`lastProducedAt` เหมือนพฤติกรรมเดิมของ §5.2 — เพดานออฟไลน์ 8 ชม. ของ `ProductionService` ครอบไว้อยู่แล้ว จึงไม่มีทางได้เครดิตผลิตเกินจริงแม้จะค้างอยู่นานกว่านั้น

**สัญญาณแจ้งเตือน**: sync payload มี `stuckHatchCount` (จำนวนฟองที่ค้าง) และ `hatching[i].stuck` (ต่อช่อง) ให้ client แสดง UI ได้ (ยังไม่ทำ UI เฟสนี้ ตามที่สั่ง)

## 6. สถานะ (Status)

### 6.1 กฎพื้นฐาน

- สถานะติดที่ **ตัวแม่เท่านั้น** ลูกไม่มีสถานะเป็นของตัวเอง
- ลูกที่ผลิตออกมา **คัดลอกชุดสถานะของแม่ ณ เวลาที่ผลิต** (snapshot ไม่ใช่ reference)
- แม่ 1 ตัวติดได้หลายสถานะพร้อมกัน
- Phase 1-3 ยังไม่มีสถานะจริง (`Config.Statuses` มี `gold` / `silver` แต่ `enabled = false`)

### 6.2 กฎที่สำคัญที่สุด: แม่ได้สถานะเพิ่มทีหลัง

> **ลูกที่ผลิตไปแล้ว "ไม่" อัปเดตย้อนหลัง**

```
วันที่ 1   ซุนหงอคง 1,500 kg ไม่มีสถานะ
          ผลิตลูก 500 ตัว  →  children["wukong|1500|"] = 500

วันที่ 3   ได้สถานะ gold
          ผลิตต่อ 300 ตัว →  children["wukong|1500|"]     = 500   ← กองเดิม ไม่เปลี่ยน
                             children["wukong|1500|gold"] = 300   ← กองใหม่

วันที่ 5   ได้ silver เพิ่ม
          ผลิตต่อ 200 ตัว →  children["wukong|1500|gold,silver"] = 200   ← กองที่สาม
```

**แม่ตัวเดียวมีลูกกระจายหลายกองได้ตามประวัติสถานะของมัน** — เป็นพฤติกรรมที่ตั้งใจ ลูกที่ผลิตตอนแม่ยังไม่มีบัฟก็ไม่ควรได้บัฟย้อนหลัง

ผลข้างเคียงที่ต้องระวัง: จำนวนกองโตตาม **(จำนวนแม่ × จำนวนชุดสถานะที่แม่แต่ละตัวเคยผ่าน)** จึงต้องมี `Config.Inventory.MAX_CHILD_STACKS = 2000`

### 6.3 บัฟที่สถานะให้ (โครงพร้อมแล้ว ค่ายังไม่เปิด)

สถานะ 1 ตัวให้บัฟได้ 4 อย่าง แม่ติดหลายสถานะ = **ตัวคูณคูณสะสมกัน** ส่วนโบนัสน้ำหนักลูก**บวกกัน**

| ฟิลด์ใน `StatusType` | ผล | ค่ากลาง |
|---|---|---|
| `damageMultiplier` | คูณ damage และ HP | 1 |
| `coinMultiplier` | คูณรายได้เงิน | 1 |
| `productionMultiplier` | คูณความเร็วผลิตลูก | 1 |
| `childRatioBonus` | บวกเข้ากับ `CHILD_RATIO` (0.01) | 0 |

ค่าตัวอย่างที่ตั้งไว้ใน Config ตอนนี้ (**`enabled = false` ทั้งคู่ จึงยังไม่มีผลอะไรเลย**):

| สถานะ | damage | เงิน | ผลิต | น้ำหนักลูก |
|---|---:|---:|---:|---|
| gold | ×2 | ×2 | ×1.5 | +1% → **ลูกหนัก 2% ของแม่** |
| silver | ×1.5 | ×1.5 | ×1.2 | +0% |

อ่านผลรวมด้วย `Config.getStatusEffects(statuses)` ซึ่งข้ามสถานะที่ `enabled = false` ให้อัตโนมัติ
`Config.computePower()` · `getCoinsPerMinute()` · `getChildWeight()` รับ `statuses` เป็นพารามิเตอร์เสริมแล้ว

**สองข้อที่ต้องรู้:**

1. **โบนัสน้ำหนักลูกไม่กระทบ stack key** — key เก็บน้ำหนัก *แม่* ไม่ใช่ลูก และลูกในกองเดียวกันมีชุดสถานะเดียวกันอยู่แล้ว จึงมีสัดส่วนน้ำหนักเท่ากันเสมอ น้ำหนักลูกจริงคำนวณกลับได้ตลอดด้วย `Config.getChildWeight(motherWeight, statuses)`
2. **มีเพดาน `MAX_CHILD_RATIO = 1`** — ลูกหนักเกินแม่ไม่ได้ `Config.validate()` เช็คว่าถ้าเปิดทุกสถานะพร้อมกันแล้วยังไม่เกินเพดาน ปัจจุบันเปิดหมด = 2% ยังห่างเพดานเยอะ

> บัฟที่คูณ damage ตรง ๆ คุ้มกว่าการเพิ่มน้ำหนักลูกมาก เพราะ damage ใช้ sqrt: เพิ่มน้ำหนักลูก ×2 ได้ damage แค่ ×1.41 แต่ `damageMultiplier = 2` ได้ ×2 เต็ม ตอนปรับสมดุล Phase 6 ควรใช้ `damageMultiplier` เป็นตัวหลัก แล้วให้ `childRatioBonus` เป็นของแถมเชิงความรู้สึก

### 6.4 การประนีประนอมเรื่องผลผลิตออฟไลน์

ตอนคำนวณผลผลิตออฟไลน์ ให้ใช้ชุดสถานะ **ปัจจุบัน** ของแม่ แล้วยกให้เป็นกองเดียว

ข้อสังเกตที่ควรรู้: **ตามดีไซน์ตอนนี้การประนีประนอมนี้ยังไม่มีผลจริง** เพราะสถานะเปลี่ยนได้เฉพาะตอนผู้เล่นออนไลน์ พอออฟไลน์ชุดสถานะจึงคงที่ตลอดช่วงนั้น = "สถานะปัจจุบัน" กับ "สถานะตอน logout" เป็นค่าเดียวกัน

กฎข้อนี้จะเริ่มมีผลจริงในวันที่สถานะเปลี่ยนเองได้ระหว่างออฟไลน์ (บัฟมีอายุ / daily reward ที่ติดสถานะอัตโนมัติ) วันนั้นการคำนวณที่ถูกต้องต้องแบ่งช่วงเวลาออฟไลน์เป็นท่อน ๆ ตามประวัติสถานะ ซึ่งซับซ้อนกว่ามาก **เรายอมรับความคลาดเคลื่อนตรงนี้** แลกกับความง่าย และให้เอียงไปทางที่ผู้เล่นได้เปรียบเสมอเมื่อต้องเลือก

## 7. การรบ — ปล่อยทหารต่อเนื่องแบบ Age of War

> **ระบบเดิม "กดส่งกองทัพทีเดียวแล้วรอผล" ถูกยกเลิกทั้งหมด**

### 7.1 จุดสปอนและการปล่อย

```
[จุดสปอน]──ปล่อย 1 ตัว/วิ──►  ทหารเดินเรียงแถว  ──►[ทหารฝ่ายรับ]──►[กำแพง]
     ▲                                                    เดินถึงใน ~30 วิ
     │
 คลังทหาร (cap 500/กอง) ◄── แม่ในคอกผลิตเข้ามาเรื่อย ๆ
```

- ปล่อยทีละตัวเรียงแถวเดินไปทางกำแพง อัตราตาม `Config.Balance.Combat.RELEASE_PER_SECOND`
- **ปล่อยเฉพาะตอนออนไลน์** ออฟไลน์ไม่ปล่อย แต่แม่ยังผลิตอยู่ตามกติกาออฟไลน์เดิม (ช้ากว่า 10 เท่า cap 8 ชั่วโมง)
- ทหารในคลังหมด → หยุดรอจนแม่ผลิตได้ แล้วปล่อยต่ออัตโนมัติ

### 7.2 ปุ่มอัญเชิญ (เปิด/ปิด) — กลไกหลักของเกม

| กด | ผล |
|---|---|
| ปิด | หยุดปล่อย ทหารที่ผลิตได้สะสมไว้ในคลัง |
| เปิด | ปล่อยต่อเนื่องอัตโนมัติ |

**สะสมกองใหญ่แล้วปล่อยรวดเดียวทะลุ ดีกว่าปล่อยทีละตัวแล้วถูกกินทีละตัว** — นี่คือการตัดสินใจหลักที่ผู้เล่นต้องทำ เก็บสถานะไว้ใน `summonEnabled`

### 7.3 คลังทหาร — cap 500 ต่อกอง

`Config.Balance.Production.STACK_CAP = 500`

**ทำไม 500:** แม่น้ำหนักฐานผลิต ~1 ตัว/นาที → 500 ตัว ≈ **8 ชั่วโมง** ซึ่งตรงกับ cap ออฟไลน์ 8 ชั่วโมงที่ใช้อยู่แล้ว ระบบจึงสม่ำเสมอกันทั้งเกม
และ 500 ตัวปล่อยที่ 1 ตัว/วินาที = ระบายหมดใน ~8 นาที ซึ่งเป็นช่วงเวลาที่นั่งดูได้จริง

**คลังเต็ม → แม่ตัวนั้นหยุดผลิต + แจ้งเตือนผู้เล่น** (`STACK_CAP_START = 200` เผื่อทำเป็น upgrade ทีหลัง)

### 7.4 ตัวแม่ในสนามรบ — กติกาที่ห้ามพลิก

| กฎ | เหตุผล |
|---|---|
| **ห้ามระบบ auto ปล่อยตัวแม่เด็ดขาด** auto ปล่อยได้เฉพาะตัวลูก | แม่ตายถาวร = เสียเครื่องผลิตไปเลย ระบบตัดสินใจแทนไม่ได้ |
| ผู้เล่นต้องกดเลือกและส่งเองทีละครั้ง **+ กล่องยืนยัน** | เหมือนกัน |
| **เลือกได้เฉพาะแม่ที่อยู่ในกระเป๋า** แม่ในคอกเลือกไม่ได้ | กันไม่ให้เผลอส่งเครื่องผลิตที่กำลังทำเงินอยู่ไปตาย |

`Config.validate()` บังคับสองกฎแรกตรง ๆ: `ALLOW_AUTO_RELEASE_MOTHERS` และ `MOTHERS_SELECTABLE_FROM_PEN` ต้องเป็น `false` ไม่งั้นเซิร์ฟไม่บูต

### 7.5 ปุ่ม "เลือกสัตว์เลี้ยงที่ดีที่สุด"

**เป็นปุ่มกดเอง ไม่ใช่ระบบอัตโนมัติที่ทำงานเอง** — ถ้าไม่กดก็ไม่จัดอะไร

กดแล้วจัดแม่เข้าคอกอัตโนมัติ เรียงตามความสามารถผลิตเงิน (`Config.getCoinsPerMinute`)
และต้องย้ายแม่จากคอกกลับกระเป๋าเองได้ตลอด

### 7.6 auto-pause เมื่อตีไม่เข้า

ปล่อยทหารไปครบ `AUTO_PAUSE_AFTER_UNITS` (100) ตัวแล้ว **HP ฝ่ายตรงข้ามไม่ลดเลย** → หยุดปล่อยอัตโนมัติ + แจ้งเตือน

กันไม่ให้ทหารถูกป้อนเข้าเครื่องบดหายถาวรโดยไม่ได้ damage ซึ่งเป็นความเสียหายที่กู้ไม่ได้

### 7.7 ความคืบหน้าสะสมถาวร

- ทหารฝ่ายรับมีจำนวนจำกัดตามตารางด่าน **ตายแล้วไม่เกิดใหม่ หมดแล้วหมดเลย**
- ทหารฝ่ายรับหมด → เดินเข้าตีกำแพงได้ทันที
- **ทั้ง `defendersRemaining` และ `wallHpRemaining` เซฟลง DataStore ต่อผู้เล่น**

**ทำไมต้องสะสมถาวร:** ด่านท้าย ๆ ใช้เวลาตี 5–10 ชั่วโมง ซึ่งนานกว่า session เดียวแน่นอน ถ้ารีเซ็ตเมื่อออกเกมหรือเซิร์ฟรีสตาร์ท ผู้เล่นจะ**ไม่มีวันผ่านด่านเหล่านั้นเลย** ไม่ว่าจะเล่นนานแค่ไหน

UI ต้องแสดง % ความคืบหน้าให้เห็นชัด (ทหารเหลือกี่ % / กำแพงเหลือกี่ %)

### 7.8 ด่าน 1 ไม่มีกำแพง

**ด่าน 1 ไม่มีกำแพงและไม่มีทหารฝ่ายรับ** ผู้เล่นเดินไปสู้บอสตัวเล็กเอาไข่ได้เลยตั้งแต่เข้าเกมครั้งแรก

แก้ปัญหาไก่กับไข่: ต้องมีแม่ถึงจะมีกองทัพ ต้องมีไข่ถึงจะมีแม่
`validate()` บังคับว่า `Stages[1].defenders == 0` และ `getStageTotalHp(1) == 0`

### 7.9 จำนวนโมเดลบนจอ

- **แสดงเฉพาะทหารของผู้เล่นคนนั้นเอง** ไม่แสดงของคนอื่น (6 คนในเซิร์ฟเวอร์เดียวกัน)
- `Config.getVisibleUnitCount(stage)` = `อัตราปล่อย × 30 วินาทีที่ใช้เดิน` ตัดที่ `MAX_VISIBLE_UNITS` (120)
- ส่วนเกินไม่ spawn โมเดล รวมเป็นตัวเลขแทน — วิธีเดียวกับทหารฝ่ายรับ

| ด่าน | ปล่อย/วิ | มีชีวิตพร้อมกัน | แสดงจริง |
|---:|---:|---:|---:|
| 1 | 1 | 30 | 30 |
| 5 | 3 | 90 | 90 |
| 9 | 10 | 300 | **120** (ตัด) |

### 7.10 ทหารฝ่ายรับ = ตัวเลข HP รวม ไม่ใช่ Model

⚠️ **ห้าม spawn ทหารฝ่ายรับเป็น Model จริงทั้งหมด** ด่าน 9 มี 1,000,000,000 ตัว

```
เก็บ:   defendersRemaining = number ค่าเดียว
แสดง:  โมเดล 20–50 ตัว ที่ค่อย ๆ หายไปตามสัดส่วน HP
```

`Config.getDisplayModelCount(hpRatio)`: HP เต็ม → 50 ตัว · ครึ่ง → 25 · 10% → 20 (พื้นขั้นต่ำ) · หมด → 0

**ทำไมมีพื้นขั้นต่ำ 20:** ถ้าลดเป็นเส้นตรงจนถึง 0 พอ HP เหลือ 2% จะเห็นทหารตัวเดียวยืนอยู่ทั้งที่ยังต้องตีอีกนาน ดูเหมือนเกมค้าง

### 7.11 ตายถาวร

- ตัวที่ตายในการรบ **หายถาวร ทั้งแม่และลูก**
- **แม่ตายแล้วกองลูกของมันอยู่ต่อ** (ลูกที่ผลิตไปแล้วเป็นของผู้เล่น ไม่ผูกกับแม่)
- ลูกที่ตายหักออกจาก `children[key]` และลบ key ทิ้งเมื่อเหลือ 0

#### 7.11.1 แม่ในสนามรบ — `battleRoster` (Phase 3C-1)

| กติกา | รายละเอียด |
|---|---|
| **ส่งจากกระเป๋าเท่านั้น** | `SendMotherToBattleRequest(uid)` ย้ายแม่ออกจาก `mothersInBag` เข้า `battleRoster` · **จำนวนในกระเป๋าลดทันทีตอนส่ง** (ข้อ D วางแม่ที่ฟักค้างลงช่องที่ว่างได้เลย) |
| **เพดาน 10 ตัว** | `Config.Balance.Combat.MAX_BATTLE_MOTHERS` · แทนดีไซน์เก่า `Inventory.MAX_TEAM_MOTHERS = 3` (ค่าเก่ายังอยู่ใน Config แต่ไม่มีโค้ดใช้) |
| **`locked = true` ส่งไม่ได้** | ปฏิเสธที่ server |
| **ปฏิเสธถ้าไม่มีด่านให้ตี** | พังครบทุกด่านแล้ว หรือด่านที่กำลังตีมี HP รวม 0 (ด่าน 1) — ไม่งั้นแม่จะตายทันทีโดยไม่ได้ตีอะไรเลย |
| **ตีวินาทีละครั้ง** | damage/วินาทีของแม่แต่ละตัว = `Config.computeBattlePower(weight, charId, statuses, damageLevel)` (แรงกว่าลูกของตัวเอง 10 เท่า) รวมกับ damage ของลูกแล้วไหลเข้า `applyDamageToStage` ทางเดียวกัน |
| **ตีเฉพาะตอนเปิดอัญเชิญ** | `summonEnabled = false` (รวมถึงตอน auto-pause) = แม่ยืนเฉย ไม่ตี แต่ยังอยู่ใน roster |
| **ด่านพัง = ตายทั้งหมดพร้อมกัน** | `killRoster` ล้างอาเรย์ทั้งชุด + `stats.mothersLost += จำนวน` · ไม่มีการตายรายตัวระหว่างตี (โมเดล HP รวม — HP รายตัวอยู่ใน `docs/combat-hp-vision.md`) |
| **ดึงกลับไม่ได้** | ไม่มี remote ย้ายออกจาก roster |

แม่ที่ตายหายจากทุกอาเรย์และ**ไม่ reuse uid** (`nextUid` ไม่ลด)

### 7.12 รางวัลผ่านด่าน — ไข่ฟรีครั้งเดียวต่อด่าน (Phase 4A)

กำแพงด่านไหนพังเป็น**ครั้งแรก** → ได้ไข่ฟรีของรังบอสด่านนั้น (`Config.getBossEggId(ด่าน)`) เข้า `heldEggs`
ยังไม่ฟัก ต้องเอาไปวางฟักเองตามปกติ · สร้างผ่าน `EggService.grantEgg` ตัวเดียวกับไข่ทุกแหล่ง
(สุ่มน้ำหนักตอนสร้าง · สุ่มคลาสตอนวางลงสวนฟัก ตามตารางของด่านนั้น)

| ด่านที่พัง | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 | รวม |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| ไข่ฟรี (`Balance.Combat.STAGE_CLEAR_BONUS_EGGS`) | **0** | 1 | 1 | 2 | 2 | 2 | 3 | 3 | 3 | 17 |

- **ทำไมเป็นไข่ ไม่ใช่เงิน:** เงินเพิ่งถูกดูดส่วนเกินด้วย `DamageUpgrade` (§8.6) · ใส่เงินก้อนเพิ่ม = ย้อนปัญหาเดิม
- **ด่าน 1 = 0:** ไม่มีกำแพงให้พัง — "พัง" ฟรีตั้งแต่ตาแรกที่ปล่อยทหาร · `validate()` บังคับว่าด่าน HP รวม 0 ต้องเป็น 0
- **สัดส่วน:** 17 ฟองทั้งเกม เทียบไข่จากบอส ~10 ฟอง/ชม. ตลอด ~54 ชม. ถึงด่าน 9 ≈ 3% — เป็นรางวัลฉลอง ไม่ใช่ตัวปรับเศรษฐกิจ

**ให้ครั้งเดียวจริง — ผูกกับจังหวะ "เพิ่งพัง" ไม่ใช่สถานะ "พังอยู่"**
```
CombatService.tick → applyDamageToStage คืน stageCleared = true (ด่านนี้เพิ่งพังในตานี้)
  → recomputeWallProgress → killRoster → claimStageClearBonus(data, stage)
       ธงด่านนั้น true อยู่แล้ว → 0 · ด่าน HP รวม 0 → 0
       ไม่งั้น → ติดธง true ก่อน แล้วคืนจำนวนไข่
  → ลูปใน CombatService.start เรียก EggService.grantStageClearBonus(player, stage, จำนวน)
       → grantEgg × จำนวน → FireClient StageClearedNotify(stage, จำนวนที่แจกได้จริง)
```
- ⚠️ **ห้ามให้รางวัลใน `recomputeWallProgress`** — มันไล่นับด่านที่พังอยู่ทั้งหมดใหม่ทุกครั้งที่ถูกเรียก
  ผู้เล่นเก่าที่ธงเป็น false จะได้ไข่ย้อนหลังทุกด่าน (และ `debugSetStageProgress` ก็เรียกมันด้วย)
- ⚠️ **ผู้เล่นเก่าไม่ได้ไข่ย้อนหลัง** สำหรับด่านที่พังไปก่อนอัปเดต v3 — migration ตั้งธง false ทั้งหมด
  แต่ด่านที่พังแล้วไม่มีวันพังซ้ำ (ตีเรียงลำดับ ไม่ย้อนด่าน) จึงไม่เกิดจังหวะ "เพิ่งพัง" อีก **ตั้งใจแบบนี้**
- กระเป๋าไข่เต็มกลางทาง → แจกเท่าที่ใส่ได้ ธงติดไปแล้ว (ได้ครั้งเดียว) · popup บอกจำนวนที่ได้จริง
- **แจ้งผู้เล่น:** remote `StageClearedNotify(stage, eggCount)` server → client ยิงครั้งเดียว **ไม่อยู่ใน sync**
  → resync กี่รอบ popup ก็ไม่โผล่ซ้ำ · client ต่อคิวถ้าแจ้งซ้อนกัน

## 8. สมดุลตัวเลข — ที่มาของทุกค่าใน Config

### 8.1 สูตร damage / HP (เลือกแล้ว: รากที่สอง)

**HP ของตัวเรา = damage ของตัวเรา** ใช้ฟังก์ชันเดียวกัน `Config.computePower(weight, charId, statuses)`

```
damage = HP = 10 × (น้ำหนัก / 100)^0.5 × ตัวคูณคลาส × ตัวคูณสถานะ
```

#### ⚠️ ตัวคูณคลาสชุดใหม่ — คลาสคือแกนที่ไต่ตามด่าน

| คลาส | ตัวคูณเดิม | **ตัวคูณใหม่** | ได้จาก |
|---|---:|---:|---|
| C | ×1 | **×1** | ทุกด่าน (90% ที่ด่าน 1 → 10% ที่ด่าน 9) |
| B | ×1.5 | **×6** | ทุกด่าน |
| A | ×2 | **×36** | ด่าน 3 ขึ้นไป (0.1% → 50%) |
| S | ×3 | **×216** | ด่าน 7 ขึ้นไป (1% → 20%) |
| SS | ×5 | **×432** | ไข่ Robux เท่านั้น |

**ทำไมต้องชันขนาดนี้:** ตารางสุ่มน้ำหนักเหมือนกันทุกด่าน (ตัดสินถาวรแล้ว) ด่านสูงจึงไม่ได้ให้แม่หนักกว่า สิ่งเดียวที่ด่านสูงให้คือ *โอกาสได้คลาสดีกว่า* → คลาสต้องรับภาระเป็นตัวไต่ทั้งหมด ตัวคูณเดิม (C→S = ×3) ทำให้ฟาร์มบอสด่าน 9 แทบไม่ช่วยให้ผ่านด่าน 9 เลย

#### ⚠️⚠️ ทำไม SS เป็น ×432 ไม่ใช่ ×1,296

ไล่ ×6 จาก C ถึง S (1 → 6 → 36 → 216) แต่ **SS หยุดที่ ×2 เหนือ S โดยตั้งใจ**

SS ออกจากไข่ Robux เท่านั้น ถ้าไล่ ×6 ต่อไปจนถึง 1,296 คนจ่ายเงินจะแรงกว่าคนไม่จ่าย **1,296 เท่า** = pay-to-win เต็มรูปแบบ เกมจะตายเพราะคนไม่จ่ายเลิกเล่น

ที่ ×432 ไข่ตำนานยังคุ้มซื้อ (ได้ ×2 บวกกับรับประกัน tier 3+ ซึ่งให้ damage อีก ×10) แต่ไม่ถึงกับ "ซื้อแล้วชนะ" เพราะ **S หาได้ฟรีจากบอสด่าน 7 ขึ้นไป**

`validate()` บังคับว่า `SS ÷ S ≤ BalanceCheck.MAX_SS_OVER_S_RATIO` (2.5) — **เกินเมื่อไหร่เซิร์ฟไม่บูต** และ assert อีกชั้นว่าตัวคูณต้องเรียงลดหลั่นตาม `order` ไม่มีคลาสไหนแซงคลาสที่อยู่เหนือมันได้

  เดิมคลาสให้แค่ ×5 ซึ่งแปลว่าฟาร์มด่านสูงไม่มีความหมาย
- แต่ **น้ำหนักยังชนะอยู่เล็กน้อย** และหายากกว่ามาก (tier 7 = 1 ในล้าน) จึงยังเป็นรางวัลใหญ่ที่ทุกคนลุ้น
  แม่ 100 kg คลาส SS (4,320) แพ้แม่ 100,000 kg คลาส A (11,400) — สองแกนนี้ตัดกันจริง ไม่ใช่แกนใดแกนหนึ่งชนะขาด
- **คลาสเป็นตัวคูณคงที่** ไม่ว่าน้ำหนักเท่าไหร่ อัตราส่วนระหว่างคลาสเท่าเดิมเสมอ ทำให้คาดเดาได้

เก็บสูตร `cbrt` และ `log10` ไว้ใน Config ด้วย เผื่ออยากสลับกลับโดยไม่ต้องหาตัวเลขใหม่

### 8.2 สูตรเงิน (รากที่สอง + ตัวคูณตามด่าน)

เงินมาจาก**แม่ในคอกเท่านั้น** และ**คลาสไม่มีผลต่อเงิน** (คลาสมีผลแค่ damage/HP)

#### ⚠️ ตัวคูณตามด่าน ×10 คือสิ่งที่ทำให้เกมนี้เล่นจบได้ ห้ามตัดทิ้ง

### 8.2.1 เงินจากการฆ่า — บ่อเงินที่สอง

เดิมเงินมาจาก **แม่ในคอก** ทางเดียว ตอนนี้เพิ่มอีกสองทาง ทั้งคู่ **server คำนวณและมอบเท่านั้น ห้าม client แจ้งยอด**

| บ่อ | สูตร | ด่าน 1 | ด่าน 5 | ด่าน 9 | โตต่อด่าน |
|---|---|---:|---:|---:|---:|
| ฆ่าทหารฝ่ายรับ (ต่อตัว) | `100 × 2^(N−1)` | — | 1,600 | 25,600 | ×2 |
| **กวาดทหารทั้งด่าน** | ต่อตัว × จำนวนทหาร | — | 160M | 25.6T | **×20** |
| ฆ่าบอส (ต่อครั้ง) | `10,000 × 10^(N−1)` | 10,000 | 100M | **1e12** | ×10 |

**ทำไมทหารใช้ ×2 แต่บอสใช้ ×10:**
จำนวนทหารโต ×10 ต่อด่านอยู่แล้ว เงินต่อตัวจึงคูณแค่ ×2 ก็ได้เงินรวมโต ×20 ต่อด่าน ซึ่งเร็วกว่าราคาของที่โต ×10
ส่วนบอสฆ่าซ้ำได้เรื่อย ๆ (รีเกิดทุก 5 นาที) จำนวนครั้งไม่โตตามด่าน ค่าต่อครั้งจึงต้องโต ×10 เองเพื่อตามราคาให้ทัน — ถ้าใช้ ×2 บอสจะกลายเป็นเศษเงินตั้งแต่กลางเกม

`validate()` บังคับทั้งสองข้อ: เงินจากการกวาดทหารต้องโตต่อด่าน **ไม่ช้ากว่าราคาของ** และตัวคูณเงินบอสต้อง **ไม่ต่ำกว่าตัวคูณราคา** — ผิดเมื่อไหร่เซิร์ฟไม่บูต

#### แบ่งเงินบอส — เท่ากันทุกคนที่ร่วมตี (ตัดสินแล้ว)

`Config.getBossKillShare(stage, participantCount)` = `รางวัลเต็ม ÷ จำนวนคนที่ร่วมตี`

- **ไม่แบ่งตามสัดส่วน damage** เพราะการตีบอสใช้เวลาไม่นาน และการตีบอสเป็นแค่กิมมิค กลไกจริงของเกมคือการแย่งไข่ — ไม่ต้องซีเรียสกับความยุติธรรมของส่วนแบ่งขนาดนั้น
- นับว่า "ร่วมตี" เมื่อทำ damage ให้บอส ≥ `BOSS_REWARD_MIN_DAMAGE` (1) — กันคนยืนเฉย ๆ ในพื้นที่บอสแล้วได้เงินฟรี
- ⚠️ **server เป็นคนนับว่าใครร่วมตีบ้าง** ห้าม client แจ้งรายชื่อหรือยอด
- ข้อมูล "ใครตีบอสตัวนี้บ้าง" เป็น **per-server ไม่ต้องเซฟ** (บอสตายแล้วล้างทิ้งได้)

**ผลข้างเคียงที่รับไว้แล้ว:** คนที่ตีครั้งเดียวตอนบอสใกล้ตายก็ได้ส่วนแบ่งเต็ม — แลกกับที่ผู้เล่นใหม่ (อาวุธอ่อน) ยังได้เงินจากบอสด่านสูงที่คนอื่นตี ซึ่งช่วยให้คนตามหลังไล่ทันได้

#### ⚠️ ทหาร 1 ตัวจ่ายเงินได้ครั้งเดียวตลอดกาล

ทหารฝ่ายรับ **ตายแล้วไม่เกิดใหม่** และ `stageProgress.defendersRemaining` เซฟความคืบหน้าถาวร
→ เงินต้องจ่ายตอน `defendersRemaining` ลดลงเท่านั้น **ห้ามจ่ายซ้ำตอนโหลดข้อมูลกลับมา** และห้ามจ่ายจากด่านที่พังไปแล้ว
นี่คือช่องโหว่ที่ตรงไปตรงมาที่สุดของระบบนี้ (ดู [§12](#12-จุดที่เสี่ยงโดนโกง-exploit))

#### บ่อเงินนี้มีที่ไปแล้ว

ตอนที่เพิ่มบ่อเงินจากการฆ่าเข้ามา รายได้เกินที่ต้องใช้ **10.6 เท่า (ด่าน 2) ถึง 299 เท่า (ด่าน 9)** เพราะคอขวดพลิกเป็น "การปล่อย" ตั้งแต่ด่าน 3 ทำให้ upgrade อัตราผลิตกับอัปคอกหมดความหมาย

ตอนนี้ **ตัวคูณ damage ที่ซื้อด้วยเงิน** ([§8.6](#86-ตัวคูณ-damage-ที่ซื้อด้วยเงิน)) ดูดส่วนเกินนั้นไปแล้ว:

| ด่าน | รายได้ทั้งด่าน | ราคาที่ต้องซื้อ (รวม upgrade damage) | เหลือ |
|---:|---:|---:|---:|
| 2 | 182K | 104K | **1.75×** |
| 5 | 580M | 261M | **2.22×** |
| 7 | 141B | 60.3B | **2.34×** |
| 9 | 128T | 50.3T | **2.54×** |

จาก 11–299 เท่า เหลือ **1.64–2.54 เท่า** ตามเป้าที่ตั้งไว้ (2–3 เท่า)

### 8.3 อาวุธกับบอส — สเกลที่ล็อกกันไว้

```
damage อาวุธขั้น N = 10 × 10^(N-1)
HP บอสด่าน N       = 100 × 10^(N-1)
```

**อาวุธขั้น N ตีบอสด่าน N ตายใน 10 ครั้งพอดีทุกด่าน** สม่ำเสมอตั้งแต่ด่าน 1 ถึง 9

`Config.validate()` บังคับว่า `Weapon.DAMAGE_MULTIPLIER == Boss.HP_MULTIPLIER` — แก้ข้างเดียวไม่ได้ ไม่งั้นความรู้สึกตอนสู้บอสจะเพี้ยนไปเรื่อย ๆ ตามด่าน

### 8.4 ทำไม upgrade อัตราผลิตเป็น ×3 ทั้งที่ราคา ×10

| อัตราผลิต | ด่าน 1 | ด่าน 5 | ด่าน 9 |
|---|---:|---:|---:|
| ×10/ขั้น (รวม ×10¹⁰) | 2.2 ชม. | 2 นาที | **ทันที** |
| **×3/ขั้น (รวม ×59,049)** | 2.2 ชม. | 4.9 ชม. | **17.8 ชม.** |
| ×2/ขั้น | 2.2 ชม. | 25.1 ชม. | 19 วัน |

ถ้าเป็น ×10 อัตราผลิตจะโตเร็วกว่าความยากของด่าน (×10⁸) ทำให้ตั้งแต่ด่าน 5 ขึ้นไปสะสมกองทัพเสร็จทันที กำแพงหมดความหมาย เหลือแค่บอสกับไข่เป็นด่านกั้น

ที่ ×3 กำแพงยังเป็นด่านกั้นจริงทุกด่าน และการที่จ่ายแพงขึ้นแต่ได้ผลน้อยกว่ายังทำให้ผู้เล่นต้องเลือกว่าจะอัปอะไรก่อน

`Config.validate()` บังคับ `UPGRADE_RATE_MULTIPLIER <= UPGRADE_COST_MULTIPLIER`

#### ⚠️ ตัดขั้นบนทิ้งแล้ว — คอก 15 → 10 · อัตราผลิต 10 → 5

ทั้งสองสายมี "เลเวลที่ไม่มีใครไปถึงได้" อยู่ข้างบน ซึ่งเป็นตัวเลขหลอกตาล้วน ๆ:

| | เพดานเดิม | ราคาขั้นบนสุด | รายได้ทั้งด่าน 9 | ไปถึงได้ไหม |
|---|---:|---:|---:|---|
| คอก | Lv 15 | 1e17 | 1.28e14 | ❌ แพงกว่ารายได้ทั้งด่าน 780 เท่า |
| upgrade อัตราผลิต | ขั้น 10 | 1e12 | 1.28e14 | ⚠️ ซื้อได้ แต่ไม่ได้ damage เพิ่มเลย |

**คอก 15 → 10 ขั้น** — ราคารวมทั้งสายลดจาก 1e17 เหลือ 1.1e12 (ถูกลง ~90,000 เท่า)
ความจุที่ผู้เล่นอ้างอิงใช้จริงคือ 5–13 ตัว (ด่าน 1–9) ซึ่งยังอยู่ในเพดานใหม่สบาย ๆ
`validate()` บังคับว่า `Pen.MAX_LEVEL ≥ Stage.COUNT` เพื่อไม่ให้ตัดลึกจนคอกขยายไม่พอ

**upgrade อัตราผลิต 10 → 5 ขั้น** — ตั้งแต่ด่าน 3 คอขวดเป็น "การปล่อย" ถาวร upgrade นี้จึงหยุดเพิ่ม damage เหลือประโยชน์แค่ "เติมคลังเร็วขึ้น" ซึ่งไม่คุ้มราคาที่ไต่ถึง 1e12

ผลของการตัด — **เวลาตีทุกด่านไม่เปลี่ยนเลย** เพราะคอขวดยังเป็นการปล่อยอยู่ดี:

| ด่าน | ขั้นที่ใช้ (เดิม → ใหม่) | ผลิตได้/วิ เดิม | ผลิตได้/วิ ใหม่ | ปล่อยได้/วิ | ผลิตเกินกี่เท่า |
|---:|---|---:|---:|---:|---:|
| 6 | 5 → 5 | 60.6 | 60.6 | 4 | 15.1× |
| 7 | 6 → **5** | 199.9 | 66.6 | 6 | 11.1× |
| 8 | 7 → **5** | 654.1 | 72.7 | 8 | 9.1× |
| 9 | 8 → **5** | 2,125.7 | 78.7 | 10 | **7.9×** (เดิม 3,327×) |

**"ผลิตเกินความจำเป็น 3,327 เท่า" หายไปด้วย** เหลือ 7.9–15.1 เท่า ซึ่งเป็นระยะเผื่อที่สมเหตุสมผล (กันคลังแห้งตอนปล่อยรัว)

`validate()` บังคับว่าหลังตัดแล้ว ทุกด่านตั้งแต่ 3 ขึ้นไปต้องยัง **ผลิตได้ ≥ ปล่อยได้** — ตัดลึกกว่านี้คอขวดจะย้อนกลับไปเป็นการผลิตและเวลาตีจะเปลี่ยนโดยไม่ตั้งใจ

### 8.5 ตารางสุ่ม

**น้ำหนัก** — สุ่ม 2 ขั้น (เลือก tier ก่อน แล้วสุ่มในช่วง) weight เป็นจำนวนเต็มต่อ 1,000,000 เพื่อเลี่ยง error ปัดเศษของ float

⚠️ **ตารางน้ำหนักใช้ชุดเดียวกันทุกด่าน (ตัดสินแล้ว)** — ความคุ้มของการไต่ด่านมาจาก**โอกาสได้คลาสดี** ไม่ใช่โอกาสได้ตัวหนัก

โครง `Config.Balance.StageWeightTiers` ยังรองรับการแยกตารางรายด่านไว้เผื่ออนาคต (`Config.getWeightTiers(stage)` ถอยไปใช้ด่านที่ต่ำกว่าที่ใกล้ที่สุดอัตโนมัติ) แต่ตอนนี้กำหนดแค่ด่าน 1 และทุกด่านถอยมาใช้ตารางเดียวกันหมด **ซึ่งเป็นพฤติกรรมที่ต้องการ ไม่ใช่ของค้าง**

ตารางด่าน 1 (ใช้เป็นค่าถอยกลับของทุกด่านตอนนี้):

| tier | ช่วง (kg) | โอกาส | พบ 1 ใน |
|---:|---|---:|---:|
| 1 | 100 – 999 | 90% | 1 |
| 4 | 100,000 – 999,999 | 0.09% | 1,111 |
| 7 | 100,000,000 | 0.0001% | 1,000,000 |

*(ทดสอบแล้วด้วยการสุ่ม 5,000,000 ครั้ง ตรงทุก tier)*

**ตัวละคร** — ไข่ต่างกันที่คลาสที่ออกได้ ไม่ใช่ที่น้ำหนัก

| ไข่ | แหล่ง | C | B | A | S | SS | รับประกัน tier |
|---|---|---:|---:|---:|---:|---:|---|
| ด่าน 1 | บอสด่าน 1 | 90% | 10% | — | — | — | — |
| ด่าน 5 | บอสด่าน 5 | 50% | 45% | 5% | — | — | — |
| ด่าน 9 | บอสด่าน 9 | 10% | 20% | 50% | **20%** | — | — |
| ตำนาน | **Robux** | — | 35% | 45% | 18% | **2%** | **tier 3 ขึ้นไป** |

ตารางเต็มทั้ง 9 ด่านอยู่ใน [§8.5.1](#851-ไข่รายด่าน-และน้ำหนักที่ล็อกตั้งแต่ในรัง)

- **ไข่จากบอสออกได้ C ถึง S** — ด่าน 7 ขึ้นไปถึงจะแตะ S ได้ (1% → 20%)
- **SS ออกได้จากไข่ตำนานเท่านั้น** `validate()` บังคับกฎนี้: ถ้าเผลอใส่ SS ในไข่ที่ `source = "boss"` เซิร์ฟเวอร์จะไม่บูต
  เหตุผล: ถ้าไข่ฟรีให้ SS ได้เมื่อไหร่ ไข่ที่จ่ายเงินจริงจะขายไม่ออกทันที
- สุ่มคลาสก่อน แล้วสุ่มตัวละครในคลาสนั้นแบบเท่า ๆ กัน

*(ทดสอบแล้วด้วยการสุ่มไข่ละ 300,000 ครั้ง ตรงทุกคลาส — ไข่ตำนานได้ SS 1.98% เทียบเป้า 2%)*

### 8.5.1 ไข่รายด่าน และน้ำหนักที่ล็อกตั้งแต่ในรัง

**บอสแต่ละด่านวางไข่คนละชนิดกัน** — `egg_stage1` … `egg_stage9` (`Config.getBossEggId(stage)`)
ไข่ผูกกับด่านผ่านฟิลด์ `stage` และ `validate()` บังคับว่าทุกด่านต้องมีไข่ของตัวเองที่ `enabled` อยู่ ไม่งั้นผู้เล่นที่ไปถึงด่านนั้นจะแย่งไข่ไม่ได้เลย = **ตันถาวร**

| ด่าน | C | B | A | S |
|---:|---:|---:|---:|---:|
| 1 | 90% | 10% | — | — |
| 2 | 80% | 20% | — | — |
| 3 | 70% | 29.9% | 0.1% | — |
| 4 | 60% | 39% | 1% | — |
| 5 | 50% | 45% | 5% | — |
| 6 | 40% | 50% | 10% | — |
| 7 | 30% | 45% | 24% | 1% |
| 8 | 20% | 30% | 40% | 10% |
| 9 | 10% | 20% | 50% | 20% |

ทุกแถวรวมได้ 10,000 พอดี (`CLASS_ROLL_MAX`) — 0.1% ของด่าน 3 = weight 10 ซึ่งความละเอียดของ `CLASS_ROLL_MAX` รองรับพอดี **ถ้าอยากได้ละเอียดกว่า 0.01% ต้องดัน `CLASS_ROLL_MAX` ขึ้นก่อน**

*(ทดสอบแล้ว: สุ่มด่านละ 60,000 ครั้ง ตรงทุกช่องทั้ง 9 ด่าน · ไม่มีด่านไหนออก SS)*

#### ⚠️ ลำดับการสุ่มเปลี่ยนแล้ว: น้ำหนักมาก่อน และมาตั้งแต่ในรัง

```
บอสเกิด → วางไข่ 5 ฟอง
            └─ สุ่ม "น้ำหนัก" ของแต่ละฟองทันที (Config.rollMotherWeightForEgg)
               └─ ขนาดโมเดลไข่ในรังแปรตามน้ำหนัก — ไข่ใหญ่ = หนัก
ผู้เล่นกดค้าง 3 วิ แย่งไข่ → ไข่ (พร้อมน้ำหนักที่ล็อกไว้แล้ว) เข้ากระเป๋า
ผู้เล่นวางไข่ลงสวนฟัก → สุ่ม "ตัวละคร" ตอนนี้เลย (Config.rollCharacter)
            └─ server เก็บ charId ไว้เงียบ ๆ ใน HatchSlot ไม่บอก client
            └─ ใช้คลาสที่สุ่มได้คำนวณเวลาฟัก (Config.getHatchSeconds) — ดูหัวข้อถัดไป
ครบเวลาฟัก → เปิดเผยตัวละครที่สุ่มไว้ (อ่านจาก slot.charId ไม่สุ่มใหม่) → ได้ตัวแม่
```

**ทำไมต้องสุ่มน้ำหนักตั้งแต่ในรัง:** core loop ของเกมคือการแย่งไข่ ถ้าไข่ทุกฟองหน้าตาเหมือนกัน การแย่งก็เป็นแค่การรีบกดสุ่ม ไม่มีการตัดสินใจอะไรเลย พอขนาดไข่บอกน้ำหนัก ผู้เล่นทั้ง 6 คนเห็นพร้อมกันว่าฟองไหนคุ้มค่าที่จะแย่ง — **การแย่งไข่จึงกลายเป็นเกมจริง**

**ผลที่ตามมาต่อ schema (ห้ามลืม):** ไข่สองฟองชนิดเดียวกันมีน้ำหนักต่างกันได้ → `heldEggs` เก็บเป็น `[eggId] = จำนวน` ไม่ได้อีกต่อไป ต้องเก็บรายฟอง และ `hatching` ต้องมีฟิลด์ `weight` ด้วย ([§3](#3-โครงสร้าง-playerdata))

⚠️ **server เป็นคนสุ่มและถือน้ำหนักไว้ฝั่งเดียว** client รู้ได้แค่ขนาดโมเดลที่ server บอก ห้ามให้ client คำนวณหรือส่งน้ำหนักมาเอง

⚠️ **ทำไมตัวละครย้ายมาสุ่มตอน "วางไข่" แทนที่จะเป็นตอน "ฟักเสร็จ" เหมือนเดิม:** เพิ่มระบบเวลาฟักตามน้ำหนัก+คลาส (หัวข้อถัดไป) แล้วเวลาฟักต้องรู้คลาสก่อนตั้งตัวจับเวลา — คลาสจึงต้องสุ่มให้เสร็จก่อนคำนวณ `hatchAt` ผู้เล่น**ยังไม่เห็นผล**จนกว่าไข่จะฟักเสร็จจริงเหมือนเดิม (server เก็บ `charId` ไว้ใน `HatchSlot` แต่ไม่ส่งเข้า sync payload) ต่างจากเดิมแค่ server รู้ผลไว้ก่อนเท่านั้น — การเปลี่ยนจังหวะนี้ทวนกับผู้ใช้แล้วก่อนลงมือ (ชนกับดีไซน์เดิมที่ "ตอนฟักถึงค่อยสุ่มตัวละคร" ซึ่งเป็นการตัดสินใจที่ล็อกไว้ก่อนหน้านี้)

#### เวลาฟักตามน้ำหนัก + คลาส (`Config.getHatchSeconds`)

⚠️ **แทนที่สูตรเดิมของไข่ source="boss" ทั้งหมด** — เดิมเวลาฟักคงที่ตาม "ด่านที่บอสวางไข่" (`SECONDS_PER_STAGE × เลขด่าน` เก็บใน `EggTypes[eggId].hatchTime`) ไม่ขึ้นกับน้ำหนัก/คลาสของสิ่งที่จะออกมาเลย ตอนนี้เปลี่ยนเป็นขึ้นกับ **น้ำหนัก+คลาสของตัวละครที่จะฟักออกมา** แทน — ด่านที่ไข่มาจากไม่มีผลต่อเวลาฟักอีกต่อไป (มีผลแค่ตารางคลาสที่สุ่มได้ ซึ่งด่านสูงมีโอกาสได้คลาสดีมากกว่า)

`Config.Balance.Hatchery.HatchTimeByTier` — เวลาฐาน (คลาส C) ตาม tier น้ำหนัก 1–7:

| tier | ช่วงน้ำหนัก | เวลาฐาน |
|---:|---|---|
| 1 | 100–999 kg | 1 นาที |
| 2 | 1K–9.9K | 5 นาที |
| 3 | 10K–99K | 30 นาที |
| 4 | 100K–999K | 2 ชม. |
| 5 | 1M–9.9M | 8 ชม. |
| 6 | 10M–99M | 16 ชม. |
| 7 | 100M (คงที่) | 24 ชม. |

`Config.Balance.Hatchery.ClassHatchMultiplier` — ตัวคูณตามคลาสที่สุ่มได้: **C ×1 · B ×1.15 · A ×1.35 · S ×2 · SS ×2.6**

`เวลาฟักจริง = HatchTimeByTier[tier] × ClassHatchMultiplier[คลาส]` — ตัวอย่างตรวจสอบ: tier 7 × คลาส S = 24 ชม. × 2 = **48 ชม.** เวลาฟักสูงสุดที่เป็นไปได้จริง (tier 7 × SS) = 24 ชม. × 2.6 = **62.4 ชม.** ยังอยู่ใต้เพดาน `MAX_HATCH_SECONDS` (7 วัน) ที่ `validate()` บังคับไว้

⚠️ **ไข่ source="robux" (ไข่ตำนาน) ไม่ใช้สูตรนี้** — ฟักคงที่ `LEGENDARY_SECONDS` (1 นาที) เสมอไม่ว่า tier/คลาสอะไร ตั้งใจให้ "จ่ายเงินจริงซื้อความเร็ว" (เร็วเท่าไข่ tier 1 ธรรมดาพอดี ไม่ได้เปรียบเรื่องความเร็วไปมากกว่านั้น)

⚠️ **`EggTypes[eggId].hatchTime` ของไข่รายด่านทั้ง 9 กลายเป็น metadata ที่ไม่ได้ใช้จริงแล้ว** ยังคงสูตร `SECONDS_PER_STAGE × เลขด่าน` และ `validate()` เดิมไว้ (ไม่ได้ลบ — เป็น field ที่ core-locked ไว้ใน CLAUDE.md แยกต่างหาก การลบต้องทวนก่อนแยกรอบ) แต่ `EggService.placeEgg()` ไม่อ่านค่านี้ไปคำนวณ `hatchAt` อีกต่อไปสำหรับไข่ source="boss"

⚠️ **ยามเวลาฟักเทียบกับรอบรีเกิดบอส 5 นาทีที่เคยเป็นข้อกังวล ([§13](#13-ค่าที่ผมตั้งเอง/รอยืนยัน)) ไม่ใช่ประเด็นอีกต่อไป** เพราะเวลาฟักตอนนี้ไม่ได้ผูกกับรอบบอสเลย (ผูกกับน้ำหนัก+คลาสของสิ่งที่จะฟักออกมาแทน) เวลาฟักช่วง 1 นาที–62.4 ชม. กว้างกว่ารอบบอสมาก ไม่มีจุดชนกันแบบเดิม

#### ขนาดโมเดลไข่/แม่ตามน้ำหนัก (`Config.getEggVisualSize` / `Config.getMotherVisualSize`)

ไข่และแม่ scale ขนาดโมเดลตามน้ำหนักด้วย **ตัวคูณชุดเดียวกัน** (`Config.Balance.VisualScale.WEIGHT_MULTIPLIER`) คนละฐาน — ฐานคือ `Config.MapDimensions.Blockout.EggSize` / `MotherSize` ที่ tier 1:

| tier | ตัวคูณ |
|---:|---:|
| 1 | ×1.00 |
| 2 | ×1.32 |
| 3 | ×1.74 |
| 4 | ×2.29 |
| 5 | ×3.02 |
| 6 | ×3.98 |
| 7 | ×5.25 |

- **ไข่** แสดงขนาดเดียวกันทุกที่ที่เห็น (ตอนนี้คือในสวนฟักเท่านั้น — สวนบอส/กระเป๋าเป็นเฟสถัดไป)
- **แม่** มีสองขนาด: "ถือ/ส่งรบ" (เต็มตามตาราง) กับ "ในคอก" ซึ่งคูณ `Config.Balance.VisualScale.MOTHER_PEN_SHRINK` (**ตอนนี้ 1 = 1:1** เท่าขนาดถือ · เดิม 0.1 = 1/10 เปลี่ยนเพราะโมเดลจริงเล็กเกินไป) **ทุก tier เท่ากัน** — ตอนนี้มีแค่การแสดงในคอกที่ implement จริง (กระเป๋า/ส่งรบยังไม่มี UI/โมเดล 3 มิติ)

⚠️ **ฐานจริงของแม่ในโค้ด (`MotherSize = 3.5×3.5×5`) ไม่ใช่ทรงลูกบาศก์ฐาน 8** — งานนี้เพิ่มแค่ "ตัวคูณ" บนฐานเดิม ไม่ได้เปลี่ยนรูปทรง/ฐานของโมเดล (ยังเป็น blockout placeholder เหมือนเดิม)

#### การรับประกัน tier ของไข่ตำนาน

ไข่ตำนานรับประกัน **tier 3 ขึ้นไป (10,000 kg+)** ซึ่งปกติเป็นผลลัพธ์ 1 ใน 111 ของไข่ฟรี

กลไก: **สุ่มตามตารางปกติก่อน ถ้าได้ต่ำกว่า tier 3 ค่อยดันขึ้นมา** ไม่ใช่สุ่มจากตารางที่ตัดชั้นล่างออก
ต่างกันตรงที่วิธีนี้ยัง**ลุ้น tier สูงกว่าได้ตามอัตราเดิมทุกชั้น** รวมถึง tier 7 (1 ในล้าน) — จ่ายเงินแล้วได้พื้นขั้นต่ำที่ดี แต่ยังมีโอกาสถูกรางวัลใหญ่เท่าเดิม

*(ทดสอบแล้ว: สุ่มไข่ตำนาน 200,000 ฟอง ไม่มีฟองไหนต่ำกว่า tier 3 และยังออก tier สูงกว่าได้)*

| คลาส | ตัวคูณ | ตัวละคร |
|---|---:|---|
| SS | ×432 | องค์ยูไล |
| S | ×216 | พระแม่กวนอิม · เง็กเซียนฮ่องเต้ |
| A | ×36 | พระถังซัมจั๋ง · ซุนหงอคง |
| B | ×6 | ตือโป๊ยก่าย · ซัวเจ๋ง · ม้าขาวมังกร |
| C | ×1 | ลิง · หมู · ม้า · ปลา |

ที่มาของตัวเลขชุดนี้และเหตุผลที่ SS หยุดที่ ×2 เหนือ S อยู่ใน [§8.1](#81-สูตร-damage--hp-เลือกแล้ว-รากที่สอง)

### 8.6 ตัวคูณ damage ที่ซื้อด้วยเงิน

⚠️ **ระบบเดิม `STAGE_DAMAGE_BASE ^ (wallProgress − 1)` ยกเลิกทั้งหมดแล้ว** ตัวคูณ damage ไม่ได้มาฟรีตามด่านอีกต่อไป — ต้อง **ซื้อทีละขั้นด้วยเงิน**

#### ทำไมถึงเปลี่ยน — ยุบสองปัญหาเข้าหากัน

| ปัญหา | อาการ |
|---|---|
| **เงินล้น** | รายได้เกินที่ต้องใช้ 11 เท่า (ด่าน 2) ถึง 299 เท่า (ด่าน 9) · คอขวดพลิกเป็น "การปล่อย" ตั้งแต่ด่าน 3 ทำให้ upgrade อัตราผลิตกับอัปคอกหมดความหมาย เหลือแค่อาวุธที่ยังคุ้ม |
| **ตัวคูณ damage ไม่มีการตัดสินใจ** | ได้ฟรีอัตโนมัติตอนพังกำแพง ผู้เล่นไม่ได้เลือกอะไรเลย |

ยุบเข้าหากัน: **ตัวคูณ damage กลายเป็นของที่ต้องซื้อ → เงินที่ล้นมีที่ไป และความคืบหน้าย้ายจาก "ดวงจากไข่" มาอยู่ที่ "รายได้ที่คาดเดาได้"**

#### กติกา

```
ตัวคูณ damage = 1.1 ^ damageLevel            (damageLevel = 0 → ×1)
เพดานที่ซื้อได้ = wallProgress × 8           (ด่าน 1 → 8 ขั้น · ด่าน 9 → 72 ขั้น)
ราคาขั้นที่ k ของด่าน N = STAGE_COST_BASE[N] × 1.3^(k−1)
```

- **ตัวคูณเป็นของบัญชีผู้เล่น ไม่ใช่ของแม่รายตัว** (`damageLevel` ใน PlayerData) — ง่ายกว่ามาก และ **แม่ตายไปก็ไม่เสียการลงทุน**
- ใช้กับทั้งตัวแม่และตัวลูกที่ส่งไปรบ · คำนวณตอนเข้ารบทุกครั้ง ไม่เก็บติดไปกับกองลูก → ลูกที่สะสมไว้แต่ด่านต้นแรงขึ้นตามผู้เล่น ไม่มีกองตกยุค
- **เพดานผูกกับด่าน — บังคับ** ไม่งั้นผู้เล่นจะนั่งฟาร์มเงินที่ด่าน 3 แล้วซื้อจนสุด ข้ามทั้งเกม
- ⚠️ **สูตรเงินไม่ถูกแตะ** — `10^(wallProgress−1)` ยังอยู่เหมือนเดิม ด่านยังคูณเงิน แค่ไม่คูณ damage แล้ว

#### ⚠️ off-by-one ที่พลาดง่ายที่สุด (ย้ายมาจากระบบเดิม)

ตอนอยู่ด่าน N ผู้เล่นพังกำแพงมาแล้ว N−1 ด่าน → เพดาน = `(N−1 + 1) × 8` = `wallProgress × 8`

| ด่าน | พังมาแล้ว | เพดานขั้น | ตัวคูณถ้าซื้อครบ |
|---:|---:|---:|---:|
| 1 | 0 | **8** ← ต้องไม่ใช่ 0 | ×2.1 |
| 5 | 4 | 40 | ×45.3 |
| 9 | 8 | 72 | ×955.6 |

ถ้าเผลอเขียน `(wallProgress − 1) × 8` ผู้เล่นใหม่จะซื้ออะไรไม่ได้เลยและตันตั้งแต่ด่านแรก — `validate()` assert ตรง ๆ ว่าด่าน 1 ต้องได้ 8 ขั้น พร้อม unit test แยกอีกชั้น

#### ⚠️ ทำไม 8 ขั้น/ด่าน ไม่ใช่ 9

ค่าที่สั่งมาคือ "×1.1 ต่อขั้น · **9 ขั้นต่อด่าน** · รวม **72 ขั้น**" ซึ่ง **ขัดกันเอง** — 9 ขั้น × 9 ด่าน = 81 ไม่ใช่ 72

และที่ 9 ขั้น/ด่าน ตัวคูณแรงเกินจนด่าน 4 จบใน **0.502 ชม.** ซึ่งเฉียดพื้น 0.5 ชม. แบบแทบไม่มีระยะเผื่อ (เพดานจริงคือ ×1.10014 ต่อขั้น — แก้อะไรอีกนิดเดียวก็หลุด)

| ขั้น/ด่าน | ขั้นรวม | ด่าน 4 | ด่าน 9 | ผ่านยาม |
|---:|---:|---:|---:|---|
| 7 | 63 | 1.08 ชม. | 128 ชม. | ❌ เกินเพดาน 72 ชม. |
| **8** | **72** | **0.74 ชม.** | **54 ชม.** | ✅ มีระยะเผื่อทั้งสองด้าน |
| 9 | 81 | 0.502 ชม. | 23.0 ชม. | ⚠️ ผ่านแบบเฉียดพื้น 0.4% |

เลือก **8 ขั้น/ด่าน** → ตรงกับ "รวม 72 ขั้น" ที่สั่งมาพอดี และ `1.1^8 = 2.14` ต่อด่าน ซึ่งใกล้ตัวคูณ 2.5/ด่านของระบบเดิมพอ ๆ กับที่ `1.1^9 = 2.36` ใกล้

#### วิธีคำนวณราคา — แก้สมการ ไม่ได้เดา

**เป้าหมาย:** ซื้อครบเพดานของด่านนั้นแล้ว รายได้ส่วนเกินเหลือ 2–3 เท่า (ไม่ใช่ 0 เพราะยังต้องเหลือซื้ออาวุธและอัปคอก)

```
ราคารวมของด่าน N = B_N × (1.3^8 − 1) ÷ (1.3 − 1) = B_N × 23.86
ต้องการ ราคารวม   = 0.40 × รายได้ทั้งด่าน N
→  B_N = 0.40 × รายได้ด่าน N ÷ 23.86
```

"รายได้ทั้งด่าน N" = `(เงินจากคอก/ชม. + เงินจากบอส/ชม.) × เวลาตีด่านนั้น + เงินจากกวาดทหารทั้งด่าน` ของผู้เล่นอ้างอิงที่ซื้อครบเพดาน (`Config.getReferenceStageIncome`)

ทำไม 40%: ส่วนเกิน ≈ `1 ÷ 0.40` = 2.5 เท่า ซึ่งอยู่กลางช่วงเป้าหมาย 2–3 เท่าพอดี

| ด่าน | รายได้ทั้งด่าน | `B_N` | ราคารวม/ด่าน | % ของรายได้ | ส่วนเกินหลังซื้อครบ |
|---:|---:|---:|---:|---:|---:|
| 1 | 17.8K | 300 | 7.2K | 40% | 1.75× |
| 2 | 182K | 3,100 | 74.0K | 41% | 1.75× |
| 3 | 3.82M | 64,000 | 1.53M | 40% | 2.09× |
| 4 | 21.4M | 420,000 | 10.0M | 47% | 1.64× |
| 5 | 580M | 9.7M | 231M | 40% | 2.22× |
| 6 | 18.0B | 300M | 7.16B | 40% | 2.41× |
| 7 | 141B | 2.4B | 57.3B | 41% | 2.34× |
| 8 | 4.00T | 67B | 1.60T | 40% | 2.46× |
| 9 | 128T | 2.1T | 50.1T | 39% | 2.54× |

**ส่วนเกินลดจาก 11–299 เท่า เหลือ 1.64–2.54 เท่า** ตามเป้า

หมายเหตุสองข้อ:
- **ด่าน 1 ไม่มีกำแพง** จึงไม่มี "เวลาตี" ใช้รายได้ 1 ชั่วโมงแรกเป็นฐานแทน · ขั้นแรกราคา 300 ซึ่งผู้เล่นใหม่ (มี 500 coins) ซื้อได้ทันที
- **ด่าน 4 ดันขึ้นจาก 360,000 เป็น 420,000** เพื่อให้ราคาไล่ขึ้นตลอด 72 ขั้นไม่มีช่วงถูกลง (รายได้ด่าน 4 โตแค่ 5.6 เท่าเพราะเป็นด่านที่เพิ่งได้คลาสใหม่ เวลาตีจึงสั้น) `validate()` บังคับข้อนี้

#### ระบบนี้บังคับซื้อแค่ไหน

ผู้เล่นที่ **ไม่ซื้อ upgrade เลย** (ตัวคูณ ×1 ตลอด):

| ด่าน | 2 | 3 | 4 | **5** | 7 | 9 |
|---|---:|---:|---:|---:|---:|---:|
| เวลาตี | 4.2 ชม. | 18.6 ชม. | 15.5 ชม. | **104 ชม.** | 863 ชม. | 51,761 ชม. |

**ตันที่ด่าน 5** (เกินเพดาน 72 ชม.) และด่าน 9 กลายเป็น 5.9 ปี — ซื้อครบเพดานช่วยที่ด่าน 9 ได้ **956 เท่า**
ด่าน 2–4 ยังลุยได้โดยไม่ซื้อ ซึ่งดี: ผู้เล่นได้ลองเล่นก่อนที่ระบบจะเริ่มบังคับ

#### ⚠️ ผลข้างเคียงที่ตัดสินใจรับไว้แล้ว — ห้ามแก้กลับ

- **เกมเอียงไปทาง idle มากขึ้น** — ฟาร์มเงินแล้วอัป มีน้ำหนักมากกว่าการลุ้นไข่
- **น้ำหนักแม่และคลาสมีความสำคัญน้อยลง** เมื่อเทียบกับการอัป

ทั้งสองข้อเป็น **ผลที่ตั้งใจ** ของการย้ายความคืบหน้าจาก "ดวง" มาอยู่ที่ "รายได้ที่คาดเดาได้" ไม่ใช่ผลข้างเคียงที่ต้องแก้ในรอบหน้า

#### ยามเฝ้าสมดุล

| ยาม | บังคับอะไร |
|---|---|
| `assertProgressionIsSane()` | ทุกด่านใช้เวลา 0.5–72 ชม. · ด่านท้ายไม่เร็วกว่าด่านแรก · เวลาฟาร์มไข่ ≤ 5 เท่าของเวลาตี |
| ราคา upgrade ต่อด่าน | ต้องกินรายได้ของด่านนั้น **30–70%** — ถูกไปเงินจะล้นเหมือนเดิม แพงไปผู้เล่นจะตัน |
| ราคาไล่ขึ้น | ราคาขั้น k ต้องไม่ถูกกว่าขั้น k−1 ตลอดทั้ง 72 ขั้น |
| เพดานด่าน 1 | ต้องเป็น 8 ขั้น (กัน off-by-one) |
| `assertTurretIsSurvivable()` | turret กินกำลังพลไม่เกิน 35% |

⚠️ **ผู้เล่นอ้างอิงของยามสมมติว่า "ซื้อครบเพดานของด่านนั้น"** — สมมติแบบนี้ได้อย่างซื่อสัตย์ เพราะเงินเป็นรายได้ที่คาดเดาได้ ต่างจากคลาสที่เป็นการสุ่ม และยามราคาข้างบนบังคับอยู่แล้วว่าราคาต้องอยู่ในวิสัยที่จ่ายไหว

*(ทดสอบแล้วว่ายามจับได้จริง: ตั้งตัวคูณต่อขั้นเป็น 1.3 หรือ 1.01 · ตั้งราคาด่าน 5 ถูกลง/แพงขึ้น 100 เท่า — `validate()` ล้มทุกกรณี)*

### 8.6.1 turret — คำนวณจากสูตร ไม่เก็บเป็นตัวเลข

**ประวัติของค่านี้ เพราะมันพลาดมาแล้วสองครั้งในทางตรงข้ามกัน แล้วต้องคำนวณใหม่ด้วยมืออีกสามครั้ง:**

| รอบ | สาเหตุ | ค่าที่ด่าน 9 |
|---:|---|---:|
| 1 | ตั้งจาก damage ทหารฝ่ายรับทั้งด่าน | 1,000,000,000 → turret ไร้ผล (0.35%) |
| 2 | ระบบรบเปลี่ยนเป็นปล่อยต่อเนื่อง ค่าเดิมไม่ได้แก้ | 1,000,000,000 → **ฆ่ายกกอง** (238× ของเรา) |
| 3 | ตั้งใหม่เป็นสัดส่วนของ damage/วินาที | 840,000 |
| 4 | เปลี่ยนตัวคูณคลาส → ต้องคำนวณใหม่ | 250,000 |
| 5 | ย้ายตัวคูณ damage มาเป็นระบบซื้อ → คำนวณใหม่อีก | 150,000 |

**รากของปัญหา:** `turretDps` ไม่เคยเป็นค่าที่ตั้งอิสระได้เลย มันเป็น *ผลลัพธ์* ของ `TOLL × damage/วินาที` มาตั้งแต่รอบที่ 3 แต่ถูกเก็บเป็นตัวเลขดิบ 9 ค่า ซึ่งต้องไล่แก้มือทุกครั้งที่อะไรก็ตามใน 5 อย่างนี้ขยับ: **ตัวคูณคลาส · ตัวคูณ damage ที่ซื้อได้ · อัตราปล่อย · อัตราผลิต · ความจุคอก**

และยามเดิมจับได้แค่ตอน **เกินเพดาน 35%** เท่านั้น ถ้าค่าเพี้ยนไปอยู่ที่ 2% (turret ไร้ผล) หรือ 30% (โหดเกิน) มันปล่อยผ่านเงียบ ๆ

#### ✅ ตอนนี้เก็บแค่ "สัดส่วน" แล้วให้โค้ดคำนวณ damage เอง

```lua
Config.Balance.Combat.TURRET_TOLL = { 0, 0.10, 0.11, 0.13, 0.14, 0.16, 0.17, 0.19, 0.20 }

turretDps(N) = TURRET_TOLL[N] × Config.getReferenceDps(N)
```

ตาราง `Stages` **ไม่มีฟิลด์ `turretDps` แล้ว** — ปรับตัวคูณคลาส/upgrade/อัตราปล่อยอะไรก็ตาม **turret ขยับตามเองทันที ไม่ต้องแตะอะไรเลย**

สูตรที่ทำให้ทั้งหมดนี้เป็นไปได้ (ระยะเวลารบตัดกันออกทั้งสองฝั่ง เพราะ **HP ของตัวเรา = damage ของตัวเรา**):

```
สัดส่วนกำลังพลที่เสียให้ turret = turretDps ÷ (damage/วินาทีของเรา)
```

| ด่าน | damage/วิ ของเรา | `turretDps` ที่คำนวณได้ | กินกำลังพล |
|---:|---:|---:|---:|
| 2 | 4.6 | 0.46 | **10.0%** |
| 4 | 566 | 73.6 | **13.0%** |
| 6 | 5,206 | 833 | **16.0%** |
| 9 | 769K | 153.8K | **20.0%** |

สัดส่วนตรงเป๊ะทุกด่านแล้ว (เดิมเพี้ยนไป 10.0–19.5% เพราะปัดเลขตอนคำนวณมือ)

#### สิ่งที่ยามเช็คตอนนี้

| ยาม | บังคับอะไร |
|---|---|
| `TURRET_TOLL` ครบ 9 ด่าน | ขาดด่านไหน = `nil` แล้ว turret ด่านนั้นพัง |
| ด่าน 1 ต้องเป็น 0 | ด่าน 1 ไม่มีกำแพง |
| ทุกค่า ≤ `TURRET_TOLL_CEILING` (35%) | เกินแล้วทหารตายก่อนถึงกำแพง |
| **ไล่ขึ้นไม่ถอยหลัง** | กำแพงด่านสูงต้องเขี้ยวขึ้น ไม่ใช่อ่อนลง |
| `turretDps ÷ dps` ต้องเท่ากับ `TOLL` เป๊ะ | ดักกรณีมีคนเผลอกลับไปเขียนตัวเลขดิบอีก |

*(ทดสอบแล้ว: ลดตัวคูณ damage ต่อขั้นจาก 1.1 เป็น 1.05 → `turretDps` ลดตามเองทันที และสัดส่วนยังเป็น 20% เท่าเดิม · ตั้ง TOLL เป็น 90% หรือให้ด่าน 9 ต่ำกว่าด่าน 8 → `validate()` ล้มทั้งสองกรณี)*

#### ⚠️ ผลข้างเคียงที่ตั้งใจ: ไม่ซื้อ upgrade = เจอ turret เขี้ยวกว่า

`getReferenceDps()` สมมติว่าผู้เล่น **ซื้อ upgrade ครบเพดานของด่านนั้น** ดังนั้น `turretDps` ที่ตั้งไว้คือค่าที่กินกำลังพล 10–20% *ของผู้เล่นที่ซื้อครบ*

ผู้เล่นที่ยังไม่ซื้อจะมี damage/วินาทีต่ำกว่า → **turret กินสัดส่วนของเขามากกว่า** ตามที่เขาขาด — เช่น คนที่ซื้อไปครึ่งเดียวจะเสียกำลังพลราวสองเท่าของสัดส่วนในตาราง

**นี่คือพฤติกรรมที่ถูกต้อง** ไม่ซื้อของก็ควรเจอกำแพงที่เขี้ยวกว่า และมันเสริมกับระบบ upgrade ที่ซื้อด้วยเงินพอดี — ไม่ใช่บั๊กที่ต้องแก้

#### ข้อดีที่ติดมาฟรี

สัดส่วนที่เสียยังแปรผกผันกับน้ำหนักแม่เหมือนเดิม — แม่หนักกว่า = damage ต่อตัวสูงกว่า = เสียสัดส่วนน้อยกว่า ผู้เล่นที่ลงทุนกับแม่ได้รางวัลตรงนี้โดยไม่ต้องเขียนกฎเพิ่ม

`EggType` จึงไม่มีฟิลด์ `price` โดยตั้งใจ (`validate()` บังคับว่าทุกไข่ต้องมี `source` เป็น `"boss"` หรือ `"robux"`)

| ไข่ | `source` | ได้มายังไง |
|---|---|---|
| ธรรมดา · หายาก | `"boss"` | แย่งจากรังบอส กดค้าง 3 วินาที |
| ตำนาน | `"robux"` | ซื้อด้วย Robux ผ่าน Developer Product เท่านั้น |

#### ทำไมไม่เก็บราคา Robux ใน Config

ราคาจริงตั้งใน **Creator Dashboard** ถ้าเก็บไว้ใน Config ด้วยจะมีสองแหล่งความจริง วันที่ปรับราคาแล้วลืมแก้ Config ผู้เล่นจะเห็นราคาผิดในร้าน แล้วโวยตอนกดซื้อ

Config เก็บแค่ `productId` · ชื่อ · คำอธิบาย · ให้ไข่อะไรกี่ฟอง
ฝั่ง client ดึงราคามาโชว์ด้วย `MarketplaceService:GetProductInfo(productId, Enum.InfoType.Product)`

#### ProcessReceipt — จุดที่พลาดแล้วเสียเงินจริง

Roblox เรียก `ProcessReceipt` **ซ้ำได้เรื่อย ๆ** จนกว่าจะได้ `PurchaseGranted` ถ้าเซิร์ฟเวอร์ล่มกลางทาง หรือคืน `NotProcessedYet` มันจะเรียกใหม่ในเซิร์ฟเวอร์อื่น อาจเป็นชั่วโมงถัดมา

```
ProcessReceipt(receiptInfo):

1. หา product จาก receiptInfo.ProductId
   ไม่เจอ → คืน NotProcessedYet (อย่าคืน PurchaseGranted เด็ดขาด
            ไม่งั้นผู้เล่นจ่ายเงินแล้วไม่ได้ของ และเรียกคืนไม่ได้)

2. เช็คว่าเคยให้ของไปแล้วหรือยัง
   key = Config.PurchaseLog.RECEIPT_PREFIX .. receiptInfo.PurchaseId
   เคยให้แล้ว → คืน PurchaseGranted ทันที (idempotent)

3. หาผู้เล่นจาก receiptInfo.PlayerId
   ไม่อยู่ในเซิร์ฟเวอร์นี้ → คืน NotProcessedYet
   (Roblox จะเรียกใหม่ตอนผู้เล่นเข้ามา ไม่ใช่ความผิดพลาด)

4. ให้ของ + บันทึก receipt ลง DataStore ใน UpdateAsync เดียวกัน
   ⚠️ ต้องสำเร็จทั้งคู่หรือไม่สำเร็จเลย

5. เซฟสำเร็จ → คืน PurchaseGranted
   เซฟไม่สำเร็จ → คืน NotProcessedYet (อย่ากลืน error)
```

**กฎเหล็ก 4 ข้อ:**

| กฎ | พลาดแล้วเป็นไง |
|---|---|
| **ห้ามคืน `PurchaseGranted` ก่อนเซฟสำเร็จ** | ผู้เล่นเสียเงินแล้วของหาย ไม่มีทางกู้ |
| **ต้อง idempotent ด้วย `PurchaseId`** | Roblox retry แล้วผู้เล่นได้ของสองรอบจากการจ่ายครั้งเดียว |
| **`NotProcessedYet` คือคำตอบที่ปลอดภัยเสมอ** | คืน `PurchaseGranted` ตอนไม่แน่ใจ = เสียของฟรี · Roblox จะลองใหม่ให้เอง |
| **เก็บ log ทุกธุรกรรม** | มีคนทักว่าไม่ได้ของแล้วตรวจไม่ได้ |

log เก็บใน DataStore แยก (`Config.PurchaseLog.STORE_NAME`) ไม่ปนกับ `PlayerData` เพราะเป็นข้อมูลคนละอายุ (ธุรกรรมเก็บถาวรเพื่อตรวจสอบ ส่วน PlayerData เขียนทับตลอด)

> **ยังไม่ตัดสิน:** ไข่ตำนานควรให้แม่ tier ไหน — ดู [§13](#13-ค่าที่ผมตั้งเองรอยืนยัน) มีสองทางเลือก

### 8.8 ความเร็ววิ่งที่ซื้อด้วยเงิน

**บ่อเงินบ่อที่สองต่อจากตัวคูณ damage** (`Config.Balance.SpeedUpgrade` · `speedLevel` ใน PlayerData)

ที่มา: เกมแนวขโมยไข่ให้ผู้เล่นวิ่งบนลู่เพื่อเก็บความเร็ว เกมนี้เปลี่ยนเป็น **ซื้อด้วยเงิน** แทน
เพราะแมพยาว 1,968 studs และเวลาเดินทางไป-กลับรังบอสด่าน 9 กินถึง **33% ของรอบบอส 5 นาที**

⚠️ **เอาแท่นวาปออกหมดแล้ว** ผู้เล่นเดินไปเองทุกที่ · ไม่มีวาปไปรังบอสด้วย
(วาปไปรังได้เมื่อไหร่ การแย่งไข่ก็หมดความหมาย)

```
ตัวคูณ = 1 + (MAX_MULTIPLIER − 1) × (ขั้น ÷ MAX_LEVEL) ^ CURVE_EXPONENT
       = 1 + 3 × (ขั้น ÷ 5) ^ 0.75

ความเร็ว = MapDimensions.Player.WalkSpeed × ตัวคูณ = 32 × ตัวคูณ
ราคาขั้น N = 10,000 × 10^(N−1)
```

| ขั้น | ราคา | ตัวคูณ | ความเร็ว | เร็วขึ้นจากขั้นก่อน |
|---:|---:|---:|---:|---:|
| 0 | — | ×1.00 | 32 | — |
| 1 | 10,000 | ×1.90 | 61 | **+90%** |
| 2 | 100,000 | ×2.51 | 80 | +32% |
| 3 | 1,000,000 | ×3.05 | 97 | +21% |
| 4 | 10,000,000 | ×3.54 | 113 | +16% |
| 5 | 100,000,000 | ×4.00 | 128 | +13% |

รวมทั้งสาย **111,110,000 coins**

#### ⚠️⚠️ ทำไม 5 ขั้น ไม่ใช่ 10 — เป็นการตัดสินใจถาวร ห้ามขยาย

ราคาไล่ ×10 ต่อขั้น **ถ้าทำ 10 ขั้น ขั้นสุดท้ายจะแพงกว่าขั้นแรกหนึ่งพันล้านเท่า**
แต่ตัวคูณชนเพดาน ×4 ไปแล้ว จึงให้ความเร็วเพิ่มแค่ 3–4% ต่อขั้น

= ขั้นที่ไม่มีใครซื้อ เป็นตัวเลขหลอกตาในตารางเฉย ๆ
**เป็นความผิดพลาดแบบเดียวกับคอก Lv11–15 ที่ตัดทิ้งไปแล้ว** (ดู `Config.Balance.Pen.MAX_LEVEL`)

5 ขั้นจบที่ 100M ยังคุ้มทุกขั้น และครอบคลุมช่วงเกมพอแล้ว —
ตาราง ข ใน `docs/balance-tables.html` §13 พิสูจน์ว่าขั้น N ซื้อไหวพอดีที่ด่าน N ทุกขั้น

#### ⚠️ ตัวคูณถดถอย: ขั้นที่แก้ปัญหาจริงคือขั้นที่ถูกที่สุด

`CURVE_EXPONENT = 0.75` ทำให้ขั้นแรกให้เยอะสุด (+90%) แล้วค่อย ๆ ลดเหลือ +13%
ซึ่ง**ตรงกับปัญหาที่ต้องแก้พอดี**: ไป-กลับรังบอสด่าน 9 กินรอบบอสจาก 33% → 17% ตั้งแต่ขั้น 1
ขั้น 2 เหลือ 13% (หายเป็นปัญหาแล้ว) · ขั้น 5 เหลือ 8% ซึ่งเป็นการซื้อความสบาย ไม่ใช่การแก้ปัญหา

ถ้าตั้งเป็น 1.0 (เพิ่มเท่ากันทุกขั้น) ขั้นท้าย ๆ ที่แพงกว่าพันเท่าจะคุ้มเท่าขั้นแรกแบบไร้เหตุผล

#### ⚠️ ความหนากำแพงผูกกับความเร็ว — ห้ามแยกจากกัน

ที่ 128 studs/วิ บน 60 fps ตัวละครขยับ **2.13 stud ต่อเฟรม**
กำแพงที่บางกว่านั้นจะถูก "ข้าม" ทั้งชิ้นระหว่างสองเฟรม **โดยไม่มีการชนเกิดขึ้นเลย**

```
ความหนาขั้นต่ำ = ความเร็วสูงสุด ÷ PHYSICS_FPS × THICKNESS_SAFETY
               = 128 ÷ 60 × 2 = 4.27 studs
```

| กำแพง | ก่อน | หลัง |
|---|---:|---:|
| กำแพงกั้นด่าน (`WALL_THICKNESS`) | 5 | 5 (ไม่ต้องแก้) |
| กำแพงข้างเลน (`LANE_WALL_THICKNESS`) | 3.2 | **5** |
| กำแพงใสขอบแมพ (`BOUNDARY_THICKNESS`) | 2 | **5** |
| รั้วคอก (`FENCE_THICKNESS`) | 0.8 | **5** |

`validate()` บังคับทั้งสี่ตัวผ่าน `Config.getMinWallThickness()` —
**ขึ้นความเร็วแล้วลืมเพิ่มความหนาเมื่อไหร่ เซิร์ฟไม่บูต**
แทนที่จะปล่อยให้ผู้เล่นไปเจอเองว่าวิ่งทะลุกำแพงได้

⚠️ กำแพงข้างเลนเคยเขียนเป็น `FENCE_THICKNESS * 4` ใน MapBuilder ซึ่งผูกความหนา
**กำแพงกันตก**ไว้กับความหนา**รั้วประดับ**โดยไม่มีเหตุผลเชิงดีไซน์ — แยกเป็นค่าของตัวเองแล้ว

⚠️ รั้วคอกหนาขึ้นแล้วยื่นเข้าไปในคอกข้างละ 2.5 studs · `PEN_EDGE_MARGIN` = 4
ยังกว้างกว่า `validate()` จึงบังคับ `PEN_EDGE_MARGIN ≥ FENCE_THICKNESS / 2` ไว้ด้วย

#### ⚠️ เพดาน 200 — เกินแล้วแก้ด้วยความหนากำแพงไม่ได้

`SPEED_CEILING = 200` · ต่ำกว่า ~100 ปลอดภัย · 100–200 เริ่มทะลุของบาง · เกิน 200 ทะลุบ่อยจนเล่นไม่ได้
128 อยู่ในโซนกลาง จึงต้องมีกฎความหนาคู่กันเสมอ
เกิน 200 เมื่อไหร่ความหนาที่ต้องใช้จะกินพื้นที่เล่นไปหมด — `validate()` จึงตัดจบที่ตรงนั้น

#### 🔴 สองบ่อเงินไม่ได้แข่งกันจริง — ข้อจำกัดที่ยอมรับแล้ว

```
damage/วินาที = min(อัตราผลิต, อัตราปล่อย) × damage ต่อตัว × ตัวคูณ damage
```

**ความเร็ววิ่งไม่อยู่ในสมการนี้เลย** เพราะลูกเกิดที่แท่นปล่อยต้นเลน ไม่ได้เดินมาจากคอก
จำลองแล้ว (ตาราง ง ใน `balance-tables.html` §13): เลือก "เร่งความเร็วก่อน" **ช้าลง 10–29%**
ที่ด่าน 2–5 และ **เสมอกันเป๊ะ** ที่ด่าน 6–9

→ **"เร่ง damage ก่อน" เป็นคำตอบเดียวเสมอ** ไม่ใช่การเลือก

ที่ยอมรับได้เพราะ **`damageLevel` มีเพดานต่อด่าน (`wallProgress × 8`)** ซื้อครบแล้วเงินที่เหลือ
ไม่มีที่ไปอยู่ดี ความเร็วจึงทำหน้าที่เป็น **บ่อดูดส่วนเกิน** ไม่ใช่ทางเลือกแข่งกับ damage
ลำดับที่ถูกคือ "damage ให้ครบเพดานก่อน แล้วความเร็วดูดที่เหลือ"

⚠️ **ถ้าวันไหนอยากให้เป็นการเลือกจริง** ต้องทำให้ความเร็วมีผลต่อ throughput ของไข่
(เช่น ให้ความเร็วเพิ่มโอกาสคว้าไข่ในรังที่แย่งกัน 6 คน) ซึ่งโมเดลสมดุลตอนนี้มองไม่เห็น
เพราะ `getEggsPerHour()` สมมติว่าไข่แบ่งเท่ากันทุกคน

## 9. ขนาดข้อมูล

### 9.1 ตัวเลขจริง

ลิมิตของ Roblox DataStore คือ **4 MB (4,194,304 bytes) ต่อ 1 key**

⚠️ ตัวเลขข้างล่างวัดด้วย `PlayerData.estimateBytes()` ซึ่ง **ไม่ใช่ตัว encode ตัวเดียวกับที่ Roblox ใช้จริง**
(`HttpService:JSONEncode` เรียกนอก Roblox ไม่ได้) จึงตั้งเพดานของตัวเองไว้ที่ **3 MB** ไม่ใช่ 4 MB
`PlayerData.validate()` วัดเคสเต็มพิกัดแล้วเทียบกับเพดานนั้นทุกครั้งที่เซิร์ฟเวอร์บูต

| สถานการณ์ | ขนาด | % ของลิมิต |
|---|---:|---:|
| ผู้เล่นใหม่ (ยังไม่มีอะไรเลย) | 937 B | **0.02%** |
| ถือไข่ 10 ฟอง | 1,368 B | **0.03%** |
| ถือไข่ 10 ฟอง — **ถ้ายังใช้โครงอาเรย์ยาวคงที่ 10,000 ช่อง** | 61,212 B | 1.46% — เสียฟรี 45 เท่า |
| **เต็มพิกัดทุกช่อง** (คอก 14 + กระเป๋า 100 + กองลูก 2,000 + ไข่ฟัก 50 + **ไข่ถือ 10,000**) | 707,844 B | **16.9%** |

⚠️ **กระเป๋าไข่กลายเป็นส่วนที่กินที่มากที่สุด** — 10,000 ฟอง × ~55 B = ~550 KB
คิดเป็น 78% ของเคสเต็มพิกัด ถ้าวันหนึ่งจะดันเพดานไข่ขึ้นอีก ต้องดูตัวเลขนี้ก่อนตัวอื่น
(ยามใน `PlayerData.validate()` จะจับให้เองถ้าดันจนทะลุ — ทดสอบแล้วว่าจับได้จริงที่ 60,000 ฟอง)

แยกตามส่วน (เคสเต็มพิกัด): กองลูก 76,631 B · แม่ในกระเป๋า 11,749 B · ไข่ฟัก 4,301 B · แม่ในคอก 2,784 B · **ไข่ที่ถืออยู่ 2,113 B** · ความคืบหน้าต่อด่าน 585 B · `summonEnabled` 21 B

ไข่กินที่เพิ่มขึ้น 3,163 B จากรอบก่อน เพราะตอนนี้เก็บไข่ **รายฟองพร้อมน้ำหนัก** (`hatching` +1,050 B · `heldEggs` +2,081 B) — ยังไม่ถึง 0.08% ของลิมิต

**ฟิลด์ที่เพิ่มมารอบนี้แทบไม่กินที่เลย** `stageProgress` เป็นอาเรย์ยาวคงที่ 9 ช่อง แต่ละช่องเก็บแค่ 2 ตัวเลข:

| กรณี | ขนาด `stageProgress` |
|---|---:|
| ปกติ (กำลังตีอยู่ด่านเดียว อีก 8 ช่องเป็น `false`) | 118 B |
| worst case (สมมติทั้ง 9 ช่องมีค่า และเป็นเลข 10 หลักทั้งคู่) | 585 B |

worst case จริงเกิดไม่ได้ เพราะผู้เล่นตีทีละด่านเรียงกัน ด่านที่พังแล้วเซตกลับเป็น `false` ได้ — แต่ถึงเผื่อเต็มทั้ง 9 ช่องก็ยังเป็น **0.014% ของลิมิต**

*(วัดด้วย uid แบบ string `"987654321-42"` ซึ่งกินที่มากกว่าเลขล้วนประมาณ 10 bytes ต่อตัว — ที่แม่ 119 ตัวคือ ~1.4 KB ไม่มีนัยสำคัญ)*

### 9.2 ทำไมถึงปลอดภัยระยะยาว

**จำนวนลูกไม่มีผลต่อขนาดข้อมูลเลย** ลูก 5,000 ตัวกับ 500,000,000,000 ตัวในกองเดียวกันใช้ที่ต่างกันไม่กี่ตัวอักษร ตัวที่โตคือ *จำนวนกอง* ซึ่งถูกจำกัดด้วย (จำนวนแม่ × ประวัติสถานะ) ไม่ใช่ด้วยเวลาที่ผู้เล่นเล่น

การเลือกเก็บลูกเป็นกองจึงไม่ใช่แค่ประหยัดที่ แต่เป็นสิ่งที่**ทำให้เกมนี้เป็นไปได้เลย** ถ้าเก็บลูกรายตัวแบบเดียวกับแม่ ที่ 5 แสนล้านตัวจะกินพื้นที่ระดับเทราไบต์

ปัญหาที่จะมาถึงก่อนขนาดข้อมูล:
1. **UI คลัง** — 2,000 กอง × ปุ่มละ 1 Frame ทำให้เกมกระตุก ต้องทำ virtual scrolling
2. **request budget** — งบเขียน `60 + ผู้เล่น×10` ครั้ง/นาที autosave ทุก 60 วินาทีใช้แค่ 6 ครั้งที่ 6 คน สบาย แต่**ห้ามเซฟทุกครั้งที่ผลิตลูก**

### 9.3 กฎการเซฟของ DataStore ที่ต้องรู้

⚠️ **ข้อแรกคือเหตุผลที่ `hatching` ต้องเป็น array ยาวคงที่ (`Config.Balance.Hatchery.MAX_SLOTS` ช่อง)**

| ห้าม | เกิดอะไรขึ้น |
|---|---|
| table ที่มี key ตัวเลขแบบมีรู เช่น `{[2] = x}` | encode ได้ `{"2": x}` decode กลับได้ key เป็น **string** `"2"` ไม่ใช่ number `2` → `hatching[2]` คืน nil ทั้งที่ข้อมูลไม่ได้หาย |
| table ที่ผสม array กับ string key ในตัวเดียว | SetAsync error |
| `nil` กลางอาเรย์ | อาเรย์ขาด ความยาวเพี้ยน |
| `Vector3` / `Color3` / `Enum` / `Instance` / function | เซฟไม่ได้เลย — **`Config.EggTypes[x].color` เป็น `Color3` ห้ามหลุดลง PlayerData** (มีคอมเมนต์เตือนใน Config แล้ว) |
| `NaN` / `inf` | encode ไม่ผ่าน — ระวังตอนหาร `produced / ratePerSecond` ถ้า rate เป็น 0 |
| จำนวนเต็มเกิน 9,007,199,254,740,992 (2⁵³) | เริ่มปัดเศษเงียบ ๆ — `MAX_CHILDREN_PER_STACK = 1e15` ตั้งไว้ต่ำกว่าเพดานนี้แล้ว |
| key ยาวเกิน 50 ตัวอักษร | error (`validate()` เช็ค `KEY_PREFIX` ให้แล้ว) |

> `children` เป็น dictionary ที่ key มี `|` และ `,` — **ปลอดภัย** เพราะเป็น string key ธรรมดา JSON รับได้หมด

วิธีกัน: เขียน `sanitizeForSave(data)` ตรวจตามกฎนี้แล้วเรียกก่อน `UpdateAsync` ทุกครั้ง ตอน dev ให้ `error()` ไปเลยจะได้เจอตั้งแต่เทสต์

### 9.4 ⚠️ รอบเซฟซ้อนกัน — เคยทำข้อมูลผู้เล่นหายจริง

`UpdateAsync` ของ Roblox **ยืดเวลา** และมีสองช่วงที่ค้าง: ดึงค่าปัจจุบัน แล้วค่อยเขียนกลับ
สิ่งที่ต้องรู้คือ **Roblox แปลงค่าที่ transform คืนมาเป็น JSON ทันทีที่ transform จบ**
อะไรที่แก้หลังจากนั้นจะไม่เข้าไปในรอบเซฟนั้นแล้ว แม้จะเป็นตารางตัวเดียวกันก็ตาม

อาการที่เจอในเกมจริง (แอป Roblox ไม่ใช่ Studio): ฟักไข่ได้แม่ เห็นแม่ในคอกชัด ๆ
รอเกินหนึ่งนาที ออกจากเกม เข้าใหม่ — **แม่หายไป มีไข่น้ำหนักเท่าเดิมเป๊ะกลับมาค้างในสวนฟักแทน**

```
t+60.0  autosave เริ่ม · UpdateAsync ค้างระหว่างยิงข้ามเน็ต   saving[uid] = true
t+60.2  transform ทำงาน → Roblox ตรึง snapshot (ยังไม่ฟัก)
t+60.5  ไข่ฟักเสร็จ → แม่เข้าคอก (อยู่ในหน่วยความจำเท่านั้น)
t+60.6  ผู้เล่นกด Leave → เซฟรอบสุดท้ายเห็น saving[uid] → ไม่ทำอะไรเลย  ← 🔴 บั๊ก
t+60.7  forget() ทิ้งข้อมูลในหน่วยความจำ
t+60.8  autosave เขียน snapshot เก่าลง DataStore
```

**กฎที่ตามมา:** ตัวกัน "เซฟซ้อน" ใช้ได้กับ autosave เท่านั้น
**เซฟรอบสุดท้าย (ตอนผู้เล่นออกเกม / ปิดเซิร์ฟ) ต้องรอรอบก่อนหน้าให้จบแล้วเขียนทับเสมอ ห้ามข้าม**
คุมด้วย `SAVE_WAIT_LIMIT` / `SAVE_WAIT_STEP` ใน `Config.DataStore`

ผลพวงข้อที่สองที่มองข้ามง่าย: เซฟรอบสุดท้ายที่ถูกข้ามไป **ไม่ได้ปลด `sessionLock` ด้วย**
ผู้เล่นจึงเข้าเกมใหม่ไม่ได้จนกว่า lock จะหมดอายุ 5 นาที

⚠️ บั๊กนี้เป็นเรื่อง **จังหวะล้วน ๆ** เทสต์ที่ใช้ store ซึ่งทำงานจบในบรรทัดเดียวจับไม่ได้เลย
`tests/playerdata.spec.luau` จึงมี store ที่ค้างได้ไว้จำลองเคสนี้โดยเฉพาะ

#### บั๊กพี่น้องกัน: ผู้เล่นคนสุดท้ายออก แล้วเซิร์ฟปิดทับเซฟที่ยังไม่จบ

อาการ **เหมือนกันเป๊ะ** แต่คนละสาเหตุ และการแก้ข้อบนไม่ครอบคลุมข้อนี้

```
1. ผู้เล่นคนสุดท้ายกด Leave → PlayerRemoving ยิง → เซฟรอบสุดท้ายค้างใน UpdateAsync
2. Roblox เริ่มปิดเซิร์ฟ → BindToClose ยิง
3. ถึงตอนนี้ Players:GetPlayers() ว่างไปแล้ว           ← 🔴
4. โค้ดเดิมเจอว่างแล้ว return ทันที → เซิร์ฟตายทับเซฟที่ยังวิ่งอยู่
```

**กฎ:** ตอนปิดเซิร์ฟต้องไล่จาก **ข้อมูลที่ยังค้างอยู่ในแคช** (`DataService.pendingOnClose`)
ไม่ใช่รายชื่อผู้เล่นที่ยังอยู่ — คนที่ "ออกไปแล้วแต่เซฟยังไม่จบ" คือคนที่เสี่ยงที่สุดและมองไม่เห็นจากรายชื่อ

## 10. แผนการ migration

### 10.1 กลไก

```
Config.SCHEMA_VERSION = 2     -- เลขปัจจุบันของโค้ดที่กำลังรัน (ประวัติใน §10.4)

MIGRATIONS = { [1] = v1→v2, [2] = v2→v3, ... }
```

ตอนโหลด:

```
data = อ่านจาก DataStore
ถ้า data == nil                → สร้างจาก template (Config.Balance.NewPlayer) จบ
ถ้า data.schemaVersion == nil  → ถือว่าเป็น 1
ถ้า data.schemaVersion > Config.SCHEMA_VERSION → ⚠️ ห้ามเซฟทับ (ดู §10.2)

วนซ้ำ: ตราบใดที่ data.schemaVersion < Config.SCHEMA_VERSION
    data = MIGRATIONS[data.schemaVersion](data)
    data.schemaVersion += 1

เติมฟิลด์ที่ยังขาดจาก template (กัน migration ลืม)
validate: uid ในทีมมีจริงไหม / stack key parse ได้ไหม / charId ยังมีใน Config ไหม /
          จำนวนแม่เกินความจุไหม / ตัวเลขติดลบไหม
```

migration แต่ละตัวต้อง **idempotent** และ **ห้ามพึ่งค่าใน `Config` ปัจจุบัน** — Config เปลี่ยนได้ แต่ migration ต้องให้ผลเดิมเสมอ ถ้าต้องใช้ค่าคงที่ ให้ hard-code ไว้ในตัว migration เอง

### 10.2 กฎเหล็ก

| กฎ | เหตุผล |
|---|---|
| **เพิ่มฟิลด์ = เพิ่ม version + ใส่ default** | ห้ามเพิ่มเงียบ ๆ แล้วหวังว่าโค้ดจะเช็ค nil ครบ |
| **ห้ามลบฟิลด์เก่า ห้ามเปลี่ยนความหมาย** | ไม่ใช้แล้วก็ปล่อยไว้ ราคาไม่กี่ byte ถูกกว่าความเสี่ยง |
| **ห้าม reuse `charId` / `eggId` / `statusId` เดิมกับของใหม่** | ผู้เล่นที่มี `"wukong"` เก่าใน stack key จะกลายเป็นตัวใหม่ทันที |
| **ห้ามลด `nextUid`** | uid ซ้ำ = ทีมชี้ผิดแม่ |
| **`schemaVersion > ปัจจุบัน` → ห้ามเซฟทับ** | เกิดตอน rollback เซิร์ฟเวอร์ ถ้าเซฟทับข้อมูลใหม่หายถาวร ให้เล่นแบบ read-only แล้วแจ้งเตือน |
| **ทดสอบ migration ด้วยข้อมูลจริงก่อน publish** | ทำ key สำรอง `player_<id>_backup_v<n>` ก่อนรัน migration ครั้งแรกของแต่ละคน |

### 10.3 ตัวอย่างสถานการณ์

| อยากทำ | ต้อง migrate ไหม | วิธี |
|---|---|---|
| ปรับตัวคูณคลาส (SS ×5 → ×6) | ❌ ไม่ต้อง | อยู่ใน Config คำนวณตอน runtime |
| ปรับสูตรเงิน / damage / ราคา / HP ด่าน | ❌ ไม่ต้อง | เหมือนกัน |
| ปรับ tier น้ำหนัก / ตารางคลาสของไข่ | ❌ ไม่ต้อง | แม่ที่มีอยู่เก็บน้ำหนักกับ charId เป็นค่าตรง ไม่ได้เก็บ tier |
| เพิ่มตัวละคร / สถานะ / ไข่ชนิดใหม่ | ❌ ไม่ต้อง | ข้อมูลเก่าไม่รู้จักก็ไม่กระทบ |
| เพิ่มฟิลด์ `nickname` ให้แม่ | ✅ ต้อง | v1→v2 เติม `nickname = ""` ให้ทุกตัวทั้งสองอาเรย์ |
| **เปลี่ยนตัวคั่นของ stack key** | ⚠️ อันตรายที่สุด | ต้องอ่านทุก key เก่า parse ด้วยกฎเก่า เขียนใหม่ด้วยกฎใหม่ พลาดตรงไหน = ลูกหายทั้งกอง |
| **เปลี่ยน `CHILD_RATIO`** | ⚠️ อันตราย | key เก็บน้ำหนักแม่ ข้อมูลไม่พัง แต่ลูกเก่าทั้งหมดเปลี่ยนน้ำหนักย้อนหลังทันที |
| **ลบตัวละคร/สถานะออกจาก Config** | ⚠️ อันตราย | key เก่ายังมี id นั้น parse ได้แต่ lookup ไม่เจอ → ตั้ง `enabled = false` แทน อย่าลบ |

### 10.4 ประวัติ migration

| จาก → ไป | Phase | เปลี่ยนอะไร |
|---|---|---|
| v1 → v2 | 3C-1 | เพิ่ม `battleRoster = {}` (ไม่แตะฟิลด์อื่น · ข้อมูลที่มีอยู่แล้วไม่ทับ) |
| v2 → v3 | 4A | เพิ่ม `stageClearBonusGranted` = false 9 ช่อง · **ไม่ย้อนให้รางวัลด่านที่พังไปแล้ว** (§7.12) · มีอยู่แล้วไม่ทับ |

## 11. จุดเสี่ยง

### 🔴 เปลี่ยนทีหลังแล้วเจ็บ

| สิ่งที่ | เจ็บยังไง |
|---|---|
| **รูปแบบ stack key** (ตัวคั่น · กฎเรียง · ใช้ charId + น้ำหนักแม่) | เป็นคีย์ของ dictionary ที่เซฟไปแล้ว เปลี่ยนเมื่อไหร่ = กองลูกของทุกคนอ่านไม่ออก |
| **`charId` / `statusId` / `eggId`** | ฝังอยู่ใน stack key และใน `mothersInPen`/`Bag` ของทุกคน |
| **รูปแบบ `uid`** | ตัดสินแล้วเป็น global `"<UserId>-<n>"` ([§3.2](#32-ทำไม-uid-ต้องเป็น-global)) เปลี่ยนกลับเป็นเลขต่อผู้เล่นทีหลัง = ทีมที่ทุกคนจัดไว้พังหมด |
| **`CHILD_RATIO = 1%`** | ไม่ทำข้อมูลพัง แต่เปลี่ยนน้ำหนักลูกเก่าย้อนหลังทั้งหมด |
| **ฐานเวลาของ `hatchAt` / `lastProducedAt`** | สลับ absolute ↔ relative ทีหลัง = ไข่และการผลิตทั้งหมดคำนวณผิด |
| **แยก `mothersInPen` / `mothersInBag` เป็นสองอาเรย์** | รวมกลับเป็นอาเรย์เดียวทีหลังต้อง migrate ทุกตัว |
| **ชื่อ DataStore + รูปแบบ key** | เปลี่ยนแล้วผู้เล่นเก่าอ่านข้อมูลไม่เจอ = เริ่มใหม่หมด |
| **`wallProgress` เป็นตัวคูณเงิน** | ถ้าวันหนึ่งจะรีเซ็ตด่าน (prestige) ต้องคิดเรื่องเงินด้วย |
| **เก็บลูกเป็นกอง ไม่ใช่รายตัว** | ย้อนกลับไม่ได้ — ข้อมูลรายตัวไม่เคยมีอยู่ตั้งแต่แรก |

### 🟢 เปลี่ยนได้สบาย

ตัวคูณคลาส · สูตร damage/เงิน · ราคาทุกอย่าง · HP ด่าน/บอส · อัตราผลิต · cap 8 ชั่วโมง · tier น้ำหนัก · ตารางคลาสของไข่ · ชื่อไทยทุกอย่าง · **เพิ่ม** ตัวละคร/ไข่/สถานะ/tier ใหม่ · จำนวนโมเดลที่แสดง · UI ทั้งหมด

เพราะทั้งหมดนี้อยู่ใน Config และคำนวณตอน runtime ไม่ได้เซฟลงข้อมูลผู้เล่น

**เพดานใน `Config.Inventory` / `Pen` / `Bag` / `Hatchery`** — **เพิ่ม**ได้อิสระ แต่**ลดต้องระวัง** ผู้เล่นที่เกินเพดานใหม่ต้องมี policy รองรับ

## 12. จุดที่เสี่ยงโดนโกง (exploit)

ทุกข้อในตารางนี้ **ต้องตัดสินที่ server เท่านั้น** client มีหน้าที่ "ขอ" กับ "แสดงผล"

| จุด | ถ้าให้ client ตัดสินจะโดนโกงยังไง | ต้องทำที่ server |
|---|---|---|
| **การแย่งไข่** ⚠️ สำคัญสุด | client ส่ง "ฉันกดค้างครบ 3 วิแล้ว" → exploiter ส่งทันทีทุกครั้งที่ไข่โผล่ ได้ไข่ทุกฟองทุกรอบ | server จับเวลาเอง · เช็คว่าผู้เล่นอยู่ในระยะจริง · เช็คว่าถูกตีระหว่างนั้นไหม · **ไข่ 1 ฟองมีเจ้าของได้คนเดียว** ต้องมี lock กันสองคนได้พร้อมกัน |
| **การสุ่มน้ำหนัก/ตัวละคร** | client สุ่มเองแล้วส่งผล → ได้องค์ยูไล 100,000,000 kg ทุกฟอง | สุ่มที่ server เท่านั้นทุกครั้ง (น้ำหนักตอนบอสวางไข่ · ตัวละครตอนวางไข่ลงสวนฟัก — ดู [§8.5.1](#851-ไข่รายด่าน-และน้ำหนักที่ล็อกตั้งแต่ในรัง)) client ไม่เคยส่งผลสุ่มมาเอง ⚠️ ทั้งสองค่าถูก "สุ่มไว้ล่วงหน้าแล้วเก็บใน state ของ server" ก่อนเห็นผลจริง — ทำได้เพราะเป็น state ฝั่ง server ล้วน (ไม่ใช่ replicated) client อ่านไม่ถึงจนกว่า server จะส่งให้ผ่าน sync/event เอง ไม่ใช่ช่องโหว่ |
| **การผลิตลูก** | client ส่ง "ฉันผลิตได้ 1,000,000 ตัว" | server คำนวณจาก `lastProducedAt` กับ `os.time()` เท่านั้น ไม่รับตัวเลขจาก client |
| **การคำนวณผลรบ** | client ส่ง "ฉันชนะแล้ว" → เปิดด่าน 9 ทันที | server คำนวณ damage รวมจาก `children` จริงที่มีอยู่ แล้วหักกองทัพที่ตายออกจริง |
| **เงิน** | client ส่ง "ให้เงินฉัน 10^15" | server คำนวณจากแม่ในคอกจริง × เวลาที่ผ่านจริง |
| **การซื้อ/อัปเกรด** | client ส่ง "ฉันอัปคอกเป็น Lv15 แล้ว" | server เช็คเงินพอไหม · เลเวลปัจจุบันถูกไหม · หักเงินเอง |
| **การเข้าพื้นที่บอส** | client teleport เข้าด่าน 9 ตั้งแต่เริ่มเกม | server เช็ค `wallProgress` ก่อนอนุญาต และเช็คซ้ำเป็นระยะว่าตำแหน่งผู้เล่นถูกต้อง |
| **การตีบอส** | client ส่ง damage เท่าไหร่ก็ได้ | server คำนวณ damage จาก `weaponLevel` ที่เซฟไว้ + rate limit จำนวนครั้งที่ตีต่อวินาที |
| **การตีกันนอกพื้นที่บอส** | client ตีคนอื่นได้ทุกที่ | server เช็คโซนก่อนรับ damage ทุกครั้ง |
| **ย้ายแม่เข้าคอก** | client ส่ง "ฉันมีแม่ 200 ตัวในคอก" | server เช็คความจุตาม `penLevel` จริง |
| **รางวัลผ่านด่าน** | client แจ้งว่า "ฉันพังด่าน 9 แล้ว ขอไข่" / ยิงซ้ำเอาไข่เพิ่ม | ไม่มี remote ให้ client ขอเลย (`StageClearedNotify` เป็น server → client อย่างเดียว) · server ตัดสินจากด่านที่เพิ่งพังจริงใน tick + ธงกันซ้ำที่เซฟไว้ |
| **ส่งแม่ไปรบ** | client ส่ง uid ของแม่ในคอก / แม่คนอื่น / แม่ที่ lock ไว้ / ส่งเกิน 10 | server รับแค่ `uid` (string) · หาในกระเป๋าของ**คนส่งเอง**เท่านั้น · เช็ค `locked` · เช็คเพดาน roster · เช็คว่ามีด่านที่มี HP ให้ตีจริง · damage ของแม่คำนวณที่ server จาก `weight`/`charId`/`statuses`/`damageLevel` ที่เซฟไว้ |

**กฎที่ใช้ได้กับทุกข้อ:** ทุก RemoteEvent ที่รับค่าจาก client ต้อง validate **ชนิดข้อมูล → ช่วงค่า → สิทธิ์ → สถานะปัจจุบัน** ตามลำดับ และต้องมี rate limit
