# Phase 2 — ออกแบบโครงสร้างข้อมูลผู้เล่น (PlayerData)

> **สถานะ: เอกสารออกแบบ + Config เท่านั้น ยังไม่มีโค้ด DataStore / combat / ระบบผลิตลูก**
> Phase 1 ยังไม่ผ่านการทดสอบใน Studio โครงนี้จึงยังปรับได้
> ทุกข้อใน [§11 สิ่งที่ต้องตัดสินใจ](#11-สิ่งที่ต้องตัดสินใจก่อนเขียนโค้ดจริง) ต้องเคลียร์ก่อนลงมือ

อ้างอิง: `src/shared/Config.lua` (ตารางจริงทั้งหมดอยู่ที่นั่นแล้ว), `CLAUDE.md` (แผนเฟส)

## 1. ภาพรวมกลไก

```
ฟักไข่ ──► ตัวแม่ (มีน้ำหนัก, เก็บรายตัว, โชว์ในฟาร์ม)
              │
              └─► ผลิต "ตัวลูก" อัตโนมัติ  (หนัก 1% ของแม่ + คัดลอกสถานะแม่ ณ เวลาผลิต)
                       │
                       └─► รวมเป็น "กอง" ตามน้ำหนัก+สถานะ (เก็บแค่ count, ไม่โชว์ในฟาร์ม)
                                │
                     จัดทีม ─────┴───── ส่งไปรบ ──► ตัวที่ตาย หายถาวร
```

หลักการที่ยึดทั้งเอกสาร:

| หลักการ | เหตุผล |
|---|---|
| **เซฟเฉพาะสิ่งที่ derive กลับไม่ได้** | สถิติทหาร ชื่อไทย สี อัตราสุ่ม อยู่ใน `Config.lua` เซฟแค่ id/น้ำหนักแล้ว lookup ตอน runtime — บาลานซ์ใหม่ทีหลังไม่ต้อง migrate |
| **เวลาเป็น timestamp สัมบูรณ์** | `os.time()` (Unix UTC) ไม่ใช่ "เหลืออีกกี่วินาที" ทั้งไข่และการผลิตลูกจึงเดินต่อข้ามการออกเกมได้ |
| **id เป็นสัญญาถาวร** | `unitId` / `eggId` / `statusId` ที่เขียนลง DataStore แล้ว เปลี่ยนไม่ได้ตลอดชีวิตโปรเจกต์ |
| **น้ำหนักแม่เป็นจำนวนเต็มเสมอ** | เพราะมันคือส่วนหนึ่งของ stack key ทศนิยมเข้ามาเมื่อไหร่กองแตกทันที (§3) |
| **ทุกฟิลด์มี default** | ผู้เล่นเก่าที่ไม่มีฟิลด์ใหม่ต้องอ่านได้เสมอ |

## 2. โครงสร้าง PlayerData

```lua
PlayerData = {
    schemaVersion = 1,                    -- number

    currency = {
        coins = 500,                      -- number (integer)
        gems  = 0,                        -- number (integer)
    },

    -- ══ ตัวแม่ ══ array เรียงต่อเนื่อง 1..n เก็บรายตัวเพราะแต่ละตัวมีสถานะของตัวเอง
    mothers = {
        {
            uid            = 1,                  -- number   ไม่ซ้ำภายในผู้เล่นคนนี้ ห้าม reuse
            weight         = 1500,               -- number   kg จำนวนเต็ม สุ่มตอนฟัก
            statuses       = { "gold" },         -- {string} เรียงยังไงก็ได้ตอนเก็บ (makeStackKey เรียงให้เอง)
            lastProducedAt = 1757740000,         -- number   os.time() ที่ผลิตลูกครั้งล่าสุด (settle แล้ว)
            obtainedAt     = 1757700000,         -- number   os.time() ตอนฟักออกมา
            locked         = false,              -- boolean  กันเผลอส่งไปรบ/ขาย
        },
        -- ...
    },
    nextUid = 2,                          -- number  ตัวนับ uid ตัวถัดไป ห้ามรีเซ็ต ห้ามลด

    -- ══ ตัวลูก ══ dictionary: stack key → จำนวน (ดู §3)
    children = {
        ["1500|gold"]        = 4820,      -- [stackKey] = count (number)
        ["1500|gold,silver"] = 96,
        ["300|"]             = 12,
    },

    -- ══ ไข่ที่กำลังฟัก ══
    -- ⚠️ ต้องเป็น array ยาวคงที่ = Config.Farm.EGG_SLOTS_PER_PLAYER (เหตุผลใน §6.3)
    hatching = {
        { eggId = "egg_rare", startedAt = 1757740000, hatchAt = 1757740120 },
        false,                            -- ช่องว่างใช้ false ห้ามใช้ nil
        false,
        false,
    },

    -- ══ ไข่ที่ซื้อไว้ยังไม่วาง ══ dictionary ก็พอ เพราะไข่ไม่มีสถานะรายฟอง
    heldEggs = {
        egg_common = 12,                  -- [eggId] = จำนวน (number)
        egg_rare   = 3,
    },

    -- ══ ทีมสำหรับรบ ══ เลือกได้ทั้งแม่และลูก
    teams = {
        {
            name        = "ทีมหลัก",       -- string   ต้องผ่าน TextService:FilterStringAsync
            motherUids  = { 1, 5 },        -- {number} ชี้ mothers[].uid
            childStacks = {                -- [stackKey] = จำนวนที่ส่งไป (ไม่ใช่ทั้งกอง)
                ["1500|gold"] = 200,
            },
        },
    },
    activeTeam = 1,                       -- number  index ใน teams

    stats = {
        eggsHatched       = 0,            -- number
        eggsHatchedByType = { egg_common = 0 },   -- [eggId] = จำนวน
        childrenProduced  = 0,            -- number  ลูกที่ผลิตได้สะสมทั้งหมด
        battlesWon        = 0,            -- number  Phase 3
        battlesLost       = 0,            -- number  Phase 3
        mothersLost       = 0,            -- number  แม่ที่ตายในการรบสะสม
        childrenLost      = 0,            -- number  ลูกที่ตายในการรบสะสม
        heaviestMother    = 0,            -- number  น้ำหนักแม่ที่หนักที่สุดที่เคยได้ (ไว้อวด/leaderboard)
        totalCoinsEarned  = 0,            -- number  Phase 4
        firstJoinAt       = 1750000000,   -- number  os.time() ครั้งแรกที่เข้าเกม
        lastSeenAt        = 1757740000,   -- number  os.time() ครั้งล่าสุดที่เซฟ (ใช้บอกว่าออฟไลน์ไปนานแค่ไหน)
        playTimeSeconds   = 0,            -- number
    },
}
```

### 2.1 อธิบายรายฟิลด์

#### ระดับบนสุด

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `schemaVersion` | number | **สำคัญที่สุด** บอกว่าข้อมูลก้อนนี้เขียนด้วยโครงเวอร์ชันไหน ไม่มีตัวนี้ = วันที่ต้องเปลี่ยนโครงจะแยกข้อมูลเก่า/ใหม่ไม่ออก แล้วต้องเดา = ข้อมูลผู้เล่นพัง ดู §9 |
| `currency` | table | เป็น table ตั้งแต่แรกแทน number เดี่ยว เกมแนวนี้เกือบทุกเกมจบที่ 2 สกุล เพิ่มทีหลังเป็น migration ที่เลี่ยงได้ฟรี |
| `mothers` | array | ตัวแม่ ดู §2.2 |
| `nextUid` | number | ต้องเซฟ ไม่งั้นโหลดใหม่แล้วเริ่มนับ 1 ใหม่ → uid ชนกัน → ทีมชี้ผิดตัว |
| `children` | dictionary | กองลูก ดู §3 |
| `hatching` | array | ไข่ที่กำลังฟัก |
| `heldEggs` | dictionary | ไข่ในกระเป๋า |
| `teams` | array | ทีมที่จัดไว้ |
| `activeTeam` | number | ทีมที่จะถูกส่งไปรบ |
| `stats` | table | ตัวเลขสะสม ใช้ทำ achievement / leaderboard / daily ใน Phase 4-5 ต้องเก็บตั้งแต่ตอนนี้เพราะย้อนเก็บไม่ได้ |

#### `mothers[i]` — ตัวแม่ 1 ตัว

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `uid` | number | ทีมและ UI ใช้ชี้ "แม่ตัวนี้" ต้องไม่ซ้ำและ **ห้าม reuse** แม้ตัวเดิมจะตายไปแล้ว ไม่งั้นทีมที่บันทึกไว้จะไปชี้แม่ตัวใหม่ที่บังเอิญได้เลขเดิม |
| `weight` | number | kg **จำนวนเต็มเสมอ** สุ่มตอนฟักด้วย `Config.rollMotherWeight` เป็นทั้งตัวกำหนด damage และเป็นส่วนหนึ่งของ stack key ของลูก |
| `statuses` | {string} | สถานะที่ติดอยู่ *ตอนนี้* อ้าง `Config.Statuses` ลำดับในอาเรย์ไม่สำคัญ เพราะ `makeStackKey` เรียงให้เองก่อนใช้ |
| `lastProducedAt` | number | `os.time()` ของจุดที่ settle การผลิตไปถึงแล้ว **ไม่ใช่** "เวลาที่ผลิตตัวล่าสุด" — ต่างกันตรงที่มันเก็บเศษเวลาไว้ด้วย ดู §4.2 |
| `obtainedAt` | number | เรียง "ใหม่สุด" ใน UI และเป็นหลักฐานตอนดีบั๊ก |
| `locked` | boolean | แม่ตายถาวร ล็อกไว้กันเผลอลากเข้าทีม เป็นฟีเจอร์ที่เพิ่มทีหลังแล้วต้อง migrate ใส่ไว้เลยถูกกว่า |

#### `hatching[i]` — ไข่ที่กำลังฟัก

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `eggId` | string | อ้าง `Config.EggTypes` |
| `startedAt` | number | `os.time()` ตอนวาง ใช้คิด progress bar |
| `hatchAt` | number | `os.time()` ที่ครบกำหนด = `startedAt + hatchTime` |

**ทำไมเก็บ `hatchAt` ทั้งที่คำนวณจาก `hatchTime` ได้:** ถ้าเก็บแต่ `startedAt` แล้ววันหนึ่งไปแก้ `hatchTime` ใน Config ไข่ที่ผู้เล่นวางค้างไว้จะเปลี่ยนเวลาฟักกลางคัน (ยาวขึ้นได้ด้วย) การเก็บ `hatchAt` ตรึงสัญญาที่ให้ไว้ตอนวาง ส่วน `startedAt` ทำให้ progress bar ยังถูกแม้สูตรเปลี่ยน

#### `teams[i]`

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `name` | string | **ต้อง sanitize + ผ่าน `TextService:FilterStringAsync`** ก่อนเซฟ ไม่งั้นเป็นช่องทางคำหยาบ |
| `motherUids` | {number} | เก็บ `uid` **ไม่ใช่** น้ำหนัก เพราะต้องชี้แม่ตัวเจาะจง (แม่คนละตัวน้ำหนักเท่ากันได้) |
| `childStacks` | dict | `[stackKey] = จำนวนที่ส่งไปรบ` ส่งไปบางส่วนของกองได้ ไม่ต้องส่งทั้งกอง |

> **ต้อง validate ตอนโหลดเสมอ:** uid ใน `motherUids` ที่หาไม่เจอใน `mothers` ให้ตัดทิ้งเงียบ ๆ และ `childStacks` ที่จำนวนเกินกองจริง ให้หั่นลงมาเท่าที่มี (เกิดได้ถ้าแม่ตายไปแล้ว หรือ migration พลาด)

## 3. Stack key — หัวใจของระบบกองลูก

### 3.1 รูปแบบ

```
"<น้ำหนักแม่><FIELD_SEPARATOR><สถานะที่เรียงแล้ว คั่นด้วย STATUS_SEPARATOR>"
```

| กรณี | key |
|---|---|
| แม่ 1,500 kg ไม่มีสถานะ | `"1500\|"` |
| แม่ 1,500 kg มี gold | `"1500\|gold"` |
| แม่ 1,500 kg มี gold + silver | `"1500\|gold,silver"` |
| แม่ 100,000,000 kg มี gold | `"100000000\|gold"` |

ตัวคั่นอยู่ใน `Config.Stack` ห้าม hard-code ที่อื่น
สร้าง/แยก key ด้วย `Config.makeStackKey()` / `Config.parseStackKey()` **เท่านั้น**

### 3.2 กฎ 3 ข้อที่ห้ามพลาด

**1. ใช้น้ำหนัก "แม่" ไม่ใช่น้ำหนัก "ลูก"**

ลูกหนัก 1% ของแม่ ซึ่งเป็นทศนิยมได้ (แม่ 999 kg → ลูก 9.99 kg) ถ้าเอา 9.99 ไปทำ key จะเจอปัญหา float: โค้ดคนละที่อาจได้ `9.99` กับ `9.990000000000001` → กลายเป็นคนละกองโดยไม่มีใครรู้ตัว

น้ำหนักแม่เป็นจำนวนเต็มเสมอ (`Config.rollMotherWeight` คืน `NextInteger`) จึงเป็น identity ที่ปลอดภัย น้ำหนักลูกคำนวณกลับได้เมื่อไหร่ก็ได้ด้วย `Config.getChildWeight()`

**2. เรียงสถานะก่อนเสมอ**

`{gold, silver}` กับ `{silver, gold}` คือชุดสถานะเดียวกัน ต้องได้ key เดียวกัน
`makeStackKey` เรียกใช้ `table.sort` ทุกครั้ง — เรียงตามลำดับ byte ของ ASCII ซึ่งคงที่ ไม่ขึ้นกับ locale
นี่คือเหตุผลที่ `Config.validate()` บังคับว่า status id ต้องเป็น `^[a-z][a-z0-9_]*$`

**3. ตัดสถานะซ้ำก่อนเรียง**

`{gold, gold}` ต้องได้ key เดียวกับ `{gold}` ไม่งั้นบั๊กที่เผลอใส่สถานะซ้ำจะสร้างกองผี

> ทั้ง 3 ข้อนี้ถูกทดสอบด้วยชุดเทสต์แล้ว รวมถึงเคส `{silver,gold}` ต้องได้ key เดียวกับ `{gold,silver}`

### 3.3 ทำไมกองลูกไม่ต้องเก็บ `statuses` แยกอีกชุด

เพราะ **key คือ identity ทั้งหมดของกองอยู่แล้ว** ถ้าเก็บซ้ำเป็น

```lua
children = { ["1500|gold"] = { weight = 15, statuses = {"gold"}, count = 4820 } }   -- ❌ อย่าทำ
```

จะได้ปัญหา 3 อย่างฟรี ๆ:

1. **ข้อมูลขัดกันเองได้** — วันหนึ่งจะมีบั๊กที่ key บอก `gold` แต่ฟิลด์ข้างในบอก `silver` แล้วไม่มีใครรู้ว่าอันไหนถูก
2. **เปลืองที่ 5-6 เท่า** — `["1500|gold"]=4820` ใช้ ~19 bytes ส่วนแบบ table ใช้ ~100 bytes (ที่ 500 กองคือ 9.5 KB vs 50 KB)
3. **ต้องเขียน validate เพิ่ม** เพื่อกันข้อ 1 ซึ่งเป็นงานที่ไม่ต้องมีตั้งแต่แรก

ค่าของ dictionary จึงเป็น **number ล้วน ๆ** คือจำนวนตัวในกอง อยากได้น้ำหนัก/สถานะกลับมาก็ `parseStackKey` เอา

## 4. การผลิตลูก

### 4.1 อัตรา

| | อัตรา | ที่มา |
|---|---|---|
| ออนไลน์ | 1 ตัว/นาที ต่อแม่ 1 ตัว | `Config.Production.ONLINE_PER_MINUTE` |
| ออฟไลน์ | 0.1 ตัว/นาที (ช้ากว่า 10 เท่า) | `Config.Production.OFFLINE_PER_MINUTE` |
| เพดานออฟไลน์ | 8 ชั่วโมง | `Config.Production.OFFLINE_CAP_SECONDS` |

**ออฟไลน์เต็มเพดานได้ 48 ตัวต่อแม่ 1 ตัว** (8 ชม × 60 นาที × 0.1)
ผู้เล่นที่มีแม่ 10 ตัวออกไป 3 วัน กลับมาได้ 480 ตัว ไม่ใช่ 4,320 ตัว

### 4.2 วิธี settle (ใช้สูตรเดียวกันทั้งออนไลน์และออฟไลน์)

```
ต่อแม่ 1 ตัว:
    ratePerSecond = (ออนไลน์ ? ONLINE_PER_MINUTE : OFFLINE_PER_MINUTE) / 60

    windowStart = max(mother.lastProducedAt, now - OFFLINE_CAP_SECONDS)   ← เพดานอยู่ตรงนี้
    elapsed     = max(0, now - windowStart)
    produced    = floor(elapsed * ratePerSecond)
    produced    = min(produced, MAX_PER_SETTLE)                            ← กันนาฬิกากระโดด

    ถ้า produced > 0:
        key = Config.makeStackKey(mother.weight, mother.statuses)
        children[key] = (children[key] or 0) + produced
        mother.lastProducedAt = windowStart + produced / ratePerSecond     ← ไม่ใช่ now
```

**บรรทัดสุดท้ายคือจุดที่พลาดกันบ่อยที่สุด** ถ้าเซ็ต `lastProducedAt = now` เศษเวลาที่ยังไม่ครบ 1 ตัวจะถูกทิ้งทุกรอบ ตอนออนไลน์ที่ tick ทุก 5 วินาที (ผลิตได้รอบละ 0.083 ตัว) ผู้เล่นจะไม่ได้ลูกเลยสักตัว การเลื่อนไปเท่าที่ "ใช้จริง" ทำให้เศษสะสมข้ามรอบได้โดยไม่ต้องมีฟิลด์ accumulator แยก

### 4.3 ลำดับตอนผู้เล่นล็อกอินกลับ (ห้ามสลับ)

```
1. โหลด PlayerData + migrate + validate
2. เคลียร์ไข่ที่ฟักครบระหว่างออฟไลน์   ← สร้างแม่ใหม่ ตั้ง lastProducedAt = hatchAt
3. settle การผลิตออฟไลน์ของแม่ทุกตัว   ← แม่ที่เพิ่งเกิดในข้อ 2 ก็ผลิตด้วย
4. ตั้ง lastSeenAt = now แล้วเริ่ม tick ออนไลน์
```

**ถ้าสลับข้อ 2 กับ 3** แม่ที่ฟักออกมาตอนชั่วโมงที่ 1 ของการออฟไลน์ 8 ชั่วโมง จะไม่ผลิตอะไรเลยทั้งที่ควรได้ 42 ตัว

สูตร `windowStart = max(lastProducedAt, now - cap)` จัดการเคสนี้ให้เองอยู่แล้ว เพราะแม่ที่เพิ่งเกิดมี `lastProducedAt = hatchAt` ซึ่งใหม่กว่า `now - cap`

### 4.4 ตอน logout / autosave

```
1. settle การผลิตออนไลน์จนถึง now
2. lastSeenAt = now
3. เซฟ
```

ทำข้อ 1 ก่อนเสมอ ไม่งั้นเวลาที่เล่นอยู่ช่วงท้ายจะถูกนับเป็นออฟไลน์ (ช้ากว่า 10 เท่า) = ผู้เล่นเสียเปรียบ

## 5. สถานะ (Status)

### 5.1 กฎพื้นฐาน

- สถานะติดที่ **ตัวแม่เท่านั้น** ลูกไม่มีสถานะเป็นของตัวเอง
- ลูกที่ผลิตออกมา **คัดลอกชุดสถานะของแม่ ณ เวลาที่ผลิต** (snapshot ไม่ใช่ reference)
- แม่ 1 ตัวติดได้หลายสถานะพร้อมกัน
- Phase 1-3 ยังไม่มีสถานะจริง (`Config.Statuses` มี `gold` / `silver` แต่ `enabled = false`) — schema รองรับไว้แล้ว

### 5.2 กฎที่สำคัญที่สุด: แม่ได้สถานะเพิ่มทีหลัง

> **ลูกที่ผลิตไปแล้ว "ไม่" อัปเดตย้อนหลัง**

```
วันที่ 1   แม่ #7 หนัก 1,500 kg ไม่มีสถานะ
          ผลิตลูก 500 ตัว  →  children["1500|"] = 500

วันที่ 3   แม่ #7 ได้สถานะ gold
          ผลิตลูกต่อ 300 ตัว →  children["1500|"]     = 500   ← กองเดิม ไม่เปลี่ยน
                               children["1500|gold"] = 300   ← กองใหม่

วันที่ 5   แม่ #7 ได้สถานะ silver เพิ่ม
          ผลิตลูกต่อ 200 ตัว →  children["1500|"]            = 500
                               children["1500|gold"]        = 300
                               children["1500|gold,silver"] = 200   ← กองที่สาม
```

**ผลลัพธ์: แม่ตัวเดียวมีลูกกระจายอยู่หลายกองได้ตามประวัติสถานะของมัน**
นี่คือพฤติกรรมที่ตั้งใจ ไม่ใช่บั๊ก — ลูกที่ผลิตตอนแม่ยังไม่มีบัฟ ก็ไม่ควรได้บัฟย้อนหลัง

ผลข้างเคียงที่ต้องระวัง: จำนวนกองต่อผู้เล่นโตตาม **(จำนวนแม่ × จำนวนชุดสถานะที่แม่แต่ละตัวเคยผ่าน)** ไม่ใช่แค่จำนวนแม่ จึงต้องมี `Config.Inventory.MAX_CHILD_STACKS` (ดู §11 ข้อ 6 ว่าเต็มแล้วทำยังไง)

### 5.3 การประนีประนอมเรื่องผลผลิตออฟไลน์

ตอนคำนวณผลผลิตออฟไลน์ ให้ใช้ชุดสถานะ **ปัจจุบัน** ของแม่ แล้วยกให้เป็นกองเดียว

ข้อสังเกตที่ควรรู้ไว้: **ตามดีไซน์ตอนนี้ การประนีประนอมนี้ยังไม่มีผลจริง** เพราะสถานะเปลี่ยนได้เฉพาะตอนผู้เล่นออนไลน์ (จะติดสถานะให้แม่ต้องกดเอง) พอออฟไลน์ ชุดสถานะจึงคงที่ตลอดช่วงนั้น = "สถานะปัจจุบัน" กับ "สถานะตอน logout" เป็นค่าเดียวกัน

กฎข้อนี้จะเริ่มมีผลจริงในวันที่สถานะกลายเป็นของที่เปลี่ยนเองได้ระหว่างออฟไลน์ เช่น

- บัฟมีอายุ (`gold` หมดอายุใน 2 ชั่วโมง)
- daily reward ที่ติดสถานะให้อัตโนมัติ

วันนั้นการคำนวณที่ถูกต้องจริง ๆ ต้องแบ่งช่วงเวลาออฟไลน์เป็นท่อน ๆ ตามประวัติสถานะ ซึ่งซับซ้อนกว่ามาก **เรายอมรับความคลาดเคลื่อนตรงนี้** แลกกับความง่าย และให้เอียงไปทางที่ผู้เล่นได้เปรียบเสมอเมื่อต้องเลือก

## 6. ขนาดข้อมูล

### 6.1 ตัวเลขจริง

ลิมิตของ Roblox DataStore คือ **4 MB (4,194,304 bytes) ต่อ 1 key**

วัดด้วยการ JSON-encode โครงสร้างตาม §2:

| ส่วน | ขนาด | ต่อหน่วย | ชน 4 MB ที่ |
|---|---:|---:|---:|
| `mothers` (array รายตัว) | 50 ตัว = 5,590 B | ~114 B | ~36,700 ตัว |
| `children` (dict stack→count) | 200 กอง = 3,799 B | ~19 B | ~220,000 กอง |

| สถานการณ์ | ขนาดรวม | % ของลิมิต |
|---|---:|---:|
| **แม่ 50 + กองลูก 200** (ตามโจทย์) | **10,077 B** | **0.24%** |
| แม่ 200 + กองลูก 2,000 (เพดาน Config ปัจจุบัน ×4) | 61,061 B | 1.46% |

### 6.2 สรุป: ไม่ใช่ปัญหา และจะไม่เป็นปัญหา

แม่ 50 ตัว + กองลูก 200 กอง ใช้พื้นที่ **ไม่ถึงหนึ่งในสี่ของหนึ่งเปอร์เซ็นต์** ต่อให้ชนเพดานที่ตั้งไว้ใน Config (แม่ 200 / กอง 500) ก็ยังไม่ถึง 1%

เหตุผลเชิงโครงสร้างที่ทำให้ปลอดภัยระยะยาว: **จำนวนลูกไม่มีผลต่อขนาดข้อมูลเลย** ลูก 5,000 ตัวกับ 5,000,000 ตัวในกองเดียวกันใช้ที่ต่างกันแค่ 3 ตัวอักษร ตัวที่โตคือ *จำนวนกอง* ซึ่งถูกจำกัดด้วย (จำนวนแม่ × ประวัติสถานะ) ไม่ใช่ด้วยเวลาที่ผู้เล่นเล่น

การเลือกเก็บลูกเป็น dictionary จึงไม่ใช่แค่ประหยัดที่ แต่เป็นสิ่งที่ทำให้ **เกมแนวสะสมตัวเลขใหญ่เป็นไปได้เลย** ถ้าเก็บลูกรายตัวแบบเดียวกับแม่ ที่ 5 ล้านตัวจะกิน ~375 MB = เกินลิมิตไป 90 เท่า

ปัญหาที่จะมาถึงก่อนขนาดข้อมูล:

1. **UI คลัง** — 500 กอง × ปุ่มละ 1 Frame ทำให้เกมกระตุก ต้องทำ virtual scrolling ตั้งแต่หลักร้อย
2. **request budget** — งบเขียน `60 + ผู้เล่น×10` ครั้ง/นาที autosave ทุก 60 วินาทีใช้แค่ 6 ครั้งที่ 6 คน สบายมาก แต่**ห้ามเซฟทุกครั้งที่ผลิตลูก**
3. **จำนวนกองบานปลาย** ถ้าสถานะมีหลายแบบ (§5.2)

### 6.3 กฎการเซฟของ DataStore ที่ต้องรู้ (พลาดกันบ่อย)

⚠️ **ข้อแรกคือเหตุผลที่ `hatching` ต้องเป็น array ยาวคงที่**

| ห้าม | เกิดอะไรขึ้น |
|---|---|
| table ที่มี key ตัวเลขแบบมีรู เช่น `{[2] = x}` | encode ได้ `{"2": x}` decode กลับได้ key เป็น **string** `"2"` ไม่ใช่ number `2` → `hatching[2]` คืน nil ทั้งที่ข้อมูลไม่ได้หาย |
| table ที่ผสม array กับ string key ในตัวเดียว | SetAsync error |
| `nil` กลางอาเรย์ | อาเรย์ขาด ความยาวเพี้ยน |
| `Vector3` / `Color3` / `Enum` / `Instance` / function | เซฟไม่ได้เลย — **`Config.EggTypes[x].color` เป็น `Color3` ห้ามหลุดลง PlayerData เด็ดขาด** (มีคอมเมนต์เตือนไว้ใน Config แล้ว) |
| `NaN` / `inf` | encode ไม่ผ่าน — ระวังตอนหาร `produced / ratePerSecond` ถ้า rate เป็น 0 |
| key ยาวเกิน 50 ตัวอักษร | error (`validate()` เช็ค `KEY_PREFIX` ให้แล้ว) |

> `children` เป็น dictionary ที่ key มี `|` และ `,` — **ปลอดภัย** เพราะเป็น string key ธรรมดา JSON รับได้หมด

วิธีกัน: เขียน `sanitizeForSave(data)` ตรวจตามกฎนี้แล้วเรียกก่อน `UpdateAsync` ทุกครั้ง ตอน dev ให้ `error()` ไปเลยจะได้เจอตั้งแต่เทสต์

## 7. สูตรพลังโจมตี — เลือก 1 จาก 3

ทุกสูตรตั้งให้ **แม่ 100 kg = 10 damage** เท่ากัน จะได้เทียบความชันกันตรง ๆ
ค่าคงที่ทั้งหมดอยู่ใน `Config.Damage.FORMULAS` แล้ว รอแค่ใส่ `ACTIVE_FORMULA`

### 7.1 damage ของตัวแม่

| น้ำหนักแม่ (kg) | A · รากที่สอง `w^0.5` | B · รากที่สาม `w^(1/3)` | C · ลอการิทึม `log10` |
|---:|---:|---:|---:|
| 100 | 10.0 | 10.0 | 10.0 |
| 1,000 | 31.6 | 21.5 | 20.0 |
| 10,000 | 100.0 | 46.4 | 30.0 |
| 100,000 | 316.2 | 100.0 | 40.0 |
| 1,000,000 | 1,000.0 | 215.4 | 50.0 |
| 10,000,000 | 3,162.3 | 464.2 | 60.0 |
| 100,000,000 | 10,000.0 | 1,000.0 | 70.0 |
| **แรงสุด ÷ อ่อนสุด** | **1,000×** | **100×** | **7×** |

### 7.2 damage ของตัวลูก (หนัก 1% ของแม่)

| แม่ (kg) | ลูก (kg) | A ลูก | %แม่ | B ลูก | %แม่ | C ลูก | %แม่ |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 1.00 | 1.0 | 10% | 2.2 | 22% | **−10.0** | — |
| 1,000 | 10.00 | 3.2 | 10% | 4.6 | 22% | **0.0** | — |
| 10,000 | 100.00 | 10.0 | 10% | 10.0 | 22% | 10.0 | 33% |
| 1,000,000 | 10,000.00 | 100.0 | 10% | 46.4 | 22% | 30.0 | 60% |
| 100,000,000 | 1,000,000.00 | 1,000.0 | 10% | 215.4 | 22% | 50.0 | 71% |

### 7.3 สิ่งที่ควรรู้ก่อนเลือก

| | A · รากที่สอง | B · รากที่สาม | C · ลอการิทึม |
|---|---|---|---|
| ช่วงพลังทั้งเกม | 1,000× | 100× | 7× |
| ลูกแรงกี่ % ของแม่ | 10% คงที่ทุกน้ำหนัก | 22% คงที่ทุกน้ำหนัก | ผันแปร 0–71% |
| แม่ตัวหายากคุ้มไหม | คุ้มมาก | คุ้มปานกลาง | **แทบไม่คุ้ม** — แม่ 1 ในล้านแรงกว่าแม่ทั่วไปแค่ 7 เท่า |
| กองลูกล้านตัวจะพังเกมไหม | เสี่ยง — ลูกถูกและแรง 10% | เสี่ยงกว่า — ลูกแรงถึง 22% | เสี่ยงน้อยสุด |
| ⚠️ ปัญหาเฉพาะตัว | — | — | **ให้ค่าติดลบ** กับตัวที่เบากว่า 100 kg ต้องพึ่ง `minDamage` เป็นพื้นบังคับ ซึ่งแปลว่าลูกของแม่ตัวเล็กทุกขนาดจะแรงเท่ากันหมด (= 1) |

**ผมไม่เลือกให้ตามที่สั่ง** แต่ขอชี้ข้อเท็จจริงที่มีผลต่อการตัดสินใจ: สูตร C ทำให้ระบบสุ่มน้ำหนัก 7 ชั้นที่ออกแบบมาแทบไม่มีความหมาย (แม่ 1 ในล้านแรงกว่าแม่ธรรมดาแค่ 7 เท่า) ถ้าจะเลือก C ควรพิจารณาปรับ `baseDamage` / `referenceWeight` ให้ช่วงกว้างขึ้นด้วย

> ทั้งสามสูตรปรับได้ผ่าน `baseDamage` และ `referenceWeight` ใน Config โดยไม่ต้องแตะโค้ด

## 8. การรบ (บันทึกไว้ให้ Phase 3)

- จัดทีมเลือกได้ทั้ง **แม่** และ **ลูก**
- **ตัวที่ตายหายถาวร ทั้งแม่และลูก** — แม่ตาย = เสียเครื่องผลิตถาวร
- UI ต้องแยกเป็น **สองแถบ**: แถบแม่ (รายตัว) / แถบลูก (รายกอง + จำนวน)
- **เลือกแม่เข้าทีมต้องมีกล่องยืนยัน** เตือนชัดว่าถ้าแม่ตายจะเสียเครื่องผลิตถาวร
- `Config.Inventory.MAX_TEAM_MOTHERS = 3` จำกัดความเสียหายต่อหนึ่งตา
- `locked = true` ควรกันไม่ให้แม่ตัวนั้นถูกเลือกเข้าทีมเลย

ผลต่อ schema: ตอนแม่ตายต้อง **ลบออกจาก `mothers`** และ **ไม่ reuse uid** ส่วนลูกที่ตายให้หักออกจาก `children[key]` และลบ key ทิ้งเมื่อเหลือ 0 (กันกองผีสะสม)

## 9. แผนการ migration

### 9.1 กลไก

```
Config.SCHEMA_VERSION = 1     -- เลขปัจจุบันของโค้ดที่กำลังรัน (อยู่ใน Config แล้ว)

MIGRATIONS = {
    [1] = ฟังก์ชันแปลง v1 → v2,
    [2] = ฟังก์ชันแปลง v2 → v3,
}
```

ตอนโหลด:

```
data = อ่านจาก DataStore
ถ้า data == nil                → สร้างจาก template ของเวอร์ชันปัจจุบัน (Config.NewPlayer) จบ
ถ้า data.schemaVersion == nil  → ถือว่าเป็น 1
ถ้า data.schemaVersion > Config.SCHEMA_VERSION → ⚠️ ห้ามเซฟทับ (ดู §9.2)

วนซ้ำ: ตราบใดที่ data.schemaVersion < Config.SCHEMA_VERSION
    data = MIGRATIONS[data.schemaVersion](data)
    data.schemaVersion += 1

เติมฟิลด์ที่ยังขาดจาก template (กัน migration ลืม)
validate: uid ในทีมมีจริงไหม / stack key parse ได้ไหม / ตัวเลขติดลบไหม / eggId ยังมีใน Config ไหม
```

migration แต่ละตัวต้อง **idempotent** และ **ห้ามพึ่งค่าใน `Config` ปัจจุบัน** — Config เปลี่ยนได้ แต่ migration ต้องให้ผลเดิมเสมอ ถ้าต้องใช้ค่าคงที่ ให้ hard-code ไว้ในตัว migration เอง

### 9.2 กฎเหล็ก

| กฎ | เหตุผล |
|---|---|
| **เพิ่มฟิลด์ = เพิ่ม version + ใส่ default** | ห้ามเพิ่มเงียบ ๆ แล้วหวังว่าโค้ดจะเช็ค nil ครบ |
| **ห้ามลบฟิลด์เก่า ห้ามเปลี่ยนความหมาย** | ไม่ใช้แล้วก็ปล่อยไว้ ราคาไม่กี่ byte ถูกกว่าความเสี่ยง อยากเปลี่ยนความหมาย = สร้างฟิลด์ใหม่ |
| **ห้าม reuse `unitId` / `eggId` / `statusId` เดิมกับของใหม่** | ผู้เล่นที่มี `"gold"` เก่าอยู่ใน stack key จะกลายเป็นของใหม่ทันที |
| **ห้ามลด `nextUid`** | uid ซ้ำ = ทีมชี้ผิดแม่ |
| **`schemaVersion > ปัจจุบัน` → ห้ามเซฟทับ** | เกิดตอน rollback เซิร์ฟเวอร์ ถ้าเซฟทับข้อมูลใหม่หายถาวร ให้เล่นแบบ read-only แล้วแจ้งเตือน |
| **ทดสอบ migration ด้วยข้อมูลจริงก่อน publish** | ทำ key สำรอง `player_<id>_backup_v<n>` ก่อนรัน migration ครั้งแรกของแต่ละคน |

### 9.3 ตัวอย่างสถานการณ์

| อยากทำ | ต้อง migrate ไหม | วิธี |
|---|---|---|
| ปรับ `hatchTime` / `price` / `weight` ในตารางสุ่ม | ❌ ไม่ต้อง | อยู่ใน Config ไม่ได้เซฟ |
| ปรับอัตราผลิตลูก | ❌ ไม่ต้อง | เหมือนกัน (ผลมีทันทีในการ settle ครั้งถัดไป) |
| เปลี่ยนสูตร damage | ❌ ไม่ต้อง | คำนวณตอน runtime |
| ปรับ tier น้ำหนัก / เพิ่ม tier | ❌ ไม่ต้อง | แม่ที่มีอยู่แล้วเก็บน้ำหนักไว้เป็นตัวเลข ไม่ได้เก็บ tier |
| เพิ่มสถานะชนิดใหม่ | ❌ ไม่ต้อง | เพิ่มใน `Config.Statuses` พอ key เก่าไม่กระทบ |
| เพิ่มฟิลด์ `nickname` ให้แม่ | ✅ ต้อง | v1→v2 เติม `nickname = ""` ให้ทุกตัวใน `mothers` |
| **เปลี่ยนตัวคั่นของ stack key** | ⚠️ อันตรายมาก | ต้องอ่านทุก key เก่า parse ด้วยกฎเก่า แล้วเขียนใหม่ด้วยกฎใหม่ พลาดตรงไหน = ลูกหายทั้งกอง |
| **เปลี่ยน `CHILD_RATIO`** | ⚠️ อันตราย | key เก็บน้ำหนักแม่ ไม่ใช่ลูก ดังนั้นข้อมูลไม่พัง แต่ลูกเก่าทั้งหมดจะ "เปลี่ยนน้ำหนัก" ย้อนหลังทันที ต้องตัดสินใจว่ายอมรับได้ไหม |
| **ลบสถานะออกจาก Config** | ⚠️ อันตราย | key เก่ายังมี id นั้นอยู่ parse ได้แต่ lookup ไม่เจอ → ตั้ง `enabled = false` แทน อย่าลบ |

### 🔴 เปลี่ยนทีหลังแล้วเจ็บ — ต้องคิดให้จบก่อนเขียนโค้ด

| สิ่งที่ | เจ็บยังไง |
|---|---|
| **รูปแบบ stack key** (ตัวคั่น, กฎเรียง, ใช้น้ำหนักแม่) | เป็นคีย์ของ dictionary ที่เซฟไปแล้ว เปลี่ยนเมื่อไหร่ = กองลูกของทุกคนอ่านไม่ออก ต้อง migrate ทุก key |

## 12. ⚠️ ข้อขัดแย้งที่ต้องเคลียร์: `UnitTypes` กับระบบน้ำหนัก

**ผมไม่ได้ลบหรือแก้ `Config.UnitTypes` ในรอบนี้** เพราะเป็นโครงหลักและกลไกใหม่ไม่ได้ระบุชัดว่าจะให้ทำยังไงกับมัน แต่ต้องชี้ให้เห็นว่ามันทับซ้อนกันอยู่:

| | ระบบเดิม (Phase 1 ที่เขียนไปแล้ว) | กลไกใหม่ |
|---|---|---|
| ฟักไข่แล้วได้อะไร | ทหาร 1 ตัวจาก `hatchTable` (recruit / archer / ...) | แม่ 1 ตัวที่มีน้ำหนักสุ่มจาก tier |
| อะไรกำหนดความแรง | `UnitTypes[id].damage` | น้ำหนัก ผ่านสูตรถดถอย |
| อะไรกำหนดความหายาก | `rarity` + `weight` ใน `hatchTable` | tier น้ำหนัก |

ทางเลือกที่เป็นไปได้ (**ต้องให้คุณเลือก**):

**ตัวเลือก ก — เลิกใช้ `UnitTypes` ทั้งหมด**
แม่มีแค่ น้ำหนัก + สถานะ ไม่มีสายพันธุ์ ตรงกับกลไกใหม่ที่สุด
`hatchTable` / `UnitTypes` / `rarity` ตั้ง `enabled = false` แล้วปล่อยตายไป
→ *ผลข้างเคียง:* ไข่ 3 ชนิดจะต่างกันแค่ราคาและเวลาฟัก ต้องออกแบบใหม่ว่าไข่แพงให้อะไรมากกว่า (เช่น ไข่แต่ละชนิดมีตาราง tier ของตัวเอง)

**ตัวเลือก ข — เก็บทั้งคู่**
แม่มีทั้ง `unitId` (สายพันธุ์ กำหนดหน้าตา/ชื่อ) และ `weight` (กำหนดความแรง)
→ *ผลข้างเคียง:* stack key ต้องเพิ่ม `unitId` เข้าไปด้วย → `"recruit|1500|gold"` และจำนวนกองจะคูณด้วยจำนวนสายพันธุ์

**ตัวเลือก ค — `UnitTypes` กลายเป็นแค่ skin**
สายพันธุ์กำหนดหน้าตาอย่างเดียว ไม่มีผลต่อ damage เลย และ **ไม่เข้า stack key** (ลูกทุกสายพันธุ์ที่น้ำหนักเท่ากันรวมกองกันได้)
→ *ผลข้างเคียง:* ต้องยอมรับว่าลูกในกองเดียวกันอาจมาจากแม่คนละสายพันธุ์ ซึ่งอาจดูแปลกตอนแสดงผล

> **ยังไม่ตัดสินใจข้อนี้ไม่ได้** เพราะมันกำหนดรูปแบบ stack key ซึ่งเป็นสิ่งที่เปลี่ยนทีหลังแล้วเจ็บที่สุดในเอกสารนี้ (§10)
