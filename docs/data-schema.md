# Phase 2 — ออกแบบโครงสร้างข้อมูลผู้เล่น (PlayerData)

> **สถานะ: เอกสารออกแบบ ยังไม่ได้เขียนโค้ด**
> Phase 1 ยังไม่ผ่านการทดสอบใน Studio โครงนี้จึงยังปรับได้ทั้งหมด
> ทุกข้อใน [§8 สิ่งที่ต้องยืนยัน](#8-สิ่งที่ต้องยืนยันก่อนลงมือเขียนโค้ด) ต้องเคลียร์ก่อนลงมือ

อ้างอิงของที่มีอยู่แล้ว: `src/shared/Config.lua` (ตารางไข่/ทหาร), `src/server/EggService.lua` (state ใน memory ตอนนี้)

---

## 1. ภาพรวม

ผู้เล่น 1 คน = 1 key ใน DataStore = 1 table เดียว

```
DataStore ชื่อ  "PlayerData_v1"
key            "player_<UserId>"      เช่น "player_1234567"
value          table PlayerData ตาม §2
```

หลักการที่ยึดทั้งเอกสาร:

| หลักการ | เหตุผล |
|---|---|
| **เซฟเฉพาะสิ่งที่ derive กลับไม่ได้** | `hp`/`damage`/`speed`/`ชื่อไทย`/`สี` อยู่ใน `Config.lua` อยู่แล้ว เซฟแค่ `unitId` แล้ว lookup ตอน runtime — บาลานซ์ใหม่ทีหลังผู้เล่นเก่าได้ค่าใหม่ทันที ไม่ต้อง migrate |
| **เก็บเวลาเป็น timestamp สัมบูรณ์** | `os.time()` (Unix UTC) ไม่ใช่ "เหลืออีกกี่วินาที" ไข่จึงเดินต่อได้ข้ามการออกเกม/ข้ามเซิร์ฟเวอร์ |
| **id เป็นสัญญาถาวร** | `unitId` / `eggId` ที่เขียนลง DataStore แล้ว = เปลี่ยนไม่ได้ตลอดชีวิตโปรเจกต์ |
| **ทุกฟิลด์มี default** | ผู้เล่นเก่าที่ไม่มีฟิลด์ใหม่ต้องอ่านได้เสมอ ห้ามให้ `nil` ทำให้โค้ดพัง |

## 2. โครงสร้าง PlayerData

```lua
PlayerData = {
    schemaVersion = 1,                    -- number

    currency = {
        coins = 0,                        -- number (integer)
        gems  = 0,                        -- number (integer)
    },

    -- คลังทหาร: array เรียงต่อเนื่อง 1..n (ดูเหตุผลที่เลือกแบบนี้ใน §4)
    inventory = {
        {
            uid        = 1,               -- number  เลขประจำตัว ไม่ซ้ำ "ภายในผู้เล่นคนนี้"
            unitId     = "recruit",       -- string  อ้าง Config.UnitTypes
            level      = 1,               -- number  Phase 4
            star       = 1,               -- number  Phase 4
            obtainedAt = 1757740000,      -- number  os.time() ตอนได้มา
            locked     = false,           -- boolean กันเผลอขาย/ทิ้ง
        },
        -- ...
    },
    nextUid = 2,                          -- number  ตัวนับ uid ตัวถัดไป ห้ามรีเซ็ต

    -- ไข่ที่กำลังฟักอยู่ในฟาร์ม
    -- ⚠️ ต้องเป็น array ยาวคงที่ = Config.Farm.EGG_SLOTS_PER_PLAYER (เหตุผลใน §3.2)
    hatching = {
        { eggId = "egg_rare", startedAt = 1757740000, hatchAt = 1757740120 },
        false,                            -- ช่องว่างใช้ false ห้ามใช้ nil
        false,
        false,
    },

    -- ไข่ที่ซื้อไว้แต่ยังไม่ได้วาง — dictionary ก็พอ เพราะไข่ไม่มีสถานะรายฟอง
    heldEggs = {
        egg_common    = 12,               -- [eggId] = จำนวน (number)
        egg_rare      = 3,
    },

    -- ทีมที่จัดไว้ เก็บเป็น uid ไม่ใช่ unitId (ต้องชี้ทหาร "ตัวนั้น" ที่อัปเลเวลไว้)
    teams = {
        { name = "ทีมหลัก", members = { 1, 5, 9 } },
    },
    activeTeam = 1,                       -- number  index ใน teams

    stats = {
        eggsHatched       = 0,            -- number
        eggsHatchedByType = { egg_common = 0 },   -- [eggId] = จำนวน
        unitsByRarity     = { Common = 0 },       -- [Rarity] = จำนวนที่เคยได้สะสม
        battlesWon        = 0,            -- number  Phase 3
        battlesLost       = 0,            -- number  Phase 3
        totalCoinsEarned  = 0,            -- number  Phase 4
        firstJoinAt       = 1750000000,   -- number  os.time() ครั้งแรกที่เข้าเกม
        lastSeenAt        = 1757740000,   -- number  os.time() ครั้งล่าสุดที่เซฟ
        playTimeSeconds   = 0,            -- number  เวลาเล่นสะสม
    },
}
```

### 2.1 อธิบายรายฟิลด์

#### ระดับบนสุด

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `schemaVersion` | number | **สำคัญที่สุด** บอกว่าข้อมูลก้อนนี้เขียนด้วยโครงเวอร์ชันไหน ถ้าไม่มีตัวนี้ วันที่ต้องเปลี่ยนโครงจะแยกไม่ออกว่าข้อมูลเก่าหรือใหม่ แล้วต้องเดา ซึ่งแปลว่าข้อมูลผู้เล่นพัง ดู §5 |
| `currency` | table | ทำเป็น table ตั้งแต่แรกแทน number เดี่ยว เพราะเกมแนวนี้เกือบทุกเกมจบที่ 2 สกุล (soft/hard) การเพิ่มทีหลังเป็น migration ที่เลี่ยงได้ฟรี |
| `inventory` | array | คลังทหาร ดู §2.2 |
| `nextUid` | number | ตัวนับ uid ต้องเซฟด้วย ไม่งั้นโหลดใหม่แล้วเริ่มนับ 1 ใหม่ → uid ชนกัน → ทีมชี้ผิดตัว |
| `hatching` | array | ไข่ที่กำลังฟัก ดู §2.3 |
| `heldEggs` | dictionary | ไข่ในกระเป๋าที่ยังไม่วาง |
| `teams` | array | ทีมที่จัดไว้ |
| `activeTeam` | number | ทีมที่จะถูกส่งไปรบใน Phase 3 |
| `stats` | table | ตัวเลขสะสม ใช้ทำ achievement/leaderboard/daily ใน Phase 4-5 เก็บตั้งแต่ตอนนี้เพราะย้อนเก็บไม่ได้ |

#### `inventory[i]` — ทหาร 1 ตัว

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `uid` | number | เลขประจำตัวที่ทีมและ UI ใช้ชี้ "ทหารตัวนี้" ต้องไม่ซ้ำและ**ห้าม reuse** แม้ตัวเดิมถูกขายไปแล้ว ไม่งั้นทีมที่บันทึกไว้จะไปชี้ทหารตัวใหม่ที่บังเอิญได้เลขเดิม |
| `unitId` | string | ชี้เข้า `Config.UnitTypes` ค่าสถิติจริงไป lookup เอาตอน runtime ไม่เซฟ |
| `level` | number | Phase 4 อัปเกรดรายตัว ใส่ไว้ตั้งแต่ v1 ด้วยค่า 1 จะได้ไม่ต้อง migrate ตอน Phase 4 |
| `star` | number | เช่นเดียวกัน เผื่อระบบรวมตัวซ้ำเพิ่มดาว |
| `obtainedAt` | number | ใช้เรียง "ใหม่สุด" ใน UI คลัง และเป็นหลักฐานตอนดีบั๊ก — แต่กินที่ ~24 bytes/ตัว ดู §3.1 ถ้าจะตัดออกต้องตัดตั้งแต่ v1 |
| `locked` | boolean | กันผู้เล่นเผลอขายตัวหายาก เป็นฟีเจอร์มาตรฐานที่เพิ่มทีหลังแล้วต้อง migrate ใส่ไว้เลยถูกกว่า |

#### `hatching[i]` — ไข่ที่กำลังฟัก 1 ฟอง

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `eggId` | string | ชี้เข้า `Config.EggTypes` |
| `startedAt` | number | `os.time()` ตอนวาง ใช้คำนวณ progress bar และไว้ตรวจสอบย้อนหลัง |
| `hatchAt` | number | `os.time()` ที่ครบกำหนด = `startedAt + Config.EggTypes[eggId].hatchTime` |

**ทำไมเก็บทั้งสองค่าทั้งที่คำนวณจาก `hatchTime` ได้:** ถ้าเก็บแต่ `startedAt` แล้ววันหนึ่งไปแก้ `hatchTime` ใน Config ไข่ที่ผู้เล่นวางค้างไว้จะเปลี่ยนเวลาฟักกลางคัน (ยาวขึ้นได้ด้วย) การเก็บ `hatchAt` ตรึงสัญญาที่ให้ไว้ตอนวาง ส่วน `startedAt` ทำให้ progress bar ยังถูกแม้สูตรเปลี่ยน

**ทำไมไม่เก็บ "เหลืออีกกี่วินาที":** ค่านั้นถูกแค่ ณ วินาทีที่เซฟ พอผู้เล่นออกไป 3 ชั่วโมงแล้วกลับมา ค่าเดิมยังเท่าเดิม = เวลาไม่เดิน ต้องเขียน logic หักเวลาออฟไลน์เองซึ่งพลาดง่าย timestamp สัมบูรณ์แก้ปัญหานี้ฟรี

> **หมายเหตุขัดกับโค้ด Phase 1:** ตอนนี้ `EggService.lua` ใช้ `os.clock()` ซึ่งเป็นนาฬิกา monotonic ที่**รีเซ็ตทุกครั้งที่เซิร์ฟเวอร์ใหม่** เซฟลง DataStore ไม่ได้ Phase 2 ต้องเปลี่ยนฐานเวลาเป็น `os.time()` ทั้งระบบ (ความละเอียด 1 วินาที ซึ่งพอดีกับ `SYNC_INTERVAL = 1` อยู่แล้ว)

#### `teams[i]`

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `name` | string | ผู้เล่นตั้งชื่อทีมเองได้ — **ต้อง sanitize + ผ่าน `TextService:FilterStringAsync`** ก่อนเซฟ ไม่งั้นเป็นช่องทางคำหยาบ |
| `members` | array of number | เก็บ `uid` **ไม่ใช่** `unitId` เพราะทีมต้องชี้ทหารตัวที่อัปเลเวลไว้ ไม่ใช่ชนิด |

> ต้องมีขั้น **validate ตอนโหลด**: uid ใน `members` ที่หาไม่เจอใน `inventory` ให้ตัดทิ้งเงียบ ๆ (เกิดได้ถ้า migration พลาดหรือทหารถูกลบ)

## 3. ข้อควรระวังเรื่องขนาดข้อมูล

### 3.1 ตัวเลขจริง

ลิมิตของ Roblox DataStore คือ **4 MB (4,194,304 bytes) ต่อ 1 key**

ผลจากการวัดจริง (JSON encode, ทหารสุ่มจาก 6 ชนิดใน Config ปัจจุบัน):

| รูปแบบ inventory | 500 ตัว | 5,000 ตัว | ต่อตัว | ชน 4 MB ที่ |
|---|---:|---:|---:|---:|
| array ฟิลด์ยาว + `obtainedAt` (**แบบที่เสนอ**) | 36,887 B | 375,028 B | ~75 B | ~55,800 ตัว |
| array ฟิลด์ยาว ตัด `obtainedAt` | 25,057 B | 254,942 B | ~51 B | ~82,100 ตัว |
| array ฟิลด์สั้น (`u`,`i`,`lv`) + timestamp | 25,359 B | 259,564 B | ~52 B | ~80,600 ตัว |
| dictionary `{unitId = count}` | 80 B | 86 B | ~0 B | ไม่มีวันชน |

**PlayerData ทั้งก้อนที่ทหาร 500 ตัว ≈ 37 KB = 0.89% ของลิมิต** (ส่วนที่ไม่ใช่ inventory รวมกันแค่ ~477 bytes)

### 3.2 สรุป: 500 ตัวไม่ใช่ปัญหาเลย

500 ตัวใช้พื้นที่ไม่ถึง 1% ต่อให้ผู้เล่นสะสมถึง **10,000 ตัว** ก็ยังใช้แค่ ~18% ปัญหาที่จะมาถึงก่อนขนาดข้อมูลคือ:

1. **UI คลัง** — render 500 ปุ่มพร้อมกันทำให้เกมกระตุก ต้องทำ virtual scrolling หรือแบ่งหน้าตั้งแต่หลักร้อย
2. **เวลา JSONEncode/Decode** — ทุกครั้งที่ autosave ต้อง serialize ทั้งก้อน ที่หลักหมื่นตัวจะเริ่มเห็นใน microprofiler
3. **request budget** — งบเขียนคือ `60 + จำนวนผู้เล่น × 10` ครั้งต่อนาที ที่ 6 คนได้ 120 ครั้ง/นาที การ autosave ทุก 60 วินาทีใช้แค่ 6 ครั้ง สบายมาก แต่**อย่าเซฟทุกครั้งที่ไข่ฟัก** เพราะฟัก 4 ช่อง × 6 คนพร้อมกันจะกินงบทันที

### 3.3 ถ้าวันหนึ่งใหญ่เกินจริง

ทำตามลำดับนี้ (จากเจ็บน้อยไปเจ็บมาก):

1. **ใส่ลิมิตจำนวนทหาร** — `MAX_UNITS` เช่น 1,000 ตัว เต็มแล้วห้ามฟักเพิ่มจนกว่าจะขาย/รวม วิธีนี้แก้ปัญหาที่ต้นเหตุและทำได้ตั้งแต่วันแรก **แนะนำให้ทำอันนี้**
2. **ตัดฟิลด์ที่ไม่จำเป็น** — ตัด `obtainedAt` ประหยัด 32% ทันที (แต่เสีย UI "เรียงตามใหม่สุด")
3. **ย่อชื่อฟิลด์** — `unitId`→`u` ประหยัด ~31% แต่ข้อมูลอ่านด้วยตาไม่รู้เรื่อง ดีบั๊กยากขึ้นมาก **ไม่คุ้มถ้ายังไม่จำเป็น**
4. **แยก key** — `player_<id>_profile` กับ `player_<id>_inventory` ได้พื้นที่ 2 เท่าแต่เสีย atomicity: เซฟสำเร็จอันเดียวแล้วเซิร์ฟเวอร์ crash = ข้อมูลไม่ตรงกัน ต้องทำ reconciliation ซึ่งซับซ้อนมาก
5. **hybrid** — ทหารที่ยัง `level == 1 and star == 1 and not locked` ยุบเป็น `{unitId = count}` ส่วนที่อัปแล้วเก็บรายตัว ประหยัดสุดแต่โค้ดซับซ้อนที่สุด (ต้อง "แตก" ตัวออกมาจาก count ตอนผู้เล่นจะอัปเกรด)

### 3.4 กฎการเซฟของ DataStore ที่ต้องรู้ (พลาดกันบ่อย)

⚠️ **ข้อนี้เป็นเหตุผลที่ `hatching` ต้องเป็น array ยาวคงที่**

| ห้าม | เกิดอะไรขึ้น |
|---|---|
| table ที่มี key ตัวเลขแบบมีรู เช่น `{[2] = x}` | ตอน encode กลายเป็น `{"2": x}` ตอน decode ได้ key เป็น **string** `"2"` ไม่ใช่ number `2` → `data.hatching[2]` คืน nil ทั้งที่ข้อมูลไม่ได้หาย |
| table ที่ผสม array กับ string key ในตัวเดียว | encode ไม่ผ่าน SetAsync error |
| `nil` กลางอาเรย์ | อาเรย์ขาดตรงนั้น ความยาวเพี้ยน |
| `Vector3` / `Color3` / `Enum` / `Instance` / function | เซฟไม่ได้เลย — **สำคัญ:** `Config.EggTypes[x].color` เป็น `Color3` ห้ามหลุดลง DataStore เด็ดขาด |
| `NaN` / `inf` | encode ไม่ผ่าน |
| ข้อความยาวเกิน / key ยาวเกิน 50 ตัวอักษร | error |

วิธีกัน: เขียนฟังก์ชัน `sanitizeForSave(data)` ที่ตรวจตามกฎนี้ แล้วเรียกก่อน `UpdateAsync` ทุกครั้ง ตอน dev ให้ `error()` ไปเลยจะได้เจอตั้งแต่เทสต์

## 4. Trade-off: inventory จะเก็บแบบไหน

### แบบ A — dictionary `{ [unitId] = จำนวน }`

```lua
inventory = { recruit = 152, archer = 33, dragon_rider = 1 }
```

| ข้อดี | ข้อเสีย |
|---|---|
| เล็กมาก 80 bytes ไม่ว่าจะมีกี่ตัว | **อัปเกรดทหารรายตัวไม่ได้เลย** — level/star จะเป็นของ "ทั้งชนิด" ไม่ใช่ของตัวใดตัวหนึ่ง |
| ไม่ต้องจัดการ uid ไม่มีทางชนกัน | จัดทีมชี้ "ตัวนั้น" ไม่ได้ ทำได้แค่ "เอาพลธนู 3 ตัว" |
| เพิ่มทหาร = `+= 1` โค้ดสั้นมาก | ไม่รู้ว่าตัวไหนได้มาเมื่อไหร่ เรียง "ใหม่สุด" ไม่ได้ |
| lookup O(1) | ล็อกกันขายรายตัวไม่ได้ |
| ไม่มีวันชนลิมิต DataStore | ตั้งชื่อเล่น / ใส่ skin รายตัวไม่ได้ |

### แบบ B — array ของทหารรายตัวที่มี uid

```lua
inventory = { { uid = 1, unitId = "recruit", level = 3, star = 2, ... }, ... }
```

| ข้อดี | ข้อเสีย |
|---|---|
| **รองรับ level/star/skin รายตัว** ตรงกับ Phase 4 | ใหญ่กว่า ~75 bytes/ตัว (แต่ 500 ตัว = 0.89% ของลิมิต) |
| ทีมชี้ทหารตัวเจาะจงได้ด้วย uid | ต้องจัดการ `nextUid` ให้ไม่ซ้ำและไม่ reuse |
| เรียง/กรอง/ค้นได้ทุกแบบ | ค้นด้วย uid เป็น O(n) ถ้าไม่ทำ index (แก้ได้ด้วย map ใน memory) |
| ล็อกกันขาย ตั้งชื่อเล่นได้ | ลบตัวกลางอาเรย์ต้อง `table.remove` ระวังอย่าให้เกิดรู |
| ดีบั๊กง่าย เห็นประวัติรายตัว | โค้ดยาวกว่า |

### ✅ ข้อเสนอ: เลือก **แบบ B (array + uid)**

เหตุผลเรียงตามน้ำหนัก:

1. **แผนเฟสบังคับไว้แล้ว** — CLAUDE.md เขียนว่า Phase 4 มี "อัปเกรดทหาร" ถ้าอัปเกรดเป็นรายตัว แบบ A ทำไม่ได้เลย ไม่ใช่ทำยาก แต่ทำไม่ได้
2. **Phase 2 เองก็ต้องการ** — "จัดทีม" ในเฟสนี้ ถ้าจัดด้วย unitId เฉย ๆ พอ Phase 4 มาอัปเกรดรายตัว ทีมที่ผู้เล่นจัดไว้จะชี้ผิดตัวทันที
3. **ต้นทุนที่จ่ายคือแค่ขนาด ซึ่งวัดแล้วว่าไม่เป็นปัญหา** — 500 ตัว = 0.89% ของลิมิต
4. **ย้าย A → B ทีหลังคือ migration ที่ข้อมูลหาย** — แตก count 152 ออกเป็น 152 ตัวได้ แต่ `obtainedAt` ของแต่ละตัวหายถาวร เดาไม่ได้ ส่วนย้าย B → A ทำได้ง่ายถ้าวันหนึ่งอยากยุบ (แค่นับ)

> **ทางลง (asymmetric risk):** เลือก B แล้วผิด → ยุบเป็น A ได้ทุกเมื่อ เลือก A แล้วผิด → แตกกลับเป็น B ไม่ได้ครบ เลือกทางที่ถอยได้

### ทำไม `heldEggs` ถึงใช้ dictionary ได้ (แต่ทหารใช้ไม่ได้)

เพราะ**ไข่ไม่มีสถานะรายฟอง** ไข่ธรรมดาฟองที่ 1 กับฟองที่ 50 เหมือนกันทุกประการ ไม่มีอะไรให้แยก
วันไหนที่ไข่มีสถานะรายฟอง (เช่น "ไข่ที่บัฟไว้แล้ว") ต้องย้ายมาเป็น array แบบเดียวกับทหาร

## 5. แผนการ migration

### 5.1 กลไก

```
Config.SCHEMA_VERSION = 1     -- ตัวเลขปัจจุบันของโค้ดที่กำลังรัน

MIGRATIONS = {
    [1] = ฟังก์ชันที่แปลง v1 → v2,
    [2] = ฟังก์ชันที่แปลง v2 → v3,
    ...
}
```

ตอนโหลด:

```
data = อ่านจาก DataStore
ถ้า data == nil        → สร้างจาก template ของเวอร์ชันปัจจุบัน จบ
ถ้า data.schemaVersion == nil → ถือว่าเป็น 1
วนซ้ำ: ตราบใดที่ data.schemaVersion < Config.SCHEMA_VERSION
    data = MIGRATIONS[data.schemaVersion](data)
    data.schemaVersion += 1
เติมฟิลด์ที่ยังขาดจาก template (กันกรณี migration ลืม)
validate (uid ในทีมมีจริงไหม, ตัวเลขติดลบไหม, eggId ยังมีใน Config ไหม)
```

migration แต่ละตัวต้อง **idempotent** และห้ามพึ่งค่าใน `Config` ปัจจุบัน (Config เปลี่ยนได้ แต่ migration ต้องให้ผลเดิมเสมอ) — ถ้าต้องใช้ค่าคงที่ ให้ hard-code ค่านั้นไว้ในตัว migration เอง

### 5.2 กฎเหล็ก

| กฎ | เหตุผล |
|---|---|
| **เพิ่มฟิลด์ = เพิ่ม version + ใส่ default** | ห้ามเพิ่มฟิลด์เงียบ ๆ แล้วหวังว่าโค้ดจะเช็ค nil ครบ |
| **ห้ามลบฟิลด์เก่า ห้ามเปลี่ยนความหมาย** | ถ้าไม่ใช้แล้วก็ปล่อยไว้เฉย ๆ ราคาแค่ไม่กี่ byte ถูกกว่าความเสี่ยงมาก อยากเปลี่ยนความหมาย = สร้างฟิลด์ใหม่ |
| **ห้าม reuse `unitId` / `eggId` เดิมกับของใหม่** | ผู้เล่นที่มี `"archer"` เก่าอยู่ในคลังจะกลายเป็นของใหม่ทันที |
| **ห้ามลด `nextUid`** | uid ซ้ำ = ทีมชี้ผิดตัว |
| **`schemaVersion > ปัจจุบัน` → ห้ามเซฟทับ** | เกิดตอน rollback เซิร์ฟเวอร์: ผู้เล่นที่เล่นเวอร์ชันใหม่มาแล้วเจอเซิร์ฟเวอร์เก่า ถ้าเซฟทับข้อมูลใหม่หายถาวร ให้เล่นแบบ read-only แล้วแจ้งเตือน |
| **ทดสอบ migration ด้วยข้อมูลจริงก่อน publish** | ทำ key สำรอง `player_<id>_backup_v<n>` ก่อนรัน migration ครั้งแรกของแต่ละคน |

### 5.3 ตัวอย่างสถานการณ์

| อยากทำ | ต้อง migrate ไหม | วิธี |
|---|---|---|
| ปรับ `hp` ของอัศวินจาก 260 → 300 | ❌ ไม่ต้อง | ค่าอยู่ใน Config ไม่ได้เซฟ แก้แล้วมีผลทันทีทุกคน |
| ปรับ `weight` ในตารางสุ่ม | ❌ ไม่ต้อง | เหมือนกัน |
| เพิ่มทหารชนิดที่ 7 | ❌ ไม่ต้อง | เพิ่มใน Config พอ ข้อมูลเก่าไม่กระทบ |
| เพิ่มฟิลด์ `nickname` ให้ทหาร | ✅ ต้อง | v1→v2 เติม `nickname = ""` ให้ทุกตัวใน inventory |
| เปลี่ยน `currency` จาก number เป็น table | ✅ ต้อง | (เลี่ยงได้แล้วเพราะออกแบบเป็น table ตั้งแต่ v1) |
| **ลบทหารชนิดหนึ่งออกจาก Config** | ⚠️ อันตราย | ผู้เล่นที่มีตัวนั้นอยู่จะ lookup ไม่เจอ → ต้อง migrate แปลงเป็นชนิดอื่น หรือเก็บ `Config.RetiredUnits` ไว้ให้ lookup ได้ **แนะนำ: อย่าลบ ตั้ง `enabled = false` แทน** |

## 6. จุดเสี่ยง

### 🔴 เปลี่ยนทีหลังแล้วเจ็บ — ต้องคิดให้จบก่อนเขียนโค้ด

| สิ่งที่ | เจ็บยังไง |
|---|---|
| **`unitId` / `eggId`** (`"recruit"`, `"egg_common"`, ...) | ฝังอยู่ในข้อมูลผู้เล่นทุกคน เปลี่ยนชื่อ = ทหารในคลังหายหมด แก้ได้แค่ด้วย migration ที่ต้องเขียนถูก 100% |
| **inventory เป็น array vs dictionary** (§4) | ย้ายจาก dictionary กลับมา array ทำให้ `obtainedAt` รายตัวหายถาวร |
| **`uid` ต่อผู้เล่น vs global** | ถ้าวันหนึ่งจะทำเทรดทหารระหว่างผู้เล่น uid ที่ไม่ซ้ำแค่ในคนเดียวจะชนกันทันที → **ถ้าคิดจะมีเทรด ต้องตัดสินใจตอนนี้** |
| **ฐานเวลาของ `hatchAt`** | สลับระหว่าง absolute/relative ทีหลัง = ไข่ทุกฟองที่ค้างอยู่คำนวณผิด |
| **ชื่อ DataStore + รูปแบบ key** | เปลี่ยนแล้วผู้เล่นเก่าอ่านข้อมูลไม่เจอ = เริ่มใหม่หมด |
| **โครง `teams.members` เก็บ uid vs unitId** | เปลี่ยนแล้วทีมที่ทุกคนจัดไว้พังหมด |
| **`schemaVersion` — ถ้าไม่ใส่ตั้งแต่แรก** | ไม่มีทางแยกข้อมูลเก่า/ใหม่ได้เลย migration ครั้งแรกจะเป็นการเดา |

### 🟢 เปลี่ยนได้สบาย — ไม่ต้องกังวล

| สิ่งที่ | ทำไมปลอดภัย |
|---|---|
| `hp` / `damage` / `speed` ของทหาร | อยู่ใน Config อย่างเดียว lookup ตอน runtime ไม่ได้เซฟ |
| `hatchTime` / `price` / `weight` ในตารางสุ่ม | เหมือนกัน (ไข่ที่ค้างอยู่ก็ปลอดภัยเพราะตรึง `hatchAt` ไว้แล้ว) |
| ชื่อไทย / สีไข่ | แสดงผลล้วน ๆ |
| **เพิ่ม**ทหาร/ไข่ชนิดใหม่ | ข้อมูลเก่าไม่รู้จักก็ไม่กระทบ |
| `MAX_PLOTS` / `EGG_SLOTS_PER_PLAYER` | *เพิ่ม*ได้อิสระ — แต่ **ลดต้องระวัง**: ผู้เล่นที่มีไข่ในช่อง 4 อยู่ ถ้าลดเหลือ 3 ช่องไข่ฟองนั้นต้องมี logic คืนเข้า `heldEggs` |
| UI ทุกอย่าง | ไม่แตะข้อมูลที่เซฟ |
| ชื่อ RemoteEvent | เจ็บแค่ตอน deploy ไม่พร้อมกัน ไม่กระทบข้อมูลที่เซฟไว้ |

## ภาคผนวก — ที่มาของตัวเลขใน §3

วัดด้วยการ JSON-encode โครงสร้างตาม §2 โดยสุ่ม `unitId` จาก 6 ชนิดใน `Config.lua` ปัจจุบัน
เทียบ 500 ตัวกับ 5,000 ตัวเพื่อหาค่าต่อตัวแบบไม่รวม overhead ของฟิลด์อื่น
ลิมิตที่ใช้คือ 4 MB = 4,194,304 bytes ต่อ key ตามสเปก Roblox DataStore

ตัวเลขนี้เป็นการประมาณ — Roblox serialize ด้วย encoder ของตัวเอง ขนาดจริงอาจต่างเล็กน้อย
แต่ที่ระดับ 0.89% ของลิมิต ความคลาดเคลื่อนไม่มีผลต่อข้อสรุป
