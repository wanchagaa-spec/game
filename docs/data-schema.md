## 1. ภาพรวมกลไก

```
ฆ่าบอส ──► แย่งไข่ (กดค้าง 3 วิ) ──► ฟักที่สวน ──► ตัวแม่ (ตัวละคร + น้ำหนัก)
                                                        │
                                        ┌───────────────┴───────────────┐
                                   วางในคอก                        เก็บในกระเป๋า
                                   (ผลิตลูก + ผลิตเงิน)              (ไม่ผลิตอะไรเลย)
                                        │
                        ┌───────────────┴──────────────┐
                   กองลูก (รวมเป็นกอง)              เงิน
                        │                              │
                   ส่งไปพังกำแพง                 ซื้ออาวุธ/อัปคอก/อัปอัตราผลิต
                        │                              │
                   เปิดด่านถัดไป ◄────────────────────┘
                        │
                   บอสด่านใหม่ → ไข่ดีขึ้น → วนซ้ำ
```

**1 เซิร์ฟเวอร์ = 7 คน ใช้แมพร่วมกัน แต่กำแพงเป็นของแต่ละคน** พื้นที่บอสใช้ร่วมกัน เข้าได้เฉพาะคนที่พังกำแพงถึงด่านนั้น

หลักการที่ยึดทั้งเอกสาร:

| หลักการ | เหตุผล |
|---|---|
| **เซฟเฉพาะสิ่งที่ derive กลับไม่ได้** | ตัวคูณคลาส · สูตร damage · ราคา · HP ด่าน อยู่ใน Config ทั้งหมด เซฟแค่ id/น้ำหนัก/เลเวล แล้ว lookup ตอน runtime — บาลานซ์ใหม่ทีหลังไม่ต้อง migrate |
| **เวลาเป็น timestamp สัมบูรณ์** | `os.time()` (Unix UTC) ไม่ใช่ "เหลืออีกกี่วินาที" ทั้งไข่และการผลิตลูกจึงเดินต่อข้ามการออกเกมได้ |
| **id เป็นสัญญาถาวร** | `charId` / `eggId` / `statusId` ที่เขียนลง DataStore แล้ว เปลี่ยนไม่ได้ตลอดชีวิตโปรเจกต์ |
| **น้ำหนักแม่เป็นจำนวนเต็มเสมอ** | เพราะมันคือส่วนหนึ่งของ stack key ทศนิยมเข้ามาเมื่อไหร่กองแตกทันที ([§4](#4-stack-key--หัวใจของระบบกองลูก)) |
| **ทุกอย่างที่ตัดสินผลทำที่ server** | โดยเฉพาะการแย่งไข่ ([§12](#12-จุดที่เสี่ยงโดนโกง-exploit)) |

## 2. ขอบเขตข้อมูล 3 ชั้น

| | **ต่อผู้เล่น** (เซฟลง DataStore) | **ต่อเซิร์ฟเวอร์** (memory หายเมื่อ server ปิด) | **ชั่วคราวระหว่างรบ** (หายเมื่อจบตา) |
|---|---|---|---|
| **เก็บอะไร** | แม่ในคอก · แม่ในกระเป๋า · กองลูก · เลเวลคอก · เลเวลอัตราผลิต · เลเวลอาวุธ · เงิน · `wallProgress` · ไข่ที่ฟังอยู่ · ไข่ในกระเป๋า · ทีม · สถิติ | บอสด่านไหนเกิดอยู่ + HP ปัจจุบัน · ไข่ที่วางอยู่ในรังตอนนี้ · ใครกดค้างหยิบไข่อยู่ + กดมากี่วินาที · ใครอยู่ในพื้นที่บอส · โมเดลทหารฝ่ายรับที่ render อยู่ | HP ทหารฝ่ายรับที่เหลือ · HP กำแพงที่เหลือ · กองทัพที่ส่งไปและที่เหลือรอด |
| **อยู่ที่ไหน** | DataStore `PlayerData_v1` key `player_<UserId>` · **log ธุรกรรม Robux อยู่ DataStore แยก** `PurchaseLog_v1` | ตาราง Lua ใน ServerScriptService | ตาราง Lua ระหว่างคำนวณ |
| **หายแล้วเป็นไง** | ผู้เล่นเสียของถาวร — ห้ามหาย | เกิดใหม่ได้เอง บอสรีเกิดทุก 5 นาทีอยู่แล้ว | คำนวณใหม่ได้จาก PlayerData |
| **ใครเห็น** | เจ้าของคนเดียว | ทุกคนในเซิร์ฟเวอร์ | เจ้าของคนเดียว |

**จุดที่ต้องระวังที่สุด:** `wallProgress` อยู่ฝั่งซ้าย ไม่ใช่ฝั่งกลาง
ความคืบหน้ากำแพงเป็น**ของแต่ละคน** ถ้าเผลอเก็บไว้ฝั่งเซิร์ฟเวอร์ ผู้เล่นจะเสียความคืบหน้าทุกครั้งที่ server ปิด และคนที่เข้ามาใหม่จะได้ด่านของคนอื่นไปฟรี ๆ

ส่วนไข่ในรังอยู่ฝั่งกลางเพราะเป็นของกลางที่ทุกคนแย่งกัน **จนกว่าจะมีคนหยิบสำเร็จ** ตอนนั้นมันถึงย้ายไปฝั่งซ้าย (เข้าสวนฟักของคนนั้น)

## 3. โครงสร้าง PlayerData

```lua
PlayerData = {
    schemaVersion = 1,                     -- number

    currency = {
        coins = 500,                       -- number  ได้จากแม่ในคอก ใช้ซื้อทุกอย่าง
        gems  = 0,                         -- number  พรีเมียม ยังไม่มีที่ใช้
    },

    -- ══ แม่ในคอก ══ ผลิตลูก + ผลิตเงิน  จำนวน ≤ Config.getPenCapacity(penLevel)
    mothersInPen = {
        {
            uid            = "1234567-1",  -- string   "<UserId ผู้ฟักคนแรก>-<เลขนับ>" ไม่ซ้ำทั้งเกม
            charId         = "wukong",     -- string   Config.Characters (กำหนดคลาส → ตัวคูณ damage/HP)
            weight         = 1500,         -- number   kg จำนวนเต็ม สุ่มตอนฟัก
            statuses       = { "gold" },   -- {string} สถานะที่ติดอยู่ตอนนี้
            lastProducedAt = 1757740000,   -- number   os.time() ที่ settle การผลิตไปถึงแล้ว
            obtainedAt     = 1757700000,   -- number   os.time() ตอนฟักออกมา
            locked         = false,        -- boolean  กันเผลอส่งไปรบ/ขาย
        },
    },

    -- ══ แม่ในกระเป๋า ══ ไม่ผลิตอะไรเลย  จำนวน ≤ Config.Bag.CAPACITY (100)
    -- โครงเหมือนกันทุกฟิลด์ ยกเว้นไม่มี lastProducedAt (ไม่ได้ผลิตจึงไม่ต้องนับเวลา)
    mothersInBag = { ... },

    nextUid = 2,                           -- number  เลขนับของผู้เล่นคนนี้ ห้ามรีเซ็ต ห้ามลด
                                           --         uid เต็ม = Config.makeUid(UserId, nextUid)

    -- ══ กองลูก ══ dictionary: stack key → จำนวน (ดู §4)
    children = {
        ["wukong|1500|gold"]        = 482000,
        ["wukong|1500|gold,silver"] = 9600,
        ["fish|300|"]               = 12,
    },

    -- ══ เลเวลต่าง ๆ ══
    penLevel        = 1,                   -- number  1..Config.Pen.MAX_LEVEL (15)
    productionLevel = 0,                   -- number  0..Config.Production.UPGRADE_MAX_LEVEL (10)
    weaponLevel     = 1,                   -- number  1..Config.Weapon.MAX_LEVEL (10)
    wallProgress    = 1,                   -- number  ด่านสูงสุดที่พังกำแพงได้แล้ว 1..9
                                           --         เป็นตัวคูณเงินด้วย (×10 ต่อด่าน)

    -- ══ ไข่ที่กำลังฟักในสวน ══ array ยาวคงที่ = Config.Hatchery.MAX_EGGS (50)
    -- ⚠️ ต้องเป็น array ไม่ใช่ dict ที่ key เป็นตัวเลข (เหตุผลใน §9.3)
    --
    -- ⚠️ ไข่ทุกฟอง "มีน้ำหนักของตัวเอง" ตั้งแต่ตอนบอสวางไข่ในรัง
    -- ไม่ใช่สุ่มตอนฟัก — เพราะขนาดโมเดลไข่ในรังบอกน้ำหนักให้ผู้เล่นเห็น
    hatching = {
        {
            eggId     = "egg_stage3",      -- string  ไข่ของด่าน 3 (บอสด่าน N วางไข่ด่าน N)
            weight    = 1500,              -- number  kg จำนวนเต็ม ล็อกตั้งแต่ตอนวางไข่
            startedAt = 1757740000,
            hatchAt   = 1757740120,
        },
        false,                             -- ช่องว่างใช้ false ห้ามใช้ nil
        -- ... รวม 50 ช่อง
    },

    -- ══ ไข่ที่ยังไม่เอาเข้าสวน ══ array ยาวคงที่ 50 ช่องเหมือนกัน
    -- ⚠️ เป็น array ของไข่ "รายฟอง" แล้ว ไม่ใช่ [eggId] = จำนวน อีกต่อไป
    -- เพราะไข่สองฟองชนิดเดียวกันมีน้ำหนักต่างกันได้ → นับรวมเป็นตัวเลขไม่ได้
    heldEggs = {
        { eggId = "egg_stage1", weight = 320 },
        { eggId = "egg_stage1", weight = 12000 },
        false,
        -- ... รวม 50 ช่อง
    },

    -- ══ ความคืบหน้าการตีแต่ละด่าน — สะสมถาวร ══
    -- ⚠️ array ยาวคงที่ = Config.Stage.COUNT (9) · ช่องว่างใช้ false (ดู §9.3)
    --
    -- ทหารฝ่ายรับ **ตายแล้วไม่เกิดใหม่** และ HP กำแพงที่ตีไปแล้วไม่คืน
    -- ทั้งสองค่าต้องเซฟลง DataStore ไม่รีเซ็ตเมื่อออกเกมหรือเซิร์ฟรีสตาร์ท
    -- ไม่งั้นผู้เล่นที่ตีมาครึ่งด่านแล้วเน็ตหลุดจะเสียงานทั้งหมด
    -- และจะไม่มีวันผ่านด่านที่ใช้เวลานานกว่า session เดียว
    stageProgress = {
        false,                             -- ด่าน 1 ไม่มีกำแพง ไม่ต้องเก็บอะไร
        false,                             -- ด่าน 2 พังไปแล้ว
        {
            defendersRemaining = 4500,     -- number  ทหารฝ่ายรับที่เหลือ (จาก 1,000 ของด่าน 3)
            wallHpRemaining    = 50000,    -- number  HP กำแพงที่เหลือ
        },
        false, false, false, false, false, false,
    },

    -- ══ สถานะปุ่มอัญเชิญ ══
    -- true = ปล่อยทหารต่อเนื่องอัตโนมัติ · false = หยุดปล่อย สะสมไว้ในคลัง
    -- กลไกหลักของเกม: สะสมกองใหญ่แล้วปล่อยรวดเดียวทะลุ
    -- ดีกว่าปล่อยทีละตัวแล้วถูกกินทีละตัว
    summonEnabled = true,                  -- boolean

    teams = {
        {
            name        = "ทีมหลัก",        -- string   ต้องผ่าน TextService:FilterStringAsync
            motherUids  = {                -- {string} ชี้ uid ของแม่ (ในคอกหรือกระเป๋าก็ได้)
                "1234567-1", "1234567-5",
            },
            childStacks = {                -- [stackKey] = จำนวนที่ส่งไป (ไม่ใช่ทั้งกอง)
                ["wukong|1500|gold"] = 200000,
            },
        },
    },
    activeTeam = 1,

    stats = {
        eggsHatched       = 0,             -- number
        eggsHatchedByType = { egg_common = 0 },
        eggsGrabbed       = 0,             -- number  ไข่ที่แย่งมาได้สำเร็จ
        bossKilled        = 0,             -- number
        childrenProduced  = 0,             -- number  ลูกที่ผลิตสะสมทั้งหมด
        battlesWon        = 0,
        battlesLost       = 0,
        mothersLost       = 0,             -- number  แม่ที่ตายในการรบสะสม
        childrenLost      = 0,
        heaviestMother    = 0,             -- number  น้ำหนักแม่ที่หนักสุดที่เคยได้ (ไว้อวด)
        totalCoinsEarned  = 0,
        firstJoinAt       = 1750000000,
        lastSeenAt        = 1757740000,    -- number  ใช้บอกว่าออฟไลน์ไปนานแค่ไหน
        playTimeSeconds   = 0,
    },
}
```

### 3.1 อธิบายรายฟิลด์

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `schemaVersion` | number | **สำคัญที่สุด** ไม่มีตัวนี้ = วันที่ต้องเปลี่ยนโครงจะแยกข้อมูลเก่า/ใหม่ไม่ออก ต้องเดา = ข้อมูลผู้เล่นพัง ([§10](#10-แผนการ-migration)) |
| `currency` | table | เป็น table ตั้งแต่แรกแทน number เดี่ยว เพิ่มสกุลที่สองทีหลังเป็น migration ที่เลี่ยงได้ฟรี |
| `mothersInPen` / `mothersInBag` | array | **แยกกันสองชุด ไม่ใช่ฟิลด์ `inPen` ในตัวเดียว** — เพราะโค้ดที่ settle การผลิตกับคิดเงินต้องวนเฉพาะแม่ในคอก แยกโครงไว้เลยทำให้ลืมกรองไม่ได้ และไม่ต้องวน 119 ตัวทุก tick |
| `nextUid` | number | ต้องเซฟ ไม่งั้นโหลดใหม่แล้วเริ่มนับ 1 ใหม่ → uid ชนกัน → ทีมชี้ผิดแม่ |
| `children` | dictionary | ดู [§4](#4-stack-key--หัวใจของระบบกองลูก) |
| `penLevel` | number | กำหนดความจุคอก + ราคาอัปขั้นถัดไป |
| `productionLevel` | number | ตัวคูณอัตราผลิตลูก = `3 ^ productionLevel` |
| `weaponLevel` | number | damage อาวุธ = `10 × 10^(level-1)` ใช้ตีบอสเท่านั้น |
| `wallProgress` | number | **ทำสองหน้าที่**: บอกว่าเข้าพื้นที่บอสด่านไหนได้ และเป็นตัวคูณเงิน `×10^(wallProgress-1)` |
| `hatching` | array | ไข่ที่กำลังฟัก ยาวคงที่ 50 ช่อง · **แต่ละฟองมี `weight` ของตัวเอง** |
| `heldEggs` | array | ไข่ที่ยังไม่เข้าสวน ยาวคงที่ 50 ช่อง — **รายฟอง ไม่ใช่ตัวนับ** ([§8.5.1](#851-ไข่รายด่าน-และน้ำหนักที่ล็อกตั้งแต่ในรัง)) |
| `stageProgress` | array | ทหารฝ่ายรับที่เหลือ + HP กำแพงที่เหลือของแต่ละด่าน ยาวคงที่ 9 ช่อง — **สะสมถาวร** ([§7](#7-การรบ--ปล่อยทหารต่อเนื่องแบบ-age-of-war)) |
| `summonEnabled` | boolean | ปุ่มอัญเชิญเปิดอยู่ไหม |
| `stats` | table | เก็บตั้งแต่ตอนนี้เพราะย้อนเก็บไม่ได้ |

#### แม่ 1 ตัว

| ฟิลด์ | ชนิด | ทำไมต้องมี |
|---|---|---|
| `uid` | **string** | `"<UserId>-<เลขนับ>"` — ไม่ซ้ำ**ทั้งเกม** ไม่ใช่แค่ในผู้เล่นคนเดียว **ห้าม reuse** แม้ตัวเดิมจะตายไปแล้ว ดู [§3.2](#32-ทำไม-uid-ต้องเป็น-global) |
| `charId` | string | ตัวละคร → คลาส → ตัวคูณ damage/HP (SS ×5 ถึง C ×1) **ฝังอยู่ใน stack key ของลูก** |
| `weight` | number | kg **จำนวนเต็มเสมอ** เป็นทั้งตัวกำหนด damage/HP/เงิน และเป็นส่วนหนึ่งของ stack key |
| `statuses` | {string} | สถานะที่ติดอยู่ *ตอนนี้* ลำดับในอาเรย์ไม่สำคัญ `makeStackKey` เรียงให้เอง |
| `lastProducedAt` | number | จุดที่ settle การผลิตไปถึงแล้ว **ไม่ใช่** "เวลาที่ผลิตตัวล่าสุด" ([§5.2](#52-วิธี-settle)) |
| `obtainedAt` | number | เรียง "ใหม่สุด" ใน UI และเป็นหลักฐานตอนดีบั๊ก |
| `locked` | boolean | แม่ตายถาวร ล็อกกันเผลอลากเข้าทีม |

#### ไข่ที่กำลังฟัก

| ฟิลด์ | ทำไมต้องมี |
|---|---|
| `eggId` | อ้าง `Config.EggTypes` — กำหนดว่าฟักออกมาได้คลาสไหนบ้าง (ไข่ของด่านไหน) |
| `weight` | **น้ำหนักแม่ที่จะได้ตอนฟัก** สุ่มไว้แล้วตั้งแต่ตอนบอสวางไข่ · จำนวนเต็ม |
| `startedAt` | `os.time()` ตอนวาง ใช้คิด progress bar |
| `hatchAt` | `os.time()` ที่ครบกำหนด |

**ทำไมเก็บ `hatchAt` ทั้งที่คำนวณจาก `hatchTime` ได้:** ถ้าเก็บแต่ `startedAt` แล้ววันหนึ่งไปแก้ `hatchTime` ใน Config ไข่ที่ค้างอยู่จะเปลี่ยนเวลาฟักกลางคัน (ยาวขึ้นได้ด้วย) การเก็บ `hatchAt` ตรึงสัญญาที่ให้ไว้ตอนวาง

### 3.2 ทำไม `uid` ต้องเป็น global

```
Config.makeUid(1234567, 42)   →  "1234567-42"
Config.parseUid("1234567-42") →  1234567, 42
```

`UserId` ในนี้คือ **ผู้เล่นที่ฟักแม่ตัวนี้ออกมาครั้งแรก** ไม่ใช่เจ้าของปัจจุบัน — **ห้ามเปลี่ยนตอนเทรด** เพราะจุดประสงค์คือความไม่ซ้ำ ไม่ใช่การบอกว่าใครเป็นเจ้าของ

**เหตุผล:** มีแผนจะทำเทรดแม่ระหว่างผู้เล่น ถ้า uid เป็นเลขที่ไม่ซ้ำแค่ในคนเดียว:

```
ผู้เล่น A มีแม่ uid = 5 (ซุนหงอคง 1,500 kg)   ทีมของ A ชี้ uid 5
ผู้เล่น B มีแม่ uid = 5 (ปลา 100 kg)          ทีมของ B ชี้ uid 5

B เทรดแม่ uid 5 ให้ A  →  A มีแม่ uid 5 สองตัว
                       →  ทีมของ A ชี้ตัวไหน? ไม่มีทางรู้
```

แก้ทีหลังไม่ได้ เพราะ uid ฝังอยู่ใน `teams[].motherUids` ที่เซฟไปแล้ว **ต้องตัดสินก่อนเขียนโค้ดเซฟบรรทัดแรก**

ผลข้างเคียงที่ต้องรู้: `uid` เป็น **string** ไม่ใช่ number แล้ว โค้ดที่เทียบ uid ต้องเทียบแบบ string ส่วน `nextUid` ยังเป็น number (เป็นแค่ตัวนับของผู้เล่นคนนั้น)

`Config.validate()` เช็คว่าตัวคั่นของ uid (`-`) ไม่ชนกับตัวคั่นของ stack key (`|` และ `,`)

## 4. Stack key — หัวใจของระบบกองลูก

### 4.1 รูปแบบ

```
"<charId>|<น้ำหนักแม่>|<สถานะเรียงแล้ว คั่นด้วยจุลภาค>"
```

| กรณี | key |
|---|---|
| ซุนหงอคง 1,500 kg ไม่มีสถานะ | `"wukong\|1500\|"` |
| ซุนหงอคง 1,500 kg มี gold | `"wukong\|1500\|gold"` |
| องค์ยูไล 100,000,000 kg มี gold+silver | `"yulai\|100000000\|gold,silver"` |

สร้าง/แยกด้วย `Config.makeStackKey()` / `Config.parseStackKey()` **เท่านั้น** ห้ามต่อ string เอง

### 4.2 กฎ 3 ข้อที่ห้ามพลาด

**1. ใช้น้ำหนัก "แม่" ไม่ใช่น้ำหนัก "ลูก"**

ลูกหนัก 1% ของแม่ ซึ่งเป็นทศนิยมได้ (แม่ 999 kg → ลูก 9.99 kg) ถ้าเอา 9.99 ไปทำ key จะเจอปัญหา float: โค้ดคนละที่อาจได้ `9.99` กับ `9.990000000000001` → กลายเป็นคนละกองโดยไม่มีใครรู้ตัว

น้ำหนักแม่เป็นจำนวนเต็มเสมอ (`Config.rollMotherWeight` คืน `NextInteger`) จึงเป็น identity ที่ปลอดภัย น้ำหนักลูกคำนวณกลับได้ตลอดด้วย `Config.getChildWeight()`

**2. เรียงสถานะก่อนเสมอ**

`{gold, silver}` กับ `{silver, gold}` คือชุดเดียวกัน ต้องได้ key เดียวกัน `makeStackKey` เรียกใช้ `table.sort` ทุกครั้ง — เรียงตามลำดับ byte ของ ASCII ซึ่งคงที่ ไม่ขึ้นกับ locale นี่คือเหตุผลที่ `Config.validate()` บังคับว่า `statusId` และ `charId` ต้องเป็น `^[a-z][a-z0-9_]*$`

**3. ตัดสถานะซ้ำก่อนเรียง**

`{gold, gold}` ต้องได้ key เดียวกับ `{gold}` ไม่งั้นบั๊กที่เผลอใส่สถานะซ้ำจะสร้างกองผี

> ทั้ง 3 ข้อมีชุดเทสต์ครอบอยู่แล้ว รวมถึงเคส `{silver,gold}` ต้องได้ key เดียวกับ `{gold,silver}`

### 4.3 ทำไมกองลูกไม่เก็บ `charId` / `statuses` แยกอีกชุด

เพราะ **key คือ identity ทั้งหมดของกองอยู่แล้ว** ถ้าเก็บซ้ำเป็น

```lua
children = { ["wukong|1500|gold"] = { charId="wukong", weight=15, statuses={"gold"}, count=482000 } }  -- ❌
```

จะได้ปัญหา 3 อย่างฟรี ๆ:

1. **ข้อมูลขัดกันเองได้** — วันหนึ่งจะมีบั๊กที่ key บอก `wukong` แต่ฟิลด์ข้างในบอก `tang` แล้วไม่มีใครรู้ว่าอันไหนถูก
2. **เปลืองที่ ~5 เท่า** — `["wukong|1500|gold"]=482000` ใช้ ~30 bytes ส่วนแบบ table ใช้ ~130 bytes (ที่ 2,000 กองคือ 60 KB vs 260 KB)
3. **ต้องเขียน validate เพิ่ม** เพื่อกันข้อ 1 ซึ่งเป็นงานที่ไม่ต้องมีตั้งแต่แรก

ค่าของ dictionary จึงเป็น **number ล้วน ๆ** คือจำนวนตัวในกอง

## 5. การผลิตลูก

### 5.1 อัตรา

**อัตราผลิตแปรตามน้ำหนักแม่** (ของใหม่ — เดิมแม่ทุกตัวผลิตเท่ากัน)

```
ผลิต/นาที = 1 × (น้ำหนักแม่ ÷ 100)^0.25 × ตัวคูณ upgrade × ตัวคูณสถานะ
```

| น้ำหนักแม่ | ผลิต/นาที | เติมคลัง 500 เต็มใน |
|---:|---:|---:|
| 100 kg | 1.0 | 8.3 ชม. |
| 10,000 kg | 3.2 | 2.6 ชม. |
| 1,000,000 kg | 10.0 | 50 นาที |
| 100,000,000 kg | 31.6 | 16 นาที |

#### ⚠️ ทำไมเลขชี้กำลังเป็น 0.25 ไม่ใช่ 0.5

น้ำหนักมีผลอยู่แล้ว **2 ทาง**: เงิน (√) และ damage ต่อตัว (√)
ถ้าอัตราผลิตใช้ √ ด้วย **damage รวมต่อวันจะแปรผันตรงกับน้ำหนัก** (√ × √ = 1) → ช่องว่างระหว่างแม่ 100 kg กับ 100M kg จะกลายเป็น **1,000,000 เท่า**

ใช้ 0.25 ได้ราว **31,623 เท่า** — กว้างพอให้ตัวหนักคุ้มค่า แต่ไม่ถึงกับขาดกัน
เลขชี้กำลังอยู่ใน `Config.Production.WEIGHT_EXPONENT` ปรับได้ `validate()` บังคับว่าต้องอยู่ระหว่าง 0 กับ 1

| | อัตรา | ที่มา |
|---|---|---|
| ออนไลน์ | ตามสูตรข้างบน (แม่**ในคอก**เท่านั้น) | `Config.getProductionPerMinute()` |
| ออฟไลน์ | 10% ของอัตราออนไลน์ | `Config.Production.OFFLINE_RATE_RATIO` |
| เพดานออฟไลน์ | 8 ชั่วโมง | `Config.Production.OFFLINE_CAP_SECONDS` |
| ตัวคูณจาก upgrade | `3 ^ productionLevel` สูงสุด ×59,049 | `Config.getProductionMultiplier()` |
| **เพดานคลัง** | **500 ตัว/กอง · เต็มแล้วแม่หยุดผลิต** | `Config.Production.STACK_CAP` |

**ออฟไลน์เต็มเพดานได้ 48 ตัวต่อแม่ 1 ตัว** (แม่ 100 kg ก่อนคูณ upgrade · แม่หนักกว่าได้มากกว่าตามสูตร)
ผู้เล่นที่มีแม่ในคอก 10 ตัวออกไป 3 วัน กลับมาได้ 480 ตัว ไม่ใช่ 4,320 ตัว

**แม่ในกระเป๋าไม่ผลิตอะไรเลย** — ไม่ต้องมี `lastProducedAt` และไม่ต้องวนถึงตอน settle

### 5.2 วิธี settle

ใช้สูตรเดียวกันทั้งออนไลน์และออฟไลน์ ต่างกันแค่ค่า rate

```
ต่อแม่ในคอก 1 ตัว:
    ratePerSecond = Config.getProductionPerMinute(
                        mother.weight, mother.statuses, productionLevel, ออนไลน์
                    ) / 60
    -- ⚠️ ใช้ helper ตัวนี้เท่านั้น ห้ามคูณเอง — ในนั้นรวม
    --    น้ำหนักแม่ ^WEIGHT_EXPONENT · upgrade · บัฟสถานะ · ตัวคูณออฟไลน์ ครบแล้ว

    windowStart = max(mother.lastProducedAt, now - OFFLINE_CAP_SECONDS)   ← เพดานอยู่ตรงนี้
    elapsed     = max(0, now - windowStart)
    produced    = floor(elapsed × ratePerSecond)
    produced    = min(produced, MAX_PER_SETTLE)                            ← กันนาฬิกากระโดด

    ถ้า produced > 0:
        key = Config.makeStackKey(mother.charId, mother.weight, mother.statuses)
        produced = min(produced, STACK_CAP - (children[key] or 0))   ← เพดานคลัง
        children[key] = (children[key] or 0) + produced
        ถ้าชนเพดาน → แจ้งเตือนผู้เล่นว่าแม่ตัวนี้หยุดผลิตแล้ว
        mother.lastProducedAt = windowStart + produced / ratePerSecond      ← ไม่ใช่ now
```

**บรรทัดสุดท้ายคือจุดที่พลาดกันบ่อยที่สุด** ถ้าเซ็ต `lastProducedAt = now` เศษเวลาที่ยังไม่ครบ 1 ตัวจะถูกทิ้งทุกรอบ ตอนออนไลน์ที่ tick ทุก 5 วินาที (ผลิตได้รอบละ 0.083 ตัวถ้ายังไม่อัป) ผู้เล่นจะไม่ได้ลูกเลยสักตัว การเลื่อนไปเท่าที่ "ใช้จริง" ทำให้เศษสะสมข้ามรอบได้โดยไม่ต้องมีฟิลด์ accumulator แยก

### 5.3 ลำดับตอนผู้เล่นล็อกอินกลับ (ห้ามสลับ)

```
1. โหลด PlayerData + migrate + validate
2. เคลียร์ไข่ที่ฟักครบระหว่างออฟไลน์   ← สร้างแม่ใหม่ ตั้ง lastProducedAt = hatchAt
                                        ถ้าคอกเต็ม ให้ลงกระเป๋า ถ้ากระเป๋าเต็มด้วยให้ค้างไว้ในสวน
3. settle การผลิตออฟไลน์ของแม่ในคอกทุกตัว  ← แม่ที่เพิ่งเกิดในข้อ 2 ก็ผลิตด้วย
4. ตั้ง lastSeenAt = now แล้วเริ่ม tick ออนไลน์
```

**ถ้าสลับข้อ 2 กับ 3** แม่ที่ฟักออกมาตอนชั่วโมงที่ 1 ของการออฟไลน์ 8 ชั่วโมง จะไม่ผลิตอะไรเลยทั้งที่ควรได้ 42 ตัว
สูตร `windowStart = max(lastProducedAt, now - cap)` จัดการเคสนี้ให้เองอยู่แล้ว เพราะแม่ที่เพิ่งเกิดมี `lastProducedAt = hatchAt` ซึ่งใหม่กว่า `now - cap`

### 5.4 ตอน logout / autosave

```
1. settle การผลิตออนไลน์จนถึง now
2. lastSeenAt = now
3. เซฟ
```

ทำข้อ 1 ก่อนเสมอ ไม่งั้นเวลาที่เล่นอยู่ช่วงท้ายจะถูกนับเป็นออฟไลน์ (ช้ากว่า 10 เท่า) = ผู้เล่นเสียเปรียบ

## 6. สถานะ (Status)

### 6.1 กฎพื้นฐาน

- สถานะติดที่ **ตัวแม่เท่านั้น** ลูกไม่มีสถานะเป็นของตัวเอง
- ลูกที่ผลิตออกมา **คัดลอกชุดสถานะของแม่ ณ เวลาที่ผลิต** (snapshot ไม่ใช่ reference)
- แม่ 1 ตัวติดได้หลายสถานะพร้อมกัน
- Phase 1-3 ยังไม่มีสถานะจริง (`Config.Statuses` มี `gold` / `silver` แต่ `enabled = false`)

### 6.2 กฎที่สำคัญที่สุด: แม่ได้สถานะเพิ่มทีหลัง

> **ลูกที่ผลิตไปแล้ว "ไม่" อัปเดตย้อนหลัง**

```
วันที่ 1   ซุนหงอคง 1,500 kg ไม่มีสถานะ
          ผลิตลูก 500 ตัว  →  children["wukong|1500|"] = 500

วันที่ 3   ได้สถานะ gold
          ผลิตต่อ 300 ตัว →  children["wukong|1500|"]     = 500   ← กองเดิม ไม่เปลี่ยน
                             children["wukong|1500|gold"] = 300   ← กองใหม่

วันที่ 5   ได้ silver เพิ่ม
          ผลิตต่อ 200 ตัว →  children["wukong|1500|gold,silver"] = 200   ← กองที่สาม
```

**แม่ตัวเดียวมีลูกกระจายหลายกองได้ตามประวัติสถานะของมัน** — เป็นพฤติกรรมที่ตั้งใจ ลูกที่ผลิตตอนแม่ยังไม่มีบัฟก็ไม่ควรได้บัฟย้อนหลัง

ผลข้างเคียงที่ต้องระวัง: จำนวนกองโตตาม **(จำนวนแม่ × จำนวนชุดสถานะที่แม่แต่ละตัวเคยผ่าน)** จึงต้องมี `Config.Inventory.MAX_CHILD_STACKS = 2000`

### 6.3 บัฟที่สถานะให้ (โครงพร้อมแล้ว ค่ายังไม่เปิด)

สถานะ 1 ตัวให้บัฟได้ 4 อย่าง แม่ติดหลายสถานะ = **ตัวคูณคูณสะสมกัน** ส่วนโบนัสน้ำหนักลูก**บวกกัน**

| ฟิลด์ใน `StatusType` | ผล | ค่ากลาง |
|---|---|---|
| `damageMultiplier` | คูณ damage และ HP | 1 |
| `coinMultiplier` | คูณรายได้เงิน | 1 |
| `productionMultiplier` | คูณความเร็วผลิตลูก | 1 |
| `childRatioBonus` | บวกเข้ากับ `CHILD_RATIO` (0.01) | 0 |

ค่าตัวอย่างที่ตั้งไว้ใน Config ตอนนี้ (**`enabled = false` ทั้งคู่ จึงยังไม่มีผลอะไรเลย**):

| สถานะ | damage | เงิน | ผลิต | น้ำหนักลูก |
|---|---:|---:|---:|---|
| gold | ×2 | ×2 | ×1.5 | +1% → **ลูกหนัก 2% ของแม่** |
| silver | ×1.5 | ×1.5 | ×1.2 | +0% |

อ่านผลรวมด้วย `Config.getStatusEffects(statuses)` ซึ่งข้ามสถานะที่ `enabled = false` ให้อัตโนมัติ
`Config.computePower()` · `getCoinsPerMinute()` · `getChildWeight()` รับ `statuses` เป็นพารามิเตอร์เสริมแล้ว

**สองข้อที่ต้องรู้:**

1. **โบนัสน้ำหนักลูกไม่กระทบ stack key** — key เก็บน้ำหนัก *แม่* ไม่ใช่ลูก และลูกในกองเดียวกันมีชุดสถานะเดียวกันอยู่แล้ว จึงมีสัดส่วนน้ำหนักเท่ากันเสมอ น้ำหนักลูกจริงคำนวณกลับได้ตลอดด้วย `Config.getChildWeight(motherWeight, statuses)`
2. **มีเพดาน `MAX_CHILD_RATIO = 1`** — ลูกหนักเกินแม่ไม่ได้ `Config.validate()` เช็คว่าถ้าเปิดทุกสถานะพร้อมกันแล้วยังไม่เกินเพดาน ปัจจุบันเปิดหมด = 2% ยังห่างเพดานเยอะ

> บัฟที่คูณ damage ตรง ๆ คุ้มกว่าการเพิ่มน้ำหนักลูกมาก เพราะ damage ใช้ sqrt: เพิ่มน้ำหนักลูก ×2 ได้ damage แค่ ×1.41 แต่ `damageMultiplier = 2` ได้ ×2 เต็ม ตอนปรับสมดุล Phase 6 ควรใช้ `damageMultiplier` เป็นตัวหลัก แล้วให้ `childRatioBonus` เป็นของแถมเชิงความรู้สึก

### 6.4 การประนีประนอมเรื่องผลผลิตออฟไลน์

ตอนคำนวณผลผลิตออฟไลน์ ให้ใช้ชุดสถานะ **ปัจจุบัน** ของแม่ แล้วยกให้เป็นกองเดียว

ข้อสังเกตที่ควรรู้: **ตามดีไซน์ตอนนี้การประนีประนอมนี้ยังไม่มีผลจริง** เพราะสถานะเปลี่ยนได้เฉพาะตอนผู้เล่นออนไลน์ พอออฟไลน์ชุดสถานะจึงคงที่ตลอดช่วงนั้น = "สถานะปัจจุบัน" กับ "สถานะตอน logout" เป็นค่าเดียวกัน

กฎข้อนี้จะเริ่มมีผลจริงในวันที่สถานะเปลี่ยนเองได้ระหว่างออฟไลน์ (บัฟมีอายุ / daily reward ที่ติดสถานะอัตโนมัติ) วันนั้นการคำนวณที่ถูกต้องต้องแบ่งช่วงเวลาออฟไลน์เป็นท่อน ๆ ตามประวัติสถานะ ซึ่งซับซ้อนกว่ามาก **เรายอมรับความคลาดเคลื่อนตรงนี้** แลกกับความง่าย และให้เอียงไปทางที่ผู้เล่นได้เปรียบเสมอเมื่อต้องเลือก

## 7. การรบ — ปล่อยทหารต่อเนื่องแบบ Age of War

> **ระบบเดิม "กดส่งกองทัพทีเดียวแล้วรอผล" ถูกยกเลิกทั้งหมด**

### 7.1 จุดสปอนและการปล่อย

```
[จุดสปอน]──ปล่อย 1 ตัว/วิ──►  ทหารเดินเรียงแถว  ──►[ทหารฝ่ายรับ]──►[กำแพง]
     ▲                                                    เดินถึงใน ~30 วิ
     │
 คลังทหาร (cap 500/กอง) ◄── แม่ในคอกผลิตเข้ามาเรื่อย ๆ
```

- ปล่อยทีละตัวเรียงแถวเดินไปทางกำแพง อัตราตาม `Config.Combat.RELEASE_PER_SECOND`
- **ปล่อยเฉพาะตอนออนไลน์** ออฟไลน์ไม่ปล่อย แต่แม่ยังผลิตอยู่ตามกติกาออฟไลน์เดิม (ช้ากว่า 10 เท่า cap 8 ชั่วโมง)
- ทหารในคลังหมด → หยุดรอจนแม่ผลิตได้ แล้วปล่อยต่ออัตโนมัติ

### 7.2 ปุ่มอัญเชิญ (เปิด/ปิด) — กลไกหลักของเกม

| กด | ผล |
|---|---|
| ปิด | หยุดปล่อย ทหารที่ผลิตได้สะสมไว้ในคลัง |
| เปิด | ปล่อยต่อเนื่องอัตโนมัติ |

**สะสมกองใหญ่แล้วปล่อยรวดเดียวทะลุ ดีกว่าปล่อยทีละตัวแล้วถูกกินทีละตัว** — นี่คือการตัดสินใจหลักที่ผู้เล่นต้องทำ เก็บสถานะไว้ใน `summonEnabled`

### 7.3 คลังทหาร — cap 500 ต่อกอง

`Config.Production.STACK_CAP = 500`

**ทำไม 500:** แม่น้ำหนักฐานผลิต ~1 ตัว/นาที → 500 ตัว ≈ **8 ชั่วโมง** ซึ่งตรงกับ cap ออฟไลน์ 8 ชั่วโมงที่ใช้อยู่แล้ว ระบบจึงสม่ำเสมอกันทั้งเกม
และ 500 ตัวปล่อยที่ 1 ตัว/วินาที = ระบายหมดใน ~8 นาที ซึ่งเป็นช่วงเวลาที่นั่งดูได้จริง

**คลังเต็ม → แม่ตัวนั้นหยุดผลิต + แจ้งเตือนผู้เล่น** (`STACK_CAP_START = 200` เผื่อทำเป็น upgrade ทีหลัง)

### 7.4 ตัวแม่ในสนามรบ — กติกาที่ห้ามพลิก

| กฎ | เหตุผล |
|---|---|
| **ห้ามระบบ auto ปล่อยตัวแม่เด็ดขาด** auto ปล่อยได้เฉพาะตัวลูก | แม่ตายถาวร = เสียเครื่องผลิตไปเลย ระบบตัดสินใจแทนไม่ได้ |
| ผู้เล่นต้องกดเลือกและส่งเองทีละครั้ง **+ กล่องยืนยัน** | เหมือนกัน |
| **เลือกได้เฉพาะแม่ที่อยู่ในกระเป๋า** แม่ในคอกเลือกไม่ได้ | กันไม่ให้เผลอส่งเครื่องผลิตที่กำลังทำเงินอยู่ไปตาย |

`Config.validate()` บังคับสองกฎแรกตรง ๆ: `ALLOW_AUTO_RELEASE_MOTHERS` และ `MOTHERS_SELECTABLE_FROM_PEN` ต้องเป็น `false` ไม่งั้นเซิร์ฟไม่บูต

### 7.5 ปุ่ม "เลือกสัตว์เลี้ยงที่ดีที่สุด"

**เป็นปุ่มกดเอง ไม่ใช่ระบบอัตโนมัติที่ทำงานเอง** — ถ้าไม่กดก็ไม่จัดอะไร

กดแล้วจัดแม่เข้าคอกอัตโนมัติ เรียงตามความสามารถผลิตเงิน (`Config.getCoinsPerMinute`)
และต้องย้ายแม่จากคอกกลับกระเป๋าเองได้ตลอด

### 7.6 auto-pause เมื่อตีไม่เข้า

ปล่อยทหารไปครบ `AUTO_PAUSE_AFTER_UNITS` (100) ตัวแล้ว **HP ฝ่ายตรงข้ามไม่ลดเลย** → หยุดปล่อยอัตโนมัติ + แจ้งเตือน

กันไม่ให้ทหารถูกป้อนเข้าเครื่องบดหายถาวรโดยไม่ได้ damage ซึ่งเป็นความเสียหายที่กู้ไม่ได้

### 7.7 ความคืบหน้าสะสมถาวร

- ทหารฝ่ายรับมีจำนวนจำกัดตามตารางด่าน **ตายแล้วไม่เกิดใหม่ หมดแล้วหมดเลย**
- ทหารฝ่ายรับหมด → เดินเข้าตีกำแพงได้ทันที
- **ทั้ง `defendersRemaining` และ `wallHpRemaining` เซฟลง DataStore ต่อผู้เล่น**

**ทำไมต้องสะสมถาวร:** ด่านท้าย ๆ ใช้เวลาตี 5–10 ชั่วโมง ซึ่งนานกว่า session เดียวแน่นอน ถ้ารีเซ็ตเมื่อออกเกมหรือเซิร์ฟรีสตาร์ท ผู้เล่นจะ**ไม่มีวันผ่านด่านเหล่านั้นเลย** ไม่ว่าจะเล่นนานแค่ไหน

UI ต้องแสดง % ความคืบหน้าให้เห็นชัด (ทหารเหลือกี่ % / กำแพงเหลือกี่ %)

### 7.8 ด่าน 1 ไม่มีกำแพง

**ด่าน 1 ไม่มีกำแพงและไม่มีทหารฝ่ายรับ** ผู้เล่นเดินไปสู้บอสตัวเล็กเอาไข่ได้เลยตั้งแต่เข้าเกมครั้งแรก

แก้ปัญหาไก่กับไข่: ต้องมีแม่ถึงจะมีกองทัพ ต้องมีไข่ถึงจะมีแม่
`validate()` บังคับว่า `Stages[1].defenders == 0` และ `getStageTotalHp(1) == 0`

### 7.9 จำนวนโมเดลบนจอ

- **แสดงเฉพาะทหารของผู้เล่นคนนั้นเอง** ไม่แสดงของคนอื่น (7 คนในเซิร์ฟเวอร์เดียวกัน)
- `Config.getVisibleUnitCount(stage)` = `อัตราปล่อย × 30 วินาทีที่ใช้เดิน` ตัดที่ `MAX_VISIBLE_UNITS` (120)
- ส่วนเกินไม่ spawn โมเดล รวมเป็นตัวเลขแทน — วิธีเดียวกับทหารฝ่ายรับ

| ด่าน | ปล่อย/วิ | มีชีวิตพร้อมกัน | แสดงจริง |
|---:|---:|---:|---:|
| 1 | 1 | 30 | 30 |
| 5 | 3 | 90 | 90 |
| 9 | 10 | 300 | **120** (ตัด) |

### 7.10 ทหารฝ่ายรับ = ตัวเลข HP รวม ไม่ใช่ Model

⚠️ **ห้าม spawn ทหารฝ่ายรับเป็น Model จริงทั้งหมด** ด่าน 9 มี 1,000,000,000 ตัว

```
เก็บ:   defendersRemaining = number ค่าเดียว
แสดง:  โมเดล 20–50 ตัว ที่ค่อย ๆ หายไปตามสัดส่วน HP
```

`Config.getDisplayModelCount(hpRatio)`: HP เต็ม → 50 ตัว · ครึ่ง → 25 · 10% → 20 (พื้นขั้นต่ำ) · หมด → 0

**ทำไมมีพื้นขั้นต่ำ 20:** ถ้าลดเป็นเส้นตรงจนถึง 0 พอ HP เหลือ 2% จะเห็นทหารตัวเดียวยืนอยู่ทั้งที่ยังต้องตีอีกนาน ดูเหมือนเกมค้าง

### 7.11 ตายถาวร

- ตัวที่ตายในการรบ **หายถาวร ทั้งแม่และลูก**
- `Config.Inventory.MAX_TEAM_MOTHERS = 3` จำกัดความเสียหายต่อครั้ง
- `locked = true` ควรกันไม่ให้แม่ตัวนั้นถูกเลือกลงสนามเลย
- **แม่ตายแล้วกองลูกของมันอยู่ต่อ** (ลูกที่ผลิตไปแล้วเป็นของผู้เล่น ไม่ผูกกับแม่)

แม่ตายต้องลบออกจาก `mothersInBag` และ**ไม่ reuse uid** · ลูกที่ตายหักออกจาก `children[key]` และลบ key ทิ้งเมื่อเหลือ 0

## 8. สมดุลตัวเลข — ที่มาของทุกค่าใน Config

### 8.1 สูตร damage / HP (เลือกแล้ว: รากที่สอง)

**HP ของตัวเรา = damage ของตัวเรา** ใช้ฟังก์ชันเดียวกัน `Config.computePower(weight, charId, statuses)`

```
damage = HP = 10 × (น้ำหนัก / 100)^0.5 × ตัวคูณคลาส × ตัวคูณสถานะ
```

#### ตาราง 1 — ตัวแม่

| น้ำหนัก (kg) | C ×1 | B ×1.5 | A ×2 | S ×3 | SS ×5 |
|---:|---:|---:|---:|---:|---:|
| 100 | 10 | 15 | 20 | 30 | 50 |
| 1,000 | 31.6 | 47.4 | 63.2 | 94.9 | 158 |
| 10,000 | 100 | 150 | 200 | 300 | 500 |
| 100,000 | 316 | 474 | 633 | 949 | 1.6K |
| 1,000,000 | 1.0K | 1.5K | 2.0K | 3.0K | 5.0K |
| 10,000,000 | 3.2K | 4.7K | 6.3K | 9.5K | 15.8K |
| 100,000,000 | 10.0K | 15.0K | 20.0K | 30.0K | 50.0K |
| **เบาสุด→หนักสุด** | ×1,000 | ×1,000 | ×1,000 | ×1,000 | ×1,000 |

#### ตาราง 2 — ตัวลูก (หนัก 1% ของแม่)

| น้ำหนักแม่ | น้ำหนักลูก | C | B | A | S | SS | % ของแม่ |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 1 | 1 | 1.5 | 2 | 3 | 5 | 10% |
| 10,000 | 100 | 10 | 15 | 20 | 30 | 50 | 10% |
| 1,000,000 | 10.0K | 100 | 150 | 200 | 300 | 500 | 10% |
| 100,000,000 | 1.0M | 1.0K | 1.5K | 2.0K | 3.0K | 5.0K | 10% |

**ลูกแรง 10% ของแม่เสมอ ทุกน้ำหนัก ทุกคลาส** — เพราะ `sqrt(0.01) = 0.1` พอดี
→ **กองลูก 10 ตัว = แรงเท่าแม่ 1 ตัว** เป็นกฎง่าย ๆ ที่ผู้เล่นจำได้ และใช้ประเมินได้เร็วว่าควรส่งแม่ไปเสี่ยงตายไหม

#### สิ่งที่ตารางนี้บอก

- **น้ำหนักสำคัญกว่าคลาสมาก** — น้ำหนัก ×1,000 ตลอดเกม แต่คลาสให้แค่ ×5
  แม่ 100 kg คลาส SS (50) ยังแพ้แม่ 10,000 kg คลาส C (100)
  → ผู้เล่นควรตื่นเต้นกับน้ำหนักที่สุ่มได้มากกว่าตัวละครที่ได้ ซึ่งตรงกับที่ระบบสุ่มน้ำหนัก 7 ชั้นออกแบบไว้
- **คลาสเป็นตัวคูณคงที่** ไม่ว่าน้ำหนักเท่าไหร่ SS ก็แรงกว่า C อยู่ ×5 เสมอ ทำให้คาดเดาได้และไม่มี combo ที่พังสมดุล

เก็บสูตร `cbrt` และ `log10` ไว้ใน Config ด้วย เผื่ออยากสลับกลับโดยไม่ต้องหาตัวเลขใหม่

### 8.2 สูตรเงิน (รากที่สอง + ตัวคูณตามด่าน)

```
coins/นาที = 1 × (น้ำหนักแม่ / 100)^0.5 × 10^(wallProgress - 1)
```

เงินมาจาก**แม่ในคอกเท่านั้น** และ**คลาสไม่มีผลต่อเงิน** (คลาสมีผลแค่ damage/HP)

#### ⚠️ ตัวคูณตามด่าน ×10 คือสิ่งที่ทำให้เกมนี้เล่นจบได้ ห้ามตัดทิ้ง

ราคาของทุกอย่างโต ×10 ต่อขั้น แต่รายได้จากน้ำหนักโตแค่ ×1,000 ตลอดเกม และคอกเพิ่มความจุทีละ 1 ตัว (+6% ถึง +20% ต่อเลเวล) ถ้าไม่มีตัวคูณตามด่าน:

| ค่าอัปคอก | ราคา | ใช้เวลา (แม่ 1M kg 19 ตัว) |
|---|---:|---:|
| Lv4→5 | 1.0M | 8.8 ชม. |
| Lv7→8 | 1.0B | 365 วัน |
| Lv10→11 | 1.0T | 1,001 ปี |
| Lv14→15 | 10,000T | 10 ล้านปี |

**และการดันค่าเริ่มต้นขึ้นแก้ไม่ได้** — ทดสอบด้วยการคูณรายได้เริ่มต้นด้วย K:

| เลเวล | K=1 | K=10,000 | K=10⁸ | K=10¹² |
|---|---:|---:|---:|---:|
| 7→8 | 365 วัน | 53 นาที | ทันที | ทันที |
| 10→11 | 1,001 ปี | 37 วัน | 5 นาที | ทันที |
| 14→15 | 10 ล้านปี | **1,001 ปี** | **37 วัน** | 5 นาที |

K คูณทุกช่องเท่ากัน จึงแค่ "เลื่อน" กำแพงไป ไม่ได้ลบกำแพง เพราะปัญหาคือ**อัตราการโตไม่เท่ากัน** (ต้นทุน ×10 ต่อเลเวล vs รายได้ ×1.1 ต่อเลเวล) ไม่ใช่ตัวเลขเล็กไป

ตัวคูณ ×10 ต่อด่านทำให้รายได้โตด้วยจังหวะเดียวกับราคา และเข้าจังหวะเดียวกับทุกอย่างในเกม (บอส ×10 · อาวุธ ×10 · ทหาร ×10):

| ด่าน | ตัวคูณเงิน | รายได้/วัน (คอกเต็ม) | ค่าคอกขั้นนั้น | ใช้เวลา |
|---:|---:|---:|---:|---:|
| 1 | ×1 | 16.1K | 1.0K | 1.5 ชม. |
| 5 | ×10,000 | 4.5B | 10.0M | 3 นาที |
| 9 | ×100M | 1.0e15 | 100.0B | ทันที |

ต้นทุนรวมทั้งเกม (คอก + อาวุธ + อัตราผลิต ≈ 11.1e15 coins) → **7 วัน** ที่รายได้ด่าน 9

ราคาขายผูกกับสูตรเงินอัตโนมัติ ไม่มีตารางแยก — ปรับสูตรเงินแล้วราคาขายขยับตามเอง

### 8.3 อาวุธกับบอส — สเกลที่ล็อกกันไว้

```
damage อาวุธขั้น N = 10 × 10^(N-1)
HP บอสด่าน N       = 100 × 10^(N-1)
```

**อาวุธขั้น N ตีบอสด่าน N ตายใน 10 ครั้งพอดีทุกด่าน** สม่ำเสมอตั้งแต่ด่าน 1 ถึง 9

`Config.validate()` บังคับว่า `Weapon.DAMAGE_MULTIPLIER == Boss.HP_MULTIPLIER` — แก้ข้างเดียวไม่ได้ ไม่งั้นความรู้สึกตอนสู้บอสจะเพี้ยนไปเรื่อย ๆ ตามด่าน

### 8.4 ทำไม upgrade อัตราผลิตเป็น ×3 ทั้งที่ราคา ×10

| อัตราผลิต | ด่าน 1 | ด่าน 5 | ด่าน 9 |
|---|---:|---:|---:|
| ×10/ขั้น (รวม ×10¹⁰) | 2.2 ชม. | 2 นาที | **ทันที** |
| **×3/ขั้น (รวม ×59,049)** | 2.2 ชม. | 4.9 ชม. | **17.8 ชม.** |
| ×2/ขั้น | 2.2 ชม. | 25.1 ชม. | 19 วัน |

ถ้าเป็น ×10 อัตราผลิตจะโตเร็วกว่าความยากของด่าน (×10⁸) ทำให้ตั้งแต่ด่าน 5 ขึ้นไปสะสมกองทัพเสร็จทันที กำแพงหมดความหมาย เหลือแค่บอสกับไข่เป็นด่านกั้น

ที่ ×3 กำแพงยังเป็นด่านกั้นจริงทุกด่าน และการที่จ่ายแพงขึ้นแต่ได้ผลน้อยกว่ายังทำให้ผู้เล่นต้องเลือกว่าจะอัปอะไรก่อน

`Config.validate()` บังคับ `UPGRADE_RATE_MULTIPLIER <= UPGRADE_COST_MULTIPLIER`

### 8.6 ตัวคูณ damage ตามด่าน และยามเฝ้าสมดุล

`Config.getStageDamageMultiplier(wallProgress)` คืน `STAGE_DAMAGE_BASE ^ (wallProgress − 1)`

#### ⚠️ off-by-one ที่พลาดง่ายที่สุด

ตอนผู้เล่น **กำลังตีด่าน N** เขาพังกำแพงมาแล้ว **N−1** ด่าน

| ด่านที่กำลังตี | พังมาแล้ว | ตัวคูณ |
|---:|---:|---|
| 1 | 0 | `BASE^0` = 1 |
| 5 | 4 | `BASE^4` |
| 9 | 8 | `BASE^8` |

ถ้าเผลอเขียน `BASE ^ wallProgress` ด่านแรกจะได้ตัวคูณฟรีทันที และช่องว่างจะ **เลื่อนไปทั้งเส้น ไม่ได้หายไป** — `validate()` จึง assert ตรง ๆ ว่า `getStageDamageMultiplier(1) == 1` และมี unit test แยกอีกชั้น

#### ใช้กับอะไร และคำนวณเมื่อไหร่

- ใช้กับ **ทั้งตัวแม่และตัวลูก** ที่ส่งไปรบ ผ่าน `Config.computeBattlePower()`
- **คำนวณตอนเข้ารบ** จาก `wallProgress` ปัจจุบัน ไม่เก็บตัวคูณติดไปกับกองลูก
- ผลข้างเคียงที่ตั้งใจ: **ลูกที่สะสมไว้ตั้งแต่ด่านต้นแรงขึ้นตามผู้เล่น ไม่มีกองที่ตกยุค**
  ผู้เล่นจึงไม่ต้องกังวลว่าเก็บลูกไว้นานแล้วจะเสียเปรียบ และไม่ต้องเขียน migration ตอนปรับตัวคูณ

#### ⚠️ ทำไม `STAGE_DAMAGE_BASE = 2` ไม่ใช่ 8

**ระบบรบใหม่เปลี่ยนสมการทั้งหมด** — เดิม damage รวม = "จำนวนที่สะสมได้" × damage/ตัว ทำให้ upgrade อัตราผลิต (×3/ด่าน) คูณ damage ตรง ๆ

ตอนนี้ damage/วินาที = **min(อัตราผลิต, อัตราปล่อย)** × damage/ตัว → พอชนเพดานปล่อยแล้ว **upgrade อัตราผลิตหลุดออกจากสมการ damage ทันที** (ยังมีประโยชน์อยู่เพราะเติมคลังเร็วขึ้น แต่ไม่ใช่ตัวคูณ damage อีกต่อไป)

สมการใหม่: เวลาต่อด่าน = HP ÷ (อัตราปล่อย × damage/ตัว × B^(N−1))
โดย HP โต ×10/ด่าน และ damage/ตัว โต ×1.99/ด่าน → **ต้องการ `1.99 × R × B ≈ 10`** ถึงจะยากเท่ากันทุกด่าน (R = อัตราโตของการปล่อย)

| B | R ที่ต้องการ | ด่าน 9 ต้องปล่อย | ใช้ได้ไหม |
|---:|---:|---:|---|
| 8 | 0.63/ด่าน | 0.02 ตัว/วิ | ❌ อัตราปล่อยต้อง**ลดลง** ซึ่งเป็นไปไม่ได้ |
| 4 | 1.26/ด่าน | 6.2 ตัว/วิ | ทำได้ แต่เส้นเวลาเกือบแบน |
| **2** | 2.51/ด่าน | — | ✅ ใช้ตารางปล่อยที่เลือกแล้วได้เส้นไต่ขึ้นสวย |
| 1 | 5.03/ด่าน | 406,608 ตัว/วิ | ❌ ด่านท้ายใช้เวลาหลักปี |

**ตารางเวลาจริง** (ตารางปล่อย 1,1,1,2,3,4,6,8,10):

| B | ด่าน 2 | ด่าน 4 | ด่าน 6 | ด่าน 8 | ด่าน 9 | ชัน | ผ่านยาม |

ยามคำนวณว่า "ผู้เล่นชั้นกลางใช้เวลากี่ชั่วโมงกว่าจะพังกำแพงด่าน N" แล้วบังคับให้อยู่ในช่วง **[0.5, 72] ชั่วโมง ทั้งสองด้าน** พร้อมเช็คว่าด่านสุดท้ายต้องไม่เร็วกว่าด่านแรก

**ทดสอบแล้วว่ายามทำงานจริง** — ตั้ง `BASE = 8` แล้ว `validate()` ล้มที่ด่าน 2 พร้อมข้อความว่าเร็วเกินไป และตั้งค่าต่ำเกิน (0.01) ก็ล้มเช่นกัน ค่าอ้างอิงอยู่ใน `Config.BalanceCheck` ปรับได้

### 8.6.1 turret — ตัดสินแล้ว: ตั้งเป็นสัดส่วนของ damage/วินาที

**ประวัติสั้น ๆ ของค่านี้ เพราะมันพลาดมาแล้วสองรอบในทางตรงข้ามกัน:**

| รอบ | ตั้งจาก | ผลจริง |
|---|---|---|
| 1 | 10% ของ damage ทหารฝ่ายรับทั้งด่าน | ระบบส่งทีเดียว การรบไม่มีระยะเวลา → turret ทำได้ **0.35%** = ไร้ผล |
| 2 | ค่าเดียวกัน แต่ระบบรบเปลี่ยนเป็นปล่อยต่อเนื่อง | การรบกินเวลาเป็นชั่วโมง → turret แรงกว่าเรา **17–238 เท่า** = ผ่านไม่ได้สักด่าน |
| **3 (ตอนนี้)** | **สัดส่วนของ damage/วินาที ของผู้เล่นชั้นกลาง** | กินกำลังพล **10% → 20%** ตามด่าน |

ต้นเหตุของทั้งสองรอบเป็นเรื่องเดียวกัน: `turretDps` ถูกตั้งจากตัวเลขระดับ **"ทั้งกองทัพ"** แต่มันไปยิงใส่ทหารที่ปล่อยได้ทีละ **1–10 ตัว/วินาที**

#### สูตรที่ใช้ตั้งค่า

```
สัดส่วนกำลังพลที่เสียให้ turret = turretDps ÷ (damage/วินาทีของเรา)
```

ระยะเวลารบตัดกันออกทั้งสองฝั่ง เพราะ **HP ของตัวเรา = damage ของตัวเรา** → ไม่ต้องรู้ว่ารบนานแค่ไหนก็คิดได้

| ด่าน | damage/วิ ของเรา | `turretDps` | กินกำลังพล |
|---:|---:|---:|---:|
| 2 | 5.7 | **0.57** | 10% |
| 3 | 53.7 | **6.1** | 11% |
| 4 | 416 | **53** | 13% |
| 5 | 3,326 | **480** | 14% |
| 6 | 18,102 | **2,800** | 16% |
| 7 | 162,917 | **28,000** | 17% |
| 8 | 868,893 | **160,000** | 19% |
| 9 | 4.21M | **840,000** | 20% |

ไล่ขึ้น 10% → 20% เพราะด่านสูงกำแพงควรเขี้ยวขึ้น แต่ยังไม่ถึงกับทำให้ตันได้

#### ยาม `assertTurretIsSurvivable()`

เรื่องนี้พลาดมาแล้วสองรอบและ**มองไม่เห็นด้วยตาเปล่าทั้งสองรอบ** จึงเพิ่มยามตัวที่สองไว้ใน `validate()`:
คำนวณ `turretDps ÷ damage/วินาที` ของทุกด่าน แล้วบังคับว่าต้องไม่เกิน `Config.BalanceCheck.TURRET_TOLL_CEILING` (35%) — **เกินเมื่อไหร่เซิร์ฟไม่บูต**

*(ทดสอบแล้วว่าจับได้จริง: เอาค่าชุดเดิม 1e9 ใส่กลับเข้าด่าน 9 แล้ว `validate()` ล้มทันที)*

#### ข้อดีที่ติดมาฟรี

สัดส่วนที่เสียแปรผกผันกับน้ำหนักแม่ — แม่หนักกว่า = damage ต่อตัวสูงกว่า = **เสียสัดส่วนน้อยกว่า** ผู้เล่นที่ลงทุนกับแม่ได้รางวัลตรงนี้โดยไม่ต้องเขียนกฎเพิ่ม ส่วนผู้เล่นที่ดวงไม่ดีจะรู้สึกว่ากำแพงเขี้ยวกว่า ซึ่งเป็นแรงจูงใจให้ไปลุ้นไข่ต่อ

### 8.7 แหล่งที่มาของไข่ — สองทาง แยกกันเด็ดขาด

**เงินในเกมซื้อไข่ไม่ได้เลย** ใช้ได้แค่ อาวุธ · อัปเกรดอาวุธ · อัปเกรดคอก
`EggType` จึงไม่มีฟิลด์ `price` โดยตั้งใจ (`validate()` บังคับว่าทุกไข่ต้องมี `source` เป็น `"boss"` หรือ `"robux"`)

| ไข่ | `source` | ได้มายังไง |
|---|---|---|
| ธรรมดา · หายาก | `"boss"` | แย่งจากรังบอส กดค้าง 3 วินาที |
| ตำนาน | `"robux"` | ซื้อด้วย Robux ผ่าน Developer Product เท่านั้น |

#### ทำไมไม่เก็บราคา Robux ใน Config

ราคาจริงตั้งใน **Creator Dashboard** ถ้าเก็บไว้ใน Config ด้วยจะมีสองแหล่งความจริง วันที่ปรับราคาแล้วลืมแก้ Config ผู้เล่นจะเห็นราคาผิดในร้าน แล้วโวยตอนกดซื้อ

Config เก็บแค่ `productId` · ชื่อ · คำอธิบาย · ให้ไข่อะไรกี่ฟอง
ฝั่ง client ดึงราคามาโชว์ด้วย `MarketplaceService:GetProductInfo(productId, Enum.InfoType.Product)`

#### ProcessReceipt — จุดที่พลาดแล้วเสียเงินจริง

Roblox เรียก `ProcessReceipt` **ซ้ำได้เรื่อย ๆ** จนกว่าจะได้ `PurchaseGranted` ถ้าเซิร์ฟเวอร์ล่มกลางทาง หรือคืน `NotProcessedYet` มันจะเรียกใหม่ในเซิร์ฟเวอร์อื่น อาจเป็นชั่วโมงถัดมา

```
ProcessReceipt(receiptInfo):

1. หา product จาก receiptInfo.ProductId
   ไม่เจอ → คืน NotProcessedYet (อย่าคืน PurchaseGranted เด็ดขาด
            ไม่งั้นผู้เล่นจ่ายเงินแล้วไม่ได้ของ และเรียกคืนไม่ได้)

2. เช็คว่าเคยให้ของไปแล้วหรือยัง
   key = Config.PurchaseLog.RECEIPT_PREFIX .. receiptInfo.PurchaseId
   เคยให้แล้ว → คืน PurchaseGranted ทันที (idempotent)

3. หาผู้เล่นจาก receiptInfo.PlayerId
   ไม่อยู่ในเซิร์ฟเวอร์นี้ → คืน NotProcessedYet
   (Roblox จะเรียกใหม่ตอนผู้เล่นเข้ามา ไม่ใช่ความผิดพลาด)

4. ให้ของ + บันทึก receipt ลง DataStore ใน UpdateAsync เดียวกัน
   ⚠️ ต้องสำเร็จทั้งคู่หรือไม่สำเร็จเลย

5. เซฟสำเร็จ → คืน PurchaseGranted
   เซฟไม่สำเร็จ → คืน NotProcessedYet (อย่ากลืน error)
```

**กฎเหล็ก 4 ข้อ:**

| กฎ | พลาดแล้วเป็นไง |
|---|---|
| **ห้ามคืน `PurchaseGranted` ก่อนเซฟสำเร็จ** | ผู้เล่นเสียเงินแล้วของหาย ไม่มีทางกู้ |
| **ต้อง idempotent ด้วย `PurchaseId`** | Roblox retry แล้วผู้เล่นได้ของสองรอบจากการจ่ายครั้งเดียว |
| **`NotProcessedYet` คือคำตอบที่ปลอดภัยเสมอ** | คืน `PurchaseGranted` ตอนไม่แน่ใจ = เสียของฟรี · Roblox จะลองใหม่ให้เอง |
| **เก็บ log ทุกธุรกรรม** | มีคนทักว่าไม่ได้ของแล้วตรวจไม่ได้ |

log เก็บใน DataStore แยก (`Config.PurchaseLog.STORE_NAME`) ไม่ปนกับ `PlayerData` เพราะเป็นข้อมูลคนละอายุ (ธุรกรรมเก็บถาวรเพื่อตรวจสอบ ส่วน PlayerData เขียนทับตลอด)

> **ยังไม่ตัดสิน:** ไข่ตำนานควรให้แม่ tier ไหน — ดู [§13](#13-ค่าที่ผมตั้งเองรอยืนยัน) มีสองทางเลือก

## 9. ขนาดข้อมูล

### 9.1 ตัวเลขจริง

ลิมิตของ Roblox DataStore คือ **4 MB (4,194,304 bytes) ต่อ 1 key**

| สถานการณ์ | ขนาด | % ของลิมิต |
|---|---:|---:|
| ผู้เล่นทั่วไป (คอก 8 + กระเป๋า 20 + กองลูก 150 + ไข่ฟัก 10 + ไข่ถือ 10) | 11,854 B | **0.28%** |
| **เต็มพิกัดทุกช่อง** (คอก 19 + กระเป๋า 100 + กองลูก 2,000 + ไข่ฟัก 50 + ไข่ถือ 50) | 99,312 B | **2.37%** |

แยกตามส่วน (เคสเต็มพิกัด): กองลูก 76,631 B · แม่ในกระเป๋า 11,749 B · ไข่ฟัก 4,301 B · แม่ในคอก 2,784 B · **ไข่ที่ถืออยู่ 2,113 B** · ความคืบหน้าต่อด่าน 585 B · `summonEnabled` 21 B

ไข่กินที่เพิ่มขึ้น 3,163 B จากรอบก่อน เพราะตอนนี้เก็บไข่ **รายฟองพร้อมน้ำหนัก** (`hatching` +1,050 B · `heldEggs` +2,081 B) — ยังไม่ถึง 0.08% ของลิมิต

**ฟิลด์ที่เพิ่มมารอบนี้แทบไม่กินที่เลย** `stageProgress` เป็นอาเรย์ยาวคงที่ 9 ช่อง แต่ละช่องเก็บแค่ 2 ตัวเลข:

| กรณี | ขนาด `stageProgress` |
|---|---:|
| ปกติ (กำลังตีอยู่ด่านเดียว อีก 8 ช่องเป็น `false`) | 118 B |
| worst case (สมมติทั้ง 9 ช่องมีค่า และเป็นเลข 10 หลักทั้งคู่) | 585 B |

worst case จริงเกิดไม่ได้ เพราะผู้เล่นตีทีละด่านเรียงกัน ด่านที่พังแล้วเซตกลับเป็น `false` ได้ — แต่ถึงเผื่อเต็มทั้ง 9 ช่องก็ยังเป็น **0.014% ของลิมิต**

*(วัดด้วย uid แบบ string `"987654321-42"` ซึ่งกินที่มากกว่าเลขล้วนประมาณ 10 bytes ต่อตัว — ที่แม่ 119 ตัวคือ ~1.4 KB ไม่มีนัยสำคัญ)*

### 9.2 ทำไมถึงปลอดภัยระยะยาว

**จำนวนลูกไม่มีผลต่อขนาดข้อมูลเลย** ลูก 5,000 ตัวกับ 500,000,000,000 ตัวในกองเดียวกันใช้ที่ต่างกันไม่กี่ตัวอักษร ตัวที่โตคือ *จำนวนกอง* ซึ่งถูกจำกัดด้วย (จำนวนแม่ × ประวัติสถานะ) ไม่ใช่ด้วยเวลาที่ผู้เล่นเล่น

การเลือกเก็บลูกเป็นกองจึงไม่ใช่แค่ประหยัดที่ แต่เป็นสิ่งที่**ทำให้เกมนี้เป็นไปได้เลย** ถ้าเก็บลูกรายตัวแบบเดียวกับแม่ ที่ 5 แสนล้านตัวจะกินพื้นที่ระดับเทราไบต์

ปัญหาที่จะมาถึงก่อนขนาดข้อมูล:
1. **UI คลัง** — 2,000 กอง × ปุ่มละ 1 Frame ทำให้เกมกระตุก ต้องทำ virtual scrolling
2. **request budget** — งบเขียน `60 + ผู้เล่น×10` ครั้ง/นาที autosave ทุก 60 วินาทีใช้แค่ 7 ครั้งที่ 7 คน สบาย แต่**ห้ามเซฟทุกครั้งที่ผลิตลูก**

### 9.3 กฎการเซฟของ DataStore ที่ต้องรู้

⚠️ **ข้อแรกคือเหตุผลที่ `hatching` ต้องเป็น array ยาวคงที่ 50 ช่อง**

| ห้าม | เกิดอะไรขึ้น |
|---|---|
| table ที่มี key ตัวเลขแบบมีรู เช่น `{[2] = x}` | encode ได้ `{"2": x}` decode กลับได้ key เป็น **string** `"2"` ไม่ใช่ number `2` → `hatching[2]` คืน nil ทั้งที่ข้อมูลไม่ได้หาย |
| table ที่ผสม array กับ string key ในตัวเดียว | SetAsync error |
| `nil` กลางอาเรย์ | อาเรย์ขาด ความยาวเพี้ยน |
| `Vector3` / `Color3` / `Enum` / `Instance` / function | เซฟไม่ได้เลย — **`Config.EggTypes[x].color` เป็น `Color3` ห้ามหลุดลง PlayerData** (มีคอมเมนต์เตือนใน Config แล้ว) |
| `NaN` / `inf` | encode ไม่ผ่าน — ระวังตอนหาร `produced / ratePerSecond` ถ้า rate เป็น 0 |
| จำนวนเต็มเกิน 9,007,199,254,740,992 (2⁵³) | เริ่มปัดเศษเงียบ ๆ — `MAX_CHILDREN_PER_STACK = 1e15` ตั้งไว้ต่ำกว่าเพดานนี้แล้ว |
| key ยาวเกิน 50 ตัวอักษร | error (`validate()` เช็ค `KEY_PREFIX` ให้แล้ว) |

> `children` เป็น dictionary ที่ key มี `|` และ `,` — **ปลอดภัย** เพราะเป็น string key ธรรมดา JSON รับได้หมด

วิธีกัน: เขียน `sanitizeForSave(data)` ตรวจตามกฎนี้แล้วเรียกก่อน `UpdateAsync` ทุกครั้ง ตอน dev ให้ `error()` ไปเลยจะได้เจอตั้งแต่เทสต์

## 10. แผนการ migration

### 10.1 กลไก

```
Config.SCHEMA_VERSION = 1     -- เลขปัจจุบันของโค้ดที่กำลังรัน

MIGRATIONS = { [1] = v1→v2, [2] = v2→v3, ... }
```

ตอนโหลด:

```
data = อ่านจาก DataStore
ถ้า data == nil                → สร้างจาก template (Config.NewPlayer) จบ
ถ้า data.schemaVersion == nil  → ถือว่าเป็น 1
ถ้า data.schemaVersion > Config.SCHEMA_VERSION → ⚠️ ห้ามเซฟทับ (ดู §10.2)

วนซ้ำ: ตราบใดที่ data.schemaVersion < Config.SCHEMA_VERSION
    data = MIGRATIONS[data.schemaVersion](data)
    data.schemaVersion += 1

เติมฟิลด์ที่ยังขาดจาก template (กัน migration ลืม)
validate: uid ในทีมมีจริงไหม / stack key parse ได้ไหม / charId ยังมีใน Config ไหม /
          จำนวนแม่เกินความจุไหม / ตัวเลขติดลบไหม
```

migration แต่ละตัวต้อง **idempotent** และ **ห้ามพึ่งค่าใน `Config` ปัจจุบัน** — Config เปลี่ยนได้ แต่ migration ต้องให้ผลเดิมเสมอ ถ้าต้องใช้ค่าคงที่ ให้ hard-code ไว้ในตัว migration เอง

### 10.2 กฎเหล็ก

| กฎ | เหตุผล |
|---|---|
| **เพิ่มฟิลด์ = เพิ่ม version + ใส่ default** | ห้ามเพิ่มเงียบ ๆ แล้วหวังว่าโค้ดจะเช็ค nil ครบ |
| **ห้ามลบฟิลด์เก่า ห้ามเปลี่ยนความหมาย** | ไม่ใช้แล้วก็ปล่อยไว้ ราคาไม่กี่ byte ถูกกว่าความเสี่ยง |
| **ห้าม reuse `charId` / `eggId` / `statusId` เดิมกับของใหม่** | ผู้เล่นที่มี `"wukong"` เก่าใน stack key จะกลายเป็นตัวใหม่ทันที |
| **ห้ามลด `nextUid`** | uid ซ้ำ = ทีมชี้ผิดแม่ |
| **`schemaVersion > ปัจจุบัน` → ห้ามเซฟทับ** | เกิดตอน rollback เซิร์ฟเวอร์ ถ้าเซฟทับข้อมูลใหม่หายถาวร ให้เล่นแบบ read-only แล้วแจ้งเตือน |
| **ทดสอบ migration ด้วยข้อมูลจริงก่อน publish** | ทำ key สำรอง `player_<id>_backup_v<n>` ก่อนรัน migration ครั้งแรกของแต่ละคน |

### 10.3 ตัวอย่างสถานการณ์

| อยากทำ | ต้อง migrate ไหม | วิธี |
|---|---|---|
| ปรับตัวคูณคลาส (SS ×5 → ×6) | ❌ ไม่ต้อง | อยู่ใน Config คำนวณตอน runtime |
| ปรับสูตรเงิน / damage / ราคา / HP ด่าน | ❌ ไม่ต้อง | เหมือนกัน |
| ปรับ tier น้ำหนัก / ตารางคลาสของไข่ | ❌ ไม่ต้อง | แม่ที่มีอยู่เก็บน้ำหนักกับ charId เป็นค่าตรง ไม่ได้เก็บ tier |
| เพิ่มตัวละคร / สถานะ / ไข่ชนิดใหม่ | ❌ ไม่ต้อง | ข้อมูลเก่าไม่รู้จักก็ไม่กระทบ |
| เพิ่มฟิลด์ `nickname` ให้แม่ | ✅ ต้อง | v1→v2 เติม `nickname = ""` ให้ทุกตัวทั้งสองอาเรย์ |
| **เปลี่ยนตัวคั่นของ stack key** | ⚠️ อันตรายที่สุด | ต้องอ่านทุก key เก่า parse ด้วยกฎเก่า เขียนใหม่ด้วยกฎใหม่ พลาดตรงไหน = ลูกหายทั้งกอง |
| **เปลี่ยน `CHILD_RATIO`** | ⚠️ อันตราย | key เก็บน้ำหนักแม่ ข้อมูลไม่พัง แต่ลูกเก่าทั้งหมดเปลี่ยนน้ำหนักย้อนหลังทันที |
| **ลบตัวละคร/สถานะออกจาก Config** | ⚠️ อันตราย | key เก่ายังมี id นั้น parse ได้แต่ lookup ไม่เจอ → ตั้ง `enabled = false` แทน อย่าลบ |

## 11. จุดเสี่ยง

### 🔴 เปลี่ยนทีหลังแล้วเจ็บ

| สิ่งที่ | เจ็บยังไง |
|---|---|
| **รูปแบบ stack key** (ตัวคั่น · กฎเรียง · ใช้ charId + น้ำหนักแม่) | เป็นคีย์ของ dictionary ที่เซฟไปแล้ว เปลี่ยนเมื่อไหร่ = กองลูกของทุกคนอ่านไม่ออก |
| **`charId` / `statusId` / `eggId`** | ฝังอยู่ใน stack key และใน `mothersInPen`/`Bag` ของทุกคน |
| **รูปแบบ `uid`** | ตัดสินแล้วเป็น global `"<UserId>-<n>"` ([§3.2](#32-ทำไม-uid-ต้องเป็น-global)) เปลี่ยนกลับเป็นเลขต่อผู้เล่นทีหลัง = ทีมที่ทุกคนจัดไว้พังหมด |
| **`CHILD_RATIO = 1%`** | ไม่ทำข้อมูลพัง แต่เปลี่ยนน้ำหนักลูกเก่าย้อนหลังทั้งหมด |
| **ฐานเวลาของ `hatchAt` / `lastProducedAt`** | สลับ absolute ↔ relative ทีหลัง = ไข่และการผลิตทั้งหมดคำนวณผิด |
| **แยก `mothersInPen` / `mothersInBag` เป็นสองอาเรย์** | รวมกลับเป็นอาเรย์เดียวทีหลังต้อง migrate ทุกตัว |
| **ชื่อ DataStore + รูปแบบ key** | เปลี่ยนแล้วผู้เล่นเก่าอ่านข้อมูลไม่เจอ = เริ่มใหม่หมด |
| **`wallProgress` เป็นตัวคูณเงิน** | ถ้าวันหนึ่งจะรีเซ็ตด่าน (prestige) ต้องคิดเรื่องเงินด้วย |
| **เก็บลูกเป็นกอง ไม่ใช่รายตัว** | ย้อนกลับไม่ได้ — ข้อมูลรายตัวไม่เคยมีอยู่ตั้งแต่แรก |

### 🟢 เปลี่ยนได้สบาย

ตัวคูณคลาส · สูตร damage/เงิน · ราคาทุกอย่าง · HP ด่าน/บอส · อัตราผลิต · cap 8 ชั่วโมง · tier น้ำหนัก · ตารางคลาสของไข่ · ชื่อไทยทุกอย่าง · **เพิ่ม** ตัวละคร/ไข่/สถานะ/tier ใหม่ · จำนวนโมเดลที่แสดง · UI ทั้งหมด

เพราะทั้งหมดนี้อยู่ใน Config และคำนวณตอน runtime ไม่ได้เซฟลงข้อมูลผู้เล่น

**เพดานใน `Config.Inventory` / `Pen` / `Bag` / `Hatchery`** — **เพิ่ม**ได้อิสระ แต่**ลดต้องระวัง** ผู้เล่นที่เกินเพดานใหม่ต้องมี policy รองรับ

## 12. จุดที่เสี่ยงโดนโกง (exploit)

ทุกข้อในตารางนี้ **ต้องตัดสินที่ server เท่านั้น** client มีหน้าที่ "ขอ" กับ "แสดงผล"

| จุด | ถ้าให้ client ตัดสินจะโดนโกงยังไง | ต้องทำที่ server |
|---|---|---|
| **การแย่งไข่** ⚠️ สำคัญสุด | client ส่ง "ฉันกดค้างครบ 3 วิแล้ว" → exploiter ส่งทันทีทุกครั้งที่ไข่โผล่ ได้ไข่ทุกฟองทุกรอบ | server จับเวลาเอง · เช็คว่าผู้เล่นอยู่ในระยะจริง · เช็คว่าถูกตีระหว่างนั้นไหม · **ไข่ 1 ฟองมีเจ้าของได้คนเดียว** ต้องมี lock กันสองคนได้พร้อมกัน |
| **การสุ่มน้ำหนัก/ตัวละครตอนฟัก** | client สุ่มเองแล้วส่งผล → ได้องค์ยูไล 100,000,000 kg ทุกฟอง | สุ่มที่ server ตอนไข่ครบเวลาเท่านั้น **ห้ามสุ่มล่วงหน้าแล้วเก็บไว้** (ถ้าเก็บไว้ exploiter อ่าน memory ได้ก็รู้ผลก่อน) |
| **การผลิตลูก** | client ส่ง "ฉันผลิตได้ 1,000,000 ตัว" | server คำนวณจาก `lastProducedAt` กับ `os.time()` เท่านั้น ไม่รับตัวเลขจาก client |
| **การคำนวณผลรบ** | client ส่ง "ฉันชนะแล้ว" → เปิดด่าน 9 ทันที | server คำนวณ damage รวมจาก `children` จริงที่มีอยู่ แล้วหักกองทัพที่ตายออกจริง |
| **เงิน** | client ส่ง "ให้เงินฉัน 10^15" | server คำนวณจากแม่ในคอกจริง × เวลาที่ผ่านจริง |
| **การซื้อ/อัปเกรด** | client ส่ง "ฉันอัปคอกเป็น Lv15 แล้ว" | server เช็คเงินพอไหม · เลเวลปัจจุบันถูกไหม · หักเงินเอง |
| **การเข้าพื้นที่บอส** | client teleport เข้าด่าน 9 ตั้งแต่เริ่มเกม | server เช็ค `wallProgress` ก่อนอนุญาต และเช็คซ้ำเป็นระยะว่าตำแหน่งผู้เล่นถูกต้อง |
| **การตีบอส** | client ส่ง damage เท่าไหร่ก็ได้ | server คำนวณ damage จาก `weaponLevel` ที่เซฟไว้ + rate limit จำนวนครั้งที่ตีต่อวินาที |
| **การตีกันนอกพื้นที่บอส** | client ตีคนอื่นได้ทุกที่ | server เช็คโซนก่อนรับ damage ทุกครั้ง |
| **ย้ายแม่เข้าคอก** | client ส่ง "ฉันมีแม่ 200 ตัวในคอก" | server เช็คความจุตาม `penLevel` จริง |

**กฎที่ใช้ได้กับทุกข้อ:** ทุก RemoteEvent ที่รับค่าจาก client ต้อง validate **ชนิดข้อมูล → ช่วงค่า → สิทธิ์ → สถานะปัจจุบัน** ตามลำดับ และต้องมี rate limit

### ตัดสินแล้วในรอบนี้

| เรื่อง | ผลสรุป |
|---|---|
| **`uid` เป็น global** | `"<UserId ผู้ฟักคนแรก>-<เลขนับ>"` เป็น **string** ไม่ใช่ number — รองรับการเทรดแม่ที่วางแผนไว้ ([§3.2](#32-ทำไม-uid-ต้องเป็น-global)) |
| **HP กำแพง/ทหารที่ตีค้าง เซฟลง DataStore** | ฟิลด์ `stageProgress` array 9 ช่อง (`defendersRemaining` + `wallHpRemaining`) ([§7.7](#77-ความคืบหน้าสะสมถาวร)) |
| **ระบบรบเป็นแบบปล่อยต่อเนื่อง (Age of War)** | ยกเลิก "กดส่งทีเดียวแล้วรอผล" ทั้งหมด · มีปุ่มอัญเชิญเปิด/ปิด · คลังมี cap ([§7](#7-การรบ--ปล่อยทหารต่อเนื่องแบบ-age-of-war)) |
| **ด่าน 1 ไม่มีกำแพงและไม่มีทหารฝ่ายรับ** | แก้ปัญหาไก่กับไข่: ผู้เล่นใหม่เดินไปหาบอสเอาไข่ได้ทันที (`validate()` บังคับไว้) |
| **อัตราผลิตแปรตามน้ำหนักแม่** | `(น้ำหนัก ÷ 100)^0.25` — แม่ 100M kg ผลิตเร็วกว่าแม่ 100 kg 31.6 เท่า ([§5.1](#51-อัตรา)) |
| **แม่ส่งรบได้เฉพาะจากกระเป๋า** | แม่ในคอกเลือกไม่ได้เลย · ห้าม auto ปล่อยแม่เด็ดขาด ([§7.4](#74-ตัวแม่ในสนามรบ--กติกาที่ห้ามพลิก)) |
| **บัฟสถานะ** | โครงพร้อมแล้ว 4 อย่าง: damage · เงิน · ความเร็วผลิต · น้ำหนักลูก (1% → 2%) ค่ายังไม่เปิด ([§6.3](#63-บัฟที่สถานะให้-โครงพร้อมแล้ว-ค่ายังไม่เปิด)) |
| **ไข่ตำนานใช้แบบ "รับประกันขั้นต่ำ"** | รับประกัน tier 3 ขึ้นไป · ตัด C ออก · มี S 18% และ SS 2% · **SS ออกจากไข่ตำนานเท่านั้น** |
| **ไข่จากบอสออกได้ C ถึง S** | ด่าน 7 ขึ้นไปแตะ S ได้ (1% → 20%) แต่ไม่มีทางได้ SS |
| **บอสแต่ละด่านวางไข่คนละชนิด** | `egg_stage1`…`egg_stage9` · `validate()` บังคับว่าทุกด่านต้องมีไข่ของตัวเอง ไม่งั้นด่านนั้นตันถาวร |
| **น้ำหนักสุ่มตั้งแต่บอสวางไข่ ไม่ใช่ตอนฟัก** | ขนาดโมเดลไข่ในรังบอกน้ำหนัก → การแย่งไข่มีเป้าหมายจริง · แลกด้วยการเก็บไข่รายฟองใน PlayerData ([§8.5.1](#851-ไข่รายด่าน-และน้ำหนักที่ล็อกตั้งแต่ในรัง)) |
| **`turretDps` ตั้งเป็นสัดส่วนของ damage/วินาที** | 10% (ด่าน 2) → 20% (ด่าน 9) · มียามกันค่าที่ทำให้เกมตัน |
| **cap คลัง 500 ตายตัว** | ไม่มีระบบอัปเกรด ตัด `STACK_CAP_START` ทิ้ง |
| **upgrade อัตราผลิตไม่แตะ** | รู้อยู่ว่ามันหยุดเพิ่ม damage ตั้งแต่ด่าน 3 แต่ปล่อยไว้ก่อน |
| **`egg_common` / `egg_rare` ปิดแล้ว** | `enabled = false` ไม่ลบทิ้ง (กฎ eggId) · ผู้เล่นใหม่ได้ `egg_stage1` แทน |
